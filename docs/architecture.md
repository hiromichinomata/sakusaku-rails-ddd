# うめチケット アーキテクチャ

## 層とフォルダ

| 層 | フォルダ | 置くもの | 依存してよいもの |
|----|---------|---------|----------------|
| プレゼンテーション | `app/controllers`・`app/views`・`app/mailers`・`app/forms` | HTTP・HTML・JSON・メール・入力の形の検証 | アプリケーション層・ドメイン層 |
| アプリケーション | `app/usecases/{コンテキスト}` | ユースケース（申し込む・支払う・キャンセルする） | ドメイン層・リポジトリ |
| ドメイン | `app/domain/{コンテキスト}`・`app/domain`（共有の値） | エンティティ・値オブジェクト・集約・ドメインサービス・ドメインイベント | Ruby の標準ライブラリだけ |
| インフラ | `app/infrastructure/{コンテキスト}`・`app/models` | リポジトリの実装・Active Record・外部サービスのアダプター | ドメイン層・Rails |

## 決めたこと

1. コアドメイン（予約・`Ticketing`）だけ、ドメインモデルを普通の Ruby のクラス（PORO）で書く
2. 支援サブドメイン（イベント管理）は、Active Record のモデルとコントローラだけで作る
3. `app/domain` のコードは Rails を読み込まずに動く。テストは `spec_helper` だけで実行する
4. ドメイン層は「今」を自分で取りに行かず、引数で受け取る（`now:`）
5. リポジトリは、コアドメインの集約にだけ作る
6. `app/services` は使わない。何でも入る場所になるため、置き場所は層で決める
7. Active Record のモデルは、コアドメインでは永続化のための入れ物として使う
8. 入力の形（空・形式・範囲）はフォームオブジェクト（`app/forms`）で、業務のルールはドメインで確かめる
9. ドメインのエラーと HTTP のステータスの対応は、コントローラ（`DomainErrorResponses`）だけが持つ
10. ほかのコンテキストのテーブルには書き込まない。決済の記録は `Billing::ChargeReservation` を通す
11. Active Record のモデルどうしの関連付けは、同じコンテキストの中だけにする（`Payment` と `Reservation` はIDでつなぐ）
12. 保存の入れ物（Active Record）には、業務の判断をするコールバックを書かない

## やらないこと

- 実装が1つしかないのに、インターフェース用の抽象クラスを作る
- イベント管理のような CRUD に、ユースケースやリポジトリを挟む
- すべてのクラスを PORO にする
