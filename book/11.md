# 第11章　ドメインサービスとアプリケーションサービス

**初花**: 残席の集約、予約のエンティティ、リポジトリ。部品は全部そろったよね。

**マリゴールド**: そろったよ。でも、まだ画面からの予約は、第3章の `Reservation` のバリデーションで動いている。この章で、部品を「申し込む」という手順に組み立てて、画面をつなぎ替えよう。

**初花**: 手順を組み立てるクラスって、サービスオブジェクト？ Railsでよく見る `ReservationService` みたいな。

**マリゴールド**: 近いけど、DDDでは「サービス」を2種類に分けるんだ。業務のルールを持つ **ドメインサービス** と、手順を並べる **アプリケーションサービス**（ユースケース）。この違いが、この章の中心だよ。

---

## 11.1　モデルに書く処理とサービスに書く処理

**初花**: そもそも、モデルに書けばいいことと、サービスに書くことの違いは？

**マリゴールド**: まず、**モデルに書けるなら、モデルに書く**。サービスは、どのモデルにも自然に置けない処理のための場所なんだ。第8章と第9章で作ったものを振り返ってみよう。

| 処理 | 置き場所 | 理由 |
|------|---------|------|
| 支払い金額 = 料金 × 人数 | `Ticketing::Reservation#total_price` | 予約が持っている値だけで計算できる |
| 人数は1〜4人 | `Ticketing::ReservationCount` | 人数という値の決まり |
| 残席を超えて予約しない | `Ticketing::Inventory#reserve` | 残席の集約が持つ数だけで判断できる |
| 二重予約しない | ？ | 1つの予約だけでは分からない。ほかの予約を調べる必要がある |
| 申し込む（調べて、席を押さえて、予約を作って、保存する） | ？ | いくつもの集約とリポジトリを、決まった順に使う |

**初花**: 下の2つが、どのモデルにも入らないんだ。

**マリゴールド**: そう。上は「ルール」、下は「手順」。ルールを持つのがドメインサービス、手順を並べるのがアプリケーションサービスだよ。

| | ドメインサービス | アプリケーションサービス（ユースケース） |
|---|--------------|----------------------------------|
| 持つもの | 業務のルール | 手順（何を、どの順で） |
| 置き場所 | `app/domain/ticketing/` | `app/usecases/ticketing/` |
| 知っているもの | ドメインのオブジェクト（と、リポジトリのメソッドの約束） | ドメイン・リポジトリ・トランザクション |
| 名前 | 業務の言葉（「二重予約のチェック」） | 業務の操作の動詞（「席を押さえる」） |
| テスト | Railsなし（`domain_helper`） | データベースあり（`rails_helper`） |

## 11.2　ドメインサービスが必要になるケース

**初花**: 二重予約のチェックは、どうしてドメインサービスなの？ 予約のエンティティに `double_booked?` を作ればよくない？

**マリゴールド**: 予約のエンティティは、**自分のこと** しか知らないからね。「同じイベントに、同じメールアドレスの有効な予約がほかにあるか」は、ほかの予約を探さないと分からない。エンティティにリポジトリを持たせると、エンティティがデータベースを知ることになってしまう。

| 置き方 | 問題 |
|-------|------|
| `Ticketing::Reservation#double_booked?` の中でリポジトリを呼ぶ | エンティティがデータベースを知る。ドメインのテストにデータベースが要る |
| `Ticketing::Inventory` に予約の一覧を持たせる | 第9章の案A。集約が大きくなる |
| ドメインサービスにして、リポジトリを外から渡す | ✅ ルールはドメイン層に、探し方はリポジトリに |

`app/domain/ticketing/double_booking_check.rb`:

```ruby
module Ticketing
  # 二重予約を調べるドメインサービス（R-03）。
  # 1つの予約だけでは分からないので、予約のリポジトリに問い合わせる。
  class DoubleBookingCheck
    def initialize(reservations)
      @reservations = reservations
    end

    def ensure_not_double_booked!(event_id:, email:)
      raise Reservation::AlreadyReserved if @reservations.active_exists?(event_id: event_id, email: email)
    end
  end
end
```

**初花**: `@reservations` は `Ticketing::ReservationRepository` だよね。ドメイン層がインフラ層を使っていいの？

**マリゴールド**: このクラスは、`ReservationRepository` という **名前を一度も書いていない** でしょう。受け取ったものの `active_exists?` を呼んでいるだけ。だから、テストでは同じメソッドを持つ偽物を渡せるし、ドメイン層だけでテストできるんだ。

`spec/domain/ticketing/double_booking_check_spec.rb`:

```ruby
require "domain_helper"

RSpec.describe Ticketing::DoubleBookingCheck do
  let(:email) { EmailAddress.new("hatsuka@example.com") }

  it "同じイベントに同じメールアドレスの有効な予約があれば、二重予約（R-03）" do
    reservations = double("予約のリポジトリ", active_exists?: true)

    expect { described_class.new(reservations).ensure_not_double_booked!(event_id: 1, email: email) }
      .to raise_error(Ticketing::Reservation::AlreadyReserved)
  end

  it "なければ何もしない" do
    reservations = double("予約のリポジトリ", active_exists?: false)

    expect { described_class.new(reservations).ensure_not_double_booked!(event_id: 1, email: email) }
      .not_to raise_error
  end
end
```

**初花**: 第10章では「テスト用の偽物のリポジトリは使わない」って言ってたよね。

**マリゴールド**: あれはユースケースのテストの話だったね。このテストで確かめたいのは「`active_exists?` が `true` なら二重予約のエラー」という **判断** だけで、データベースの制約までは関係ない。答えを決め打ちする `double` で十分なんだ。

⚠️ ドメインサービスは便利ですが、増やしすぎるとエンティティや値オブジェクトが「データだけの入れ物」になります（第18章の「名前だけのドメインサービス」）。まずエンティティ・値オブジェクト・集約に置けないかを考え、置けないものだけをドメインサービスにします。

## 11.3　アプリケーションサービスとユースケース

**初花**: 次はアプリケーションサービス。ユースケースって、何をするんだっけ。

**マリゴールド**: **一つの業務の操作を、最初から最後まで** 実行する。「申し込む」なら、こういう手順になるよ。

```text
「申し込む」のユースケース（Ticketing::ReserveSeats）
  1. 入力を値オブジェクトにする（申込者・人数）
  2. トランザクションを始める
  3. 受付期間を確かめる            … 受付期間（値オブジェクト）
  4. 二重予約を確かめる            … 二重予約のチェック（ドメインサービス）
  5. 残席を読み込んで、席を押さえる … 残席（集約）・リポジトリ
  6. 予約を作って保存する          … 予約（エンティティ）・リポジトリ
  7. トランザクションを終える
  8. 予約を返す
```

**初花**: ユースケースの中に、ルールそのものは書いてないんだね。「受付期間を確かめる」も「席を押さえる」も、ドメインのオブジェクトに頼んでる。

**マリゴールド**: そう。ユースケースは **段取り役** で、判断は全部ドメインに任せる。ユースケースに `if inventory.remaining_seats < count` のような判断が出てきたら、ドメインに移すサインだよ。

足りない部品が2つあります。受付期間と、申込から予約を作る方法です。

`app/domain/ticketing/sales_period.rb`:

```ruby
module Ticketing
  # 受付期間。イベントの開始時刻の前まで申込を受け付ける（R-04）
  class SalesPeriod < Data.define(:ends_at)
    class Closed < BusinessRuleViolation
      def initialize
        super("このイベントの受付は終了しました")
      end
    end

    def open_at?(time)
      time < ends_at
    end

    def ensure_open!(time)
      raise Closed unless open_at?(time)
    end
  end
end
```

`spec/domain/ticketing/sales_period_spec.rb`:

```ruby

  end

```

## 11.4　予約可能かどうかを判定する

**初花**: 予約できるかどうかの判断が、受付期間・二重予約・残席の3つに分かれたね。

**マリゴールド**: どれも予約のコンテキストのルールだけど、判断に要る情報の出どころが違うんだ。

| 判断 | ルール | 判断するもの | 要る情報 | 情報の出どころ |
|------|-------|------------|--------|-------------|
| 受付期間か | R-04 | `SalesPeriod`（値オブジェクト） | イベントの開始時刻 | イベント管理（上流） |
| 二重予約でないか | R-03 | `DoubleBookingCheck`（ドメインサービス） | ほかの有効な予約 | 予約のリポジトリ |
| 残席が足りるか | R-01 | `Inventory`（集約） | 定員・予約済みの人数 | 残席のリポジトリ |
| 料金はいくらか | R-12 | — | イベントの料金 | イベント管理（上流） |

**初花**: 開始時刻と料金は、イベント管理の `Event` から読むんだよね。ユースケースが `::Event.find` を呼んでいい？

**マリゴールド**: 第6章のコンテキストマップを思い出して。予約は下流で、上流のイベントを **自分の言葉に読み替える** と決めたよね。予約のコンテキストが要るのは、イベントの全部ではなく「料金」と「受付期間」だけ。その2つだけを持つ値を作って、読み替えはインフラ層に任せよう。

`app/domain/ticketing/sales_info.rb`:

```ruby
module Ticketing
  # 予約のコンテキストから見たイベント。申込の判断に要る料金と受付期間だけを持つ
  class SalesInfo < Data.define(:event_id, :price, :sales_period); end
end
```

`app/infrastructure/ticketing/sales_info_reader.rb`:

```ruby
module Ticketing
  # イベント管理（上流）のイベントを、予約のコンテキストの言葉（SalesInfo）に読み替える
  class SalesInfoReader
    def find(event_id)
      event = ::Event.find(event_id)
      SalesInfo.new(event_id: event.id, price: Money.new(event.price),
                    sales_period: SalesPeriod.new(ends_at: event.starts_at))
    rescue ActiveRecord::RecordNotFound
      raise NotFound, "イベント #{event_id} が見つかりません"
    end
  end
end
```

**初花**: `starts_at` が、予約のコンテキストでは `SalesPeriod` の `ends_at` になってる！ 第5章で気づいた「同じ列なのに、使われ方が違う」が、コードの名前になった。

**マリゴールド**: イベント管理にとっては「始まる時刻」、予約にとっては「受付が終わる時刻」。読み替える場所が1か所にあるから、もし「受付は開始の1時間前まで」とルールが変わっても、直すのはここと `SalesPeriod` だけで済むよ。

## 11.5　予約作成処理をユースケースとして実装する

部品がそろったので、申込のユースケースを書きます。

`app/usecases/ticketing/reserve_seats.rb`:

```ruby
module Ticketing
  # 申込のユースケース。席を押さえて、予約を作る
  class ReserveSeats
    def initialize(inventories: InventoryRepository.new, reservations: ReservationRepository.new,
                   sales_infos: SalesInfoReader.new)
      @inventories = inventories
      @reservations = reservations
      @sales_infos = sales_infos
      @double_booking = DoubleBookingCheck.new(reservations)
    end

    def call(event_id:, name:, email:, count:, now: Time.current)
      applicant = Applicant.new(name: name, email: email)
      count = ReservationCount.new(count)

      ApplicationRecord.transaction do
        sales_info = @sales_infos.find(event_id)
        sales_info.sales_period.ensure_open!(now)
        @double_booking.ensure_not_double_booked!(event_id: event_id, email: applicant.email)

        inventory = @inventories.find(event_id)
        inventory.reserve(count)
        @inventories.save(inventory)

        @reservations.add(
          Reservation.apply(event_id: event_id, applicant: applicant, count: count, price: sales_info.price)
        )
      end
    end
  end
end
```

| コード | 意味 |
|-------|------|
| `initialize` の引数の既定値 | ふだんは本物のリポジトリを使い、テストでは差し替えられる |
| `now: Time.current` | 第7章の決まり。ドメインには「今」を渡す。テストでは時刻を指定できる |
| `ApplicationRecord.transaction` | 11.6 |

ユースケースのテストは、本物のデータベースで、部品が正しくつながっているかを確かめます。

`spec/usecases/ticketing/reserve_seats_spec.rb`:

### 画面からの申込をつなぎ替える

**初花**: いよいよ、画面からの予約をこのユースケースにつなぐんだね。

**マリゴールド**: そう。Active Record の `Reservation` からは、業務のルールのバリデーション（定員・二重予約・受付期間）と `confirm_if_free` を外すよ。名前やメールアドレスが空でないか、という **入力の形** のバリデーションは、画面にエラーを出すためにまだ残しておく。入力の検証の分け方は、第13章でフォームオブジェクトを使って整えよう。

`app/models/reservation.rb`:

```ruby
class Reservation < ApplicationRecord
  belongs_to :event
  has_one :payment, dependent: :destroy

  enum :status, {
    pending: "pending",
    confirmed: "confirmed",
    canceled: "canceled",
    expired: "expired"
  }, default: :pending

  scope :active, -> { where(status: %w[pending confirmed]) }

  validates :name, presence: true
  validates :email, presence: true, format: { with: URI::MailTo::EMAIL_REGEXP }
  validates :quantity, numericality: { only_integer: true, greater_than: 0, less_than_or_equal_to: Ticketing::ReservationCount::MAX }

  before_create :copy_price_from_event
  after_create_commit :send_payment_request_mail, if: :pending?
  after_update_commit :send_confirmed_mail, if: -> { saved_change_to_status?(to: "confirmed") }

  def total_price
    Money.new(price) * quantity
  end

  private

  def copy_price_from_event
    self.price ||= event&.price
  end

  def send_payment_request_mail
    ReservationMailer.with(reservation: self).payment_request.deliver_later
  end

  def send_confirmed_mail
    ReservationMailer.with(reservation: self).confirmed.deliver_later
  end
end
```

**初花**: 60行あった `reservation.rb` が、すっきりした。残ってるのは入力の形のバリデーションと、メールのコールバックだけ。

コントローラは、入力の形を確かめてから、ユースケースを呼びます。ドメインのエラーは、画面のエラーメッセージに変えます。残席が足りないときは、第2章からの「人数が残りの席数（◯席）を超えています」をそのまま出すため、エラーが持っている残席の数を使います。

```ruby
    @event = Event.find(params[:event_id])

    return render_event_page unless @reservation.valid?

    reservation = Ticketing::ReserveSeats.new.call(
      event_id: @event.id, name: @reservation.name, email: @reservation.email, count: @reservation.quantity
    )
    notice = reservation.status == :confirmed ? "予約が確定しました。" : "仮予約しました。15分以内にお支払いください。"
    redirect_to reservation_path(reservation.id), notice: notice
  rescue Ticketing::Inventory::NotEnoughSeats => e
    @reservation.errors.add(:quantity, :exceeds_remaining_seats, count: e.remaining_seats)
    render_event_page
  rescue Ticketing::BusinessRuleViolation => e
    @reservation.errors.add(:base, e.message)
    render_event_page
  end
```

## 11.6　トランザクションの開始と終了をどこに置くか

**初花**: ユースケースの中に `ApplicationRecord.transaction` があるよね。リポジトリの中じゃなくて、ここなんだ。

**マリゴールド**: トランザクションの範囲は、「**どこまでを一緒に成功させたいか**」で決まる。それを知っているのは、手順を知っているユースケースだけなんだ。

| 置き場所 | どうなるか |
|---------|----------|
| リポジトリの `save` の中 | 残席の保存と予約の保存が、別々のトランザクションになる。片方だけ成功しうる |
| コントローラ | HTTPの入口が、データベースの都合を知ることになる。ジョブから呼ぶときに困る |
| ドメイン層 | Railsのトランザクションをドメインが知ることになる（第7章の決まりに反する） |
| ユースケース | ✅ 一つの業務の操作を、一つのトランザクションにできる |

**初花**: 本当に、残席の保存も一緒に元に戻るの？ 11.5のテストの「すり抜けても」のやつ。

**マリゴールド**: 試しに、ユースケースの `ApplicationRecord.transaction do` を `begin` に書き換えて（トランザクションをやめて）、そのテストだけを流してみよう。試したら元に戻すよ。

## 11.7　サービスオブジェクトを増やしすぎない設計

**初花**: ユースケースを作ったら、全部の操作をユースケースにしたくなってきた。イベントの登録も `RegisterEvent` にする？

**マリゴールド**: 第5章で、イベント管理は Rails の普通の作りで十分と決めたよね。ユースケースは、**ルールのある操作** を組み立てるためのもの。入力して保存するだけの操作には要らないよ。

| 作る | 作らない |
|------|--------|
| 複数の集約・リポジトリを決まった順に使う（申込・キャンセル） | 1つのモデルを保存するだけ（イベントの登録） |
| トランザクションの範囲を決める必要がある | 読むだけの画面（イベント一覧） |
| HTTP以外（ジョブ・コンソール）からも同じ手順で呼びたい | 画面の表示のための整形 |

**初花**: 名前の付け方の決まりもある？

**マリゴールド**: 業務の操作の **動詞** で名付けて、1つのクラスに1つの操作だけを入れる。`ReservationService` に `create`・`cancel`・`pay` を全部入れると、何でも入る場所になるからね。

| 名前 | 良くない理由 / 良い理由 |
|------|-------------------|
| ❌ `ReservationService` | 何をするか分からない。メソッドが増え続ける |
| ❌ `ReservationManager`・`ReservationHelper` | 同上 |
| ✅ `Ticketing::ReserveSeats` | 「席を押さえる（申し込む）」という1つの操作 |
| ✅ `Ticketing::ReleaseSeats` | 「席を戻す」という1つの操作 |
| ✅ `Ticketing::DoubleBookingCheck` | ドメインサービスは、業務のルールの名前 |

## マリゴールドの one more thing

**ユースケースの戻り値を、成功と失敗の「結果」にする書き方もある。**

この章のユースケースは、成功したら予約を返し、失敗したら例外を投げました。もう一つの書き方として、成功・失敗のどちらも `Result` のようなオブジェクトで返す方法があります（`Result.success(reservation)`・`Result.failure(:not_enough_seats)`）。呼び出す側が `rescue` ではなく `if result.success?` で分岐できるので、「失敗も業務の結果の一つ」であることがはっきりします。一方で、Rubyでは例外のほうが自然に書ける場面も多く、どちらが正しいということはありません。本書では、業務のルールに反したことを `BusinessRuleViolation` の例外で表し、第13章でHTTPのステータスコードに変える方法を扱います。
