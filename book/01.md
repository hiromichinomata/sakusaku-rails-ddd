# 第1章　ハンズオンの準備とアプリケーションの全体像

**初花**: ドメイン駆動設計、略してDDDの本を読んでみたんだ。エンティティ、値オブジェクト、集約……って用語は覚えたけど、自分のRailsアプリのどこに使えばいいのか、さっぱり分からなくて。

**マリゴールド**: よくある入り方だね。用語から入ると、「何に困ったときの道具なのか」が見えないまま形だけ真似ることになりやすいんだ。

**初花**: じゃあ、この本はどこから始めるの？

**マリゴールド**: 最初は **普通のRailsアプリ** を作る。業務のルールが増えてコードが苦しくなるのを体験してから、DDDで整理し直す。この章では、その長い開発の土台——起動できて、テストが走るRailsアプリ——を一緒に用意しよう。

## 1.1　本書で作るアプリケーションの仕様

**初花**: 何を作るかは決まってるの？

**マリゴールド**: **イベント予約・チケット販売サービス** だよ。名前は「うめチケット」。主催者がイベントを登録して、参加者が予約して、お金を払って、通知が届く。本書の最後まで、この一つのアプリを育てていく。

「うめチケット」は本書用の架空のサービスです。登場する人と、できることを整理しておきます。

| 登場人物 | やりたいこと |
|---------|-------------|
| 主催者 | イベントを登録する・定員を決める・申込状況を見る |
| 参加者 | イベントを探す・予約する・支払う・キャンセルする |
| サービス運営者 | 決済や通知の不具合を調べる・データの不整合を見つける |

**初花**: 道場の体験稽古の申込みを、いまは紙とメールでやってるんだよね。こういうのがあったら便利そう。

**マリゴールド**: まさにそういうイベントを想定しているよ。予約が一件確定するまでの流れを図にしてみよう。

```text
 主催者                     参加者                        うめチケット
───────                   ───────                      ─────────────
イベントを登録 ──────────────────────────────────▶ 定員・日時・料金を保存
                         イベントを選ぶ ────────────▶ 空きがあるか確かめる
                         人数を入れて予約 ──────────▶ 予約を作る（仮押さえ）
                         支払う ────────────────────▶ 決済サービスに依頼
                                                     決済が成功したら予約を確定
                         確認メールを受け取る ◀────── 通知を送る
```

**初花**: こうして見ると、やることはCRUDの延長に見えるけど……。

**マリゴールド**: 画面だけ見ればそうだね。難しいのは、画面に出てこない **業務のルール** の方なんだ。本書で扱うルールを先に並べておくよ。

| ルール | 例 | 主に扱う章 |
|--------|----|-----------|
| 定員を超えて予約できない | 定員20人のイベントに21人目は入れない | 第2章・第9章 |
| 同じ人が二重に予約できない | ボタンの連打で予約が2件できてはいけない | 第9章・第16章 |
| 予約人数には上限がある | 1回の予約で申し込めるのは4人まで | 第8章 |
| キャンセルには期限がある | 開催3日前を過ぎたら返金しない | 第14章 |
| 決済と予約の状態はずれることがある | 支払いは成功したのに予約が確定していない | 第14章・第15章 |
| 同時に申し込まれても定員を守る | 残り1席に2人が同時に申し込む | 第16章 |

**初花**: 最後の「同時に申し込まれても」って、`if` で人数を数えればよくない？

**マリゴールド**: 一人ずつ順番に来るなら、それで守れる。でも二つのリクエストがほぼ同時に「まだ1席空いてる」と読んだら、二人とも通ってしまうんだ。この問題は第16章で、実際に再現してから直すよ。

本書は次の順に進みます。

| 部 | やること | この部の成果物 |
|----|---------|--------------|
| 第I部 | 普通のRailsで作り、複雑になる様子を体験する | 動く予約アプリと、困りごとの一覧 |
| 第II部 | 業務の言葉と境界を整理する | 用語集・コンテキストマップ・ディレクトリ構成 |
| 第III部 | エンティティ・値オブジェクト・集約などを実装する | 予約まわりのドメインモデル |
| 第IV部 | コントローラ・外部サービス・並行処理とつなぐ | キャンセル・返金まで動くアプリ |
| 第V部 | テスト戦略を整え、アンチパターンを直す | ドメインルールを守るテスト一式 |
| 第VI部 | 運用し、新しい要件でモデルを育てる | 拡張できる予約アプリ |

**初花**: DDDっぽい話が始まるのは第II部からなんだ。

**マリゴールド**: そう。第I部では、あえてDDDを使わずに作る。困りごとを自分のコードで見ておくと、後のパターンが「何を解決しているのか」がはっきりするからね。

**初花**: Rubyはパソコンに入ってると思う。そのまま使っていい？

**マリゴールド**: まずバージョンを揃えよう。本書は2026年10月時点の最新版で進めるよ。

本書で使うバージョンです。

|-------------|-----------|------|

**初花**: `ruby 4.0.7` って出た。末尾の `arm64-darwin25` は？

**マリゴールド**: どのCPUとOS向けに作られたRubyか、という印だよ。Intel のMacやLinuxなら別の文字になるけど、先頭が `ruby 4.0.7` なら大丈夫。

```

```

### Dockerを確かめる

PostgreSQLは、パソコンに直接インストールせず **Docker** のコンテナとして動かします。[Docker Desktop](https://www.docker.com/products/docker-desktop/) を入れて起動し、次の二つでバージョンが表示されることを確かめてください。

```bash

```

**初花**: Rails 8 って、何も指定しないとSQLiteになるんじゃなかった？ わざわざPostgreSQLにする理由ある？

**マリゴールド**: いい質問。SQLiteでも予約アプリは作れるんだけど、本書の第16章では「同時に予約されたときに、データベースのロックでどう守るか」を試すんだ。その実験には、本番でよく使われるPostgreSQLの方が向いているから、最初から揃えておくよ。

| | SQLite | PostgreSQL |
|---|--------|-----------|
| 準備 | ファイル1つ。何もいらない | サーバーが必要（本書ではDocker） |
| 小さなアプリ | ✅ 十分 | ✅ 十分 |
| 行ロック（`SELECT ... FOR UPDATE`） | ❌ ない（書き込みはまとめて1本ずつ） | ✅ ある |
| 本書の第16章 | 同時予約の競合を再現しにくい | ✅ 再現して直せる |

## 1.3　Railsアプリケーションの作成

**初花**: いよいよ `rails new` だね。

**マリゴールド**: オプションを二つ付けるよ。データベースをPostgreSQLにするのと、標準のテストフレームワーク（Minitest）を入れないこと。テストはこの後、RSpecで書くからね。

作業用のフォルダで、次を実行します。

```bash
rails new ume_tickets --database=postgresql --skip-test
cd ume_tickets
```

実行結果（抜粋）:

```text
      create  README.md
      create  Rakefile
      create  .ruby-version
      ...
         run  git init from "."
Initialized empty Git repository in .../ume_tickets/.git/
      ...
         run  bundle install --quiet
      ...
       rails  solid_cache:install solid_queue:install solid_cable:install
```

| オプション | 意味 |
|-----------|------|
| `--database=postgresql` | データベースの接続先をPostgreSQLにする（`pg` gem が入る） |
| `--skip-test` | Minitest用の `test/` フォルダを作らない |

ファイルを一つも変えていない今のうちに、最初のコミットを作っておきます。Gitの使い方は1.4で説明するので、ここでは2行打つだけで大丈夫です。

```bash
git add .
git commit -m "Initial commit: rails new ume_tickets"
```

**初花**: ファイルがたくさんできた。全部覚えないとダメ？

**マリゴールド**: 今は五つだけでいい。残りは必要になった章で紹介するよ。

| 場所 | 中身 | 本書で触り始める章 |
|------|------|------------------|
| `app/` | モデル・コントローラ・ビューなど、アプリの本体 | 第1章（この章） |
| `config/routes.rb` | URLとコントローラの対応表 | 第1章 |
| `config/database.yml` | データベースへの接続設定 | 第1章 |
| `db/` | マイグレーションとテーブル定義 | 第2章 |
| `Gemfile` | 使うライブラリの一覧 | 第1章 |

ドメインモデルをどこに置くか（`app/models/` に入れるか、別のフォルダを作るか）は、第7章で決めます。

### PostgreSQLを起動する

アプリのフォルダ（`ume_tickets/`）に `compose.yaml` を作ります。

`compose.yaml`:

```yaml
services:
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
    ports:
      - "5432:5432"
    volumes:
      - db_data:/var/lib/postgresql

volumes:
  db_data:
```

```bash
docker compose up -d
docker compose ps
```

```text
NAME                IMAGE               COMMAND                  SERVICE             CREATED             STATUS              PORTS
ume_tickets-db-1    postgres:18         "docker-entrypoint.s…"   db                  4 seconds ago       Up 3 seconds        0.0.0.0:5432->5432/tcp
```

`STATUS` が `Up` になっていれば、PostgreSQLが動いています。`-d` は「裏で動かし続ける」という意味です。

⚠️ PostgreSQL 18 の公式イメージでは、データの保存先が `/var/lib/postgresql/data` から `/var/lib/postgresql` に変わりました。古い記事の `compose.yaml` をそのまま写すと、起動時にエラーになります。

### 接続設定を書く

`config/database.yml` の `default:` に、接続先の4行を足します。

```yaml
default: &default
  adapter: postgresql
  encoding: unicode
  # For details on connection pooling, see Rails configuration guide
  # https://guides.rubyonrails.org/configuring.html#database-pooling
  max_connections: <%= ENV.fetch("RAILS_MAX_THREADS") { 5 } %>
  host: <%= ENV.fetch("DB_HOST", "localhost") %>
  port: <%= ENV.fetch("DB_PORT", 5432) %>
  username: <%= ENV.fetch("DB_USERNAME", "postgres") %>
  password: <%= ENV.fetch("DB_PASSWORD", "postgres") %>
```

**初花**: `ENV.fetch("DB_HOST", "localhost")` って、どういう意味？

**マリゴールド**: 「環境変数 `DB_HOST` があればその値、なければ `localhost`」という書き方だよ。手元ではそのまま動いて、別の環境では環境変数で差し替えられる。パスワードの `postgres` は手元の開発用だけの値だからね。

⚠️ すでにパソコンでPostgreSQLを動かしていて5432番ポートが使われている場合は、`compose.yaml` の `ports` を `"5433:5432"` に変え、コマンドの前に `DB_PORT=5433` を付けて実行してください。

設定ができたら、開発用とテスト用のデータベースを作ります。

```bash
bin/rails db:create
```

```text
Created database 'ume_tickets_development'
Created database 'ume_tickets_test'
```

**初花**: データベースが二つできた。開発用とテスト用で分けるんだね。

**マリゴールド**: そう。テストはデータを作っては消すから、画面で触っている開発用のデータとは別にしておくんだ。

| データベース | 使うとき |
|-------------|---------|
| `ume_tickets_development` | `bin/rails server` で画面を触るとき |
| `ume_tickets_test` | `bundle exec rspec` でテストを走らせるとき |

## 1.4　Gitによる変更履歴の管理

**初花**: さっきの出力に `git init` ってあったね。Gitはもう準備できてるの？

**マリゴールド**: リポジトリは `rails new` が作ってくれて、1.3 で最初のコミットも作ったね。その後に足した `compose.yaml` と、書き換えた `database.yml` が、まだコミットされていない状態だよ。

```bash
git status --short
```

```text
 M config/database.yml
?? compose.yaml
```

| 記号 | 意味 |
|------|------|
| `M` | 前のコミットから変更されたファイル |
| `??` | Gitがまだ管理していない新しいファイル |

この二つを、2つ目のコミットにします。

```bash
git add .
git commit -m "Set up PostgreSQL"
git log --oneline
```

```text
f5189d7 Set up PostgreSQL
72863b3 Initial commit: rails new ume_tickets
```

ハッシュ（先頭の英数字）は環境ごとに変わります。

**初花**: 最初のコミットを `rails new` の直後に作ったのは、なんで？

**マリゴールド**: 生成されたものと、自分で変えたものを分けておくためだよ。こうしておくと、2つ目のコミットには自分の変更だけが入る。

```bash
git show --stat HEAD
```

```text
...
 compose.yaml        | 13 +++++++++++++
 config/database.yml |  4 ++++
 2 files changed, 17 insertions(+)
```

本書では、次の単位でコミットしていきます。

| タイミング | 例 |
|-----------|----|
| 節やハンズオンの区切り | 「予約テーブルを追加」「定員チェックを追加」 |
| テストが通ったとき | 赤（失敗）→ 緑（成功）になった直後 |
| リファクタリングの前 | 第3章以降、DDDで書き直す直前 |

**初花**: リファクタリングの前にもコミットするんだ。

**マリゴールド**: 第18章では、問題のあるコードと直したコードをBefore／Afterで比べる。コミットが細かく残っていれば、`git diff` だけでその比較ができるんだ。

`.gitignore` も `rails new` が用意してくれています。ログ（`log/`）、一時ファイル（`tmp/`）、秘密鍵（`config/*.key`）、環境変数のファイル（`.env*`）は、コミットされません。

```bash
git check-ignore -v log/development.log .env
```

```text
.gitignore:14:/log/*	log/development.log
.gitignore:11:/.env*	.env
```

## 1.5　テストを実行できる開発環境を整える

**初花**: テストって、機能を作ってから最後に書くものだと思ってた。

**マリゴールド**: 本書では、機能より先にテストが走る状態を作っておく。DDDで書き直すときに「動きは変わっていない」と言い切れるのは、テストがあるからなんだ。

### RSpecを入れる

`Gemfile` の `group :development, :test do` の中に、`rspec-rails` を足します。

```ruby
group :development, :test do
  # See https://guides.rubyonrails.org/debugging_rails_applications.html#debugging-with-the-debug-gem
  gem "debug", platforms: %i[ mri windows ], require: "debug/prelude"

  # Audits gems for known security defects (use config/bundler-audit.yml to ignore issues)
  gem "bundler-audit", require: false

  # Static analysis for security vulnerabilities [https://brakemanscanner.org/]
  gem "brakeman", require: false

  # Omakase Ruby styling [https://github.com/rails/rubocop-rails-omakase/]
  gem "rubocop-rails-omakase", require: false

  # Testing framework [https://rspec.info/]
  gem "rspec-rails", "~> 8.0"
end
```

```bash
bundle install
bin/rails generate rspec:install
```

```text
      create  .rspec
      create  spec
      create  spec/spec_helper.rb
      create  spec/rails_helper.rb
```

| ファイル | 役割 |
|---------|------|
| `.rspec` | `rspec` コマンドの既定のオプション |
| `spec/spec_helper.rb` | Railsを読み込まない、RSpec全体の設定 |
| `spec/rails_helper.rb` | Railsを読み込み、テスト用データベースにつなぐ設定 |

**初花**: `spec_helper` と `rails_helper` の二つがあるのはなんで？

**マリゴールド**: Railsを読み込むと、テストの起動が少し遅くなるからだよ。第8章で作る値オブジェクトのように、Railsに頼らないクラスは `spec_helper` だけで速くテストできる。今は区別があることだけ覚えておいて。

この時点でテストを実行してみます。

```bash
bundle exec rspec
```

```text
No examples found.


Finished in 0.0002 seconds (files took 0.04254 seconds to load)
0 examples, 0 failures
```

テストがまだ一つもないので、0件です。

### 環境を確かめるテストを書く

最初のテストは、「本書のバージョンで動いているか」「テスト用データベースにつながるか」を確かめるものにします。

`spec/setup/environment_spec.rb`:

```ruby
require "rails_helper"

RSpec.describe "開発環境" do
  it "Ruby 4.0 で動いている" do
    expect(RUBY_VERSION).to start_with("4.0")
  end

  it "Rails 8.1 で動いている" do
    expect(Rails.version).to start_with("8.1")
  end

  it "テスト用の PostgreSQL に接続できる" do
    connection = ActiveRecord::Base.connection
    expect(connection.adapter_name).to eq("PostgreSQL")
    expect(connection.current_database).to eq("ume_tickets_test")
  end
end
```

```bash
bundle exec rspec --format documentation
```

```text
開発環境
  Ruby 4.0 で動いている
  Rails 8.1 で動いている
  テスト用の PostgreSQL に接続できる

Finished in 0.05718 seconds (files took 0.69932 seconds to load)
3 examples, 0 failures
```

**初花**: 3件とも通った！ `--format documentation` を付けると、`it` に書いた日本語がそのまま並ぶんだね。

**マリゴールド**: テストの説明が、そのまま仕様の一覧として読めるでしょう。第4章で業務ルールを文章にするとき、この書き方が効いてくるよ。

| コード | 意味 |
|-------|------|
| `RSpec.describe "開発環境"` | 何についてのテストか（グループ） |
| `it "..." do ... end` | 確かめたいこと1つ |
| `expect(実際の値).to eq(期待する値)` | 値が等しいかを確かめる |
| `start_with("4.0")` | 文字列が「4.0」で始まるか |

### 次の日、テストが動かない

**初花**: 次の日にパソコンを立ち上げて、同じテストを流したら……全部エラーになった。昨日は通ったのに。

```text
An error occurred while loading ./spec/setup/environment_spec.rb.
Failure/Error: ActiveRecord::Migration.maintain_test_schema!

ActiveRecord::ConnectionNotEstablished:
  connection to server at "::1", port 5432 failed: Connection refused
  	Is the server running on that host and accepting TCP/IP connections?
  connection to server at "127.0.0.1", port 5432 failed: Connection refused
  	Is the server running on that host and accepting TCP/IP connections?
# ./spec/rails_helper.rb:33:in '<top (required)>'
...
No examples found.


Finished in 0.00003 seconds (files took 0.61096 seconds to load)
0 examples, 0 failures, 1 error occurred outside of examples
```

**マリゴールド**: 芯は `Connection refused` と `Is the server running` の2行だよ。5432番ポートで待っているはずのPostgreSQLが動いていない。Docker Desktopを起動し直したあと、コンテナが止まったままなんだ。

**初花**: テストのコードじゃなくて、データベースの方だったんだ。`docker compose up -d` をやり直したら通った。

**マリゴールド**: `0 examples` なのに `1 error occurred outside of examples` と出たら、テストの中身より前、**読み込みの段階** で失敗している合図。まず環境を疑えばいいよ。

| エラーの見え方 | 疑う場所 |
|--------------|---------|
| `Connection refused`（5432） | PostgreSQLのコンテナが止まっている → `docker compose up -d` |

## ハンズオン 1-A — 次の日に作業を再開する

この章の成果物は「起動とテストができるRailsアプリケーション」です。パソコンを再起動した次の日を想定して、作業を再開する手順を一度通しておきます。

```bash
cd ume_tickets
docker compose up -d        # PostgreSQL を起動
bin/rails db:prepare        # データベースがなければ作る・マイグレーションを流す
bundle exec rspec           # テストが通るか
bin/rails server            # 画面を確かめる
```

`bundle exec rspec` の結果:

```text
....

Finished in 0.08235 seconds (files took 0.56737 seconds to load)
4 examples, 0 failures
```

**初花**: `db:create` じゃなくて `db:prepare` なんだね。

**マリゴールド**: `db:prepare` は、データベースがなければ作って、あればマイグレーションだけ流してくれる。毎回これを打っておけば、状態を気にしなくていいんだ。

データを消して最初からやり直したいときは、コンテナとデータの保存場所（ボリューム）をまとめて消してから起動し直します。

```bash
docker compose down -v
docker compose up -d
bin/rails db:prepare
```

```text
Created database 'ume_tickets_development'
Created database 'ume_tickets_test'
```

| コマンド | 何をするか | データ |
|---------|-----------|-------|
| `docker compose stop` | コンテナを止める | 残る |
| `docker compose down` | コンテナを消す | 残る |
| `docker compose down -v` | コンテナとボリュームを消す | ⚠️ **消える** |

## マリゴールドの one more thing

**`bin/ci` に RSpec を足しておくと、コミット前の確認が1コマンドになる。**

Rails 8.1 の `rails new` は、`bin/ci` というコマンドと、その手順を書いた `config/ci.rb` を用意してくれます。中身はセットアップ、RuboCopによるスタイルの確認、gemの脆弱性の確認、Brakemanによるセキュリティの確認などで、`--skip-test` を付けたのでテストの手順は入っていません。`config/ci.rb` の `CI.run do` の中に `step "Tests: RSpec", "bundle exec rspec"` の1行を足すと、`bin/ci` だけでスタイル・セキュリティ・テストをまとめて確かめられます。同じ手順はGitHub Actions（`.github/workflows/ci.yml`）でも動くので、第17章でテストが増えてきたら、ここを入り口に自動テストを整えていきます。
