**初花**: 課題一覧が、ほとんど全部片付いた。あとは本番に出すだけ？

**マリゴールド**: 本番に出してからが、もう一つの仕事の始まりなんだ。申込者から「返金されていない」と問い合わせが来たら、何が起きたかを調べられる？ 返金のジョブが失敗し続けていたら、誰が気づく？

## 20.1　ドメイン上の重要なイベントを記録する

**初花**: ドメインイベントは、もう発行してるよね。それをログに書けばいい？

**マリゴールド**: そう。第12章の one more thing で話したとおり、ドメインイベントに「記録する」購読者を足そう。Rails 8.1 から入った **`Rails.event`** を使うと、名前と中身を持った構造化されたイベントとして記録できる。まず、どんな形で記録されるかを確かめるよ。

ドメインイベントを `Rails.event` に流す記録係を作ります。

`app/infrastructure/audit/domain_event_recorder.rb`:

```ruby
module Audit
  # ドメインイベントを、Rails.event の構造化されたイベントとして記録する。
  # 業務の言葉（予約が作られた・キャンセルされた）でログを残し、予約IDでたどれるようにする。
  class DomainEventRecorder
    def call(event)
      payload = event.to_h.transform_values { |value| value.is_a?(Money) ? value.yen : value }
      Rails.event.notify(event.class.event_name, **payload)
    end
  end
end
```

`config/initializers/domain_events.rb`:

```ruby
# ドメインイベントの購読者を登録する。
# 開発中にコードを読み込み直すたびに呼ばれるので、先に同じイベントの購読を外してから登録し直す。
Rails.application.config.to_prepare do

  DomainEvents.subscribe(Ticketing::ReservationCreated, mail)
  DomainEvents.subscribe(Ticketing::ReservationConfirmed, mail)
  DomainEvents.subscribe(Ticketing::ReservationCanceled, Billing::RefundSubscriber.new)

  # すべてのドメインイベントを、業務の記録としてログに残す
  recorder = Audit::DomainEventRecorder.new
  events.each { |event_class| DomainEvents.subscribe(event_class, recorder) }
```

`app/jobs/billing/refund_payment_job.rb`:

```ruby
module Billing
  # 予約のキャンセルを受けて、決済サービスに返金を頼む。
  # 決済サービスにつながらなければ、少しずつ間をあけてやり直す。
  class RefundPaymentJob < ApplicationJob
    queue_as :default

    retry_on GatewayUnavailable, wait: :polynomially_longer, attempts: 5 do |job, error|
      reservation_id = job.arguments.first
      Payment.find_by!(reservation_id: reservation_id).update!(status: :refund_failed)
      Rails.event.notify("billing.refund_failed", reservation_id: reservation_id, error: error.message)
    end

    def perform(reservation_id, amount_yen)
      payment = Payment.find_by!(reservation_id: reservation_id)
      return if payment.refunded? # すでに返金済みなら、もう一度は頼まない

      # やり直しでも同じ冪等キーを使うので、決済サービスが2回返金することはない
      refund_id = Billing.gateway.refund(charge_id: payment.charge_id, amount: Money.new(amount_yen),
                                         idempotency_key: "refund-reservation-#{reservation_id}")
      payment.update!(status: :refunded, refund_id: refund_id)
      Rails.event.notify("billing.refunded", reservation_id: reservation_id, charge_id: payment.charge_id,
                                             refund_id: refund_id, amount: amount_yen)
    end
  end
end
```

`Rails.event` に流れたイベントを、1行に1件のJSONとしてファイルに書きます。ログを集めるサービスに送るときは、このファイルを読み込ませます。

`config/initializers/event_log.rb`:

```ruby
# Rails.event で記録した業務のイベントを、1行に1件の JSON として log/events_{環境}.log に書く。
# ログを集めるサービスに送るときは、このファイルを読み込ませる。
class EventLogSubscriber
  # Rails 自身も Rails.event に出来事（SQL など）を流すので、業務のイベントだけを書く
  BUSINESS_EVENTS = %w[ticketing. billing.].freeze

  def initialize(path)
    @logger = Logger.new(path)
    @logger.formatter = ->(*, message) { "#{message}\n" }
  end

  def emit(event)
    return unless event[:name].start_with?(*BUSINESS_EVENTS)

    @logger.info(
      { at: Time.at(event[:timestamp] / 1_000_000_000r).iso8601(3), name: event[:name],
        payload: event[:payload], tags: event[:tags], context: event[:context] }.to_json
    )
  end
end

Rails.event.subscribe(EventLogSubscriber.new(Rails.root.join("log/events_#{Rails.env}.log")))
```

**初花**: `BUSINESS_EVENTS` で絞ってるのはなんで？

**マリゴールド**: 最初は絞らずに書いてみたんだけど、ファイルが SQL の行で埋まってしまったんだ。Rails 8.1 は、自分の出来事（`active_record.sql` など）も `Rails.event` に流している。業務のイベントの名前を `ticketing.`・`billing.` で始めると決めておいたから、それだけを書けばいいよ。

## 20.2　予約ID・決済IDを使ったログ追跡

**初花**: 画面から申し込んで、支払って、キャンセルしたら、どんなログになるの？

**マリゴールド**: その前に、**どのリクエスト、どのジョブで起きたか** も残すようにしよう。`Rails.event.set_context` で入れた値は、そのリクエストやジョブの中のイベントすべてに付くよ。

`app/controllers/application_controller.rb`（抜粋）:

```ruby
  allow_browser versions: :modern

  # 業務のイベントのログに、どのリクエストで起きたかを残す
  before_action { Rails.event.set_context(request_id: request.request_id) }
```

`app/controllers/api/base_controller.rb`（抜粋）:

```ruby
    include DomainErrorResponses

    before_action { Rails.event.set_context(request_id: request.request_id) }
```

`app/jobs/application_job.rb`（抜粋）:

```ruby
class ApplicationJob < ActiveJob::Base
  # 業務のイベントのログに、どのジョブで起きたかを残す
  before_perform { |job| Rails.event.set_context(job_id: job.job_id, job_class: job.class.name) }
```

## 20.3　個人情報をログに残さない

**初花**: ログに、申込者の名前やメールアドレスが残ってないか心配。

**マリゴールド**: 2つの段で守っているよ。まず、ドメインイベントそのものに、名前やメールアドレスを入れていない（第12章で「IDと要点だけ」と決めた）。次に、うっかり入れても、`Rails.event` が伏せてくれる。テストで確かめておこう。

`spec/infrastructure/audit/domain_event_recorder_spec.rb`:

```ruby
require "rails_helper"

RSpec.describe Audit::DomainEventRecorder do
  # Rails.event に流れたイベントを集める
  let(:collector) do
    Class.new do
      attr_reader :events

      def initialize
        @events = []
      end

      def emit(event)
        events << event
      end
    end.new
  end
  let(:reported) { collector.events }

  around do |example|
    Rails.event.subscribe(collector)
    example.run
  ensure
    Rails.event.unsubscribe(collector)
  end

  it "ドメインイベントを、業務の名前のイベントとして記録する。金額は円の数にする" do
    event = Ticketing::ReservationCanceled.new(reservation_id: 1, event_id: 2, refund_amount: Money.new(3000),
                                               occurred_at: Time.current)

    described_class.new.call(event)

    expect(reported.last).to include(name: "ticketing.reservation_canceled")
    expect(reported.last[:payload]).to include(reservation_id: 1, event_id: 2, refund_amount: 3000)
  end

  it "ドメインイベントには、申込者の名前やメールアドレスを入れていない" do
    events = [ Ticketing::ReservationCreated, Ticketing::ReservationConfirmed, Ticketing::ReservationCanceled,
               Ticketing::ReservationExpired ]

    expect(events.flat_map(&:members)).not_to include(:name, :email, :applicant)
  end

  it "うっかりメールアドレスを記録しても、伏せられる" do
    Rails.event.notify("ticketing.something", reservation_id: 1, email: "hatsuka@example.com")

    expect(reported.last[:payload]).to eq(reservation_id: 1, email: "[FILTERED]")
  end
end
```

```text
Audit::DomainEventRecorder
  ドメインイベントを、業務の名前のイベントとして記録する。金額は円の数にする
  ドメインイベントには、申込者の名前やメールアドレスを入れていない
  うっかりメールアドレスを記録しても、伏せられる

Finished in 0.02022 seconds (files took 1.02 seconds to load)
3 examples, 0 failures
```

| 個人情報の守り方 | 守れるもの | 気をつけること |
|------------|---------|------------|
| ドメインイベントにIDだけを入れる | 業務のイベントのログ | 第18章の「イベントで状態を運ぶ」を選ぶと、名前やメールアドレスが入る |
| `config.filter_parameters` | `Rails.event`・リクエストのパラメータ・`inspect` の表示 | `name`（お名前）は既定では入っていない。必要なら足す |
| ログを集めるサービスの保存期間 | 古いログ | 業務で決める（問い合わせに答えられる期間） |

⚠️ `config.filter_parameters` の既定には、`name` は入っていません。申込者の名前もログから伏せたいときは、`config/initializers/filter_parameter_logging.rb` に足します。ただし、`name` のような短い名前は、関係のない項目（イベントの名前など）まで伏せてしまうことがあるので、伏せたい項目の名前を見直してから決めてください。

## 20.4　失敗したジョブを調査する

**初花**: ジョブが失敗したら、どこを見ればいい？ 開発中は、ジョブってメモリの中で動いてるんだよね。

**マリゴールド**: そう、今の開発環境はメモリの中（`Async`）で動かしているから、失敗しても何も残らない。本番では Solid Queue がジョブをデータベースに保存して、失敗も記録してくれる。開発環境でも本番と同じ Solid Queue を使うようにしよう。

`config/database.yml` の開発環境に、ジョブ用のデータベースを足します。本番の設定（`queue:`）と同じ形です。

`config/database.yml`（抜粋）:

```yaml
development:
  primary:
    <<: *default
    database: ume_tickets_development
  # ジョブ（Solid Queue）は、本番と同じように別のデータベースに置く
  queue:
    <<: *default
    database: ume_tickets_development_queue
    migrations_paths: db/queue_migrate
```

`config/environments/development.rb`（抜粋）:

```ruby
  # 決済は、手元で動く偽物の窓口を使う（Billing.gateway）
  config.x.payment_gateway = :fake

  # ジョブは、本番と同じ Solid Queue で動かす（bin/jobs、または SOLID_QUEUE_IN_PUMA=1 bin/rails server）
  config.active_job.queue_adapter = :solid_queue
  config.solid_queue.connects_to = { database: { writing: :queue } }
```

```bash
bin/rails db:prepare
```

```text
Created database 'ume_tickets_development_queue'
```

ジョブを動かす係は、`bin/jobs` で起動します（サーバーと一緒に動かすなら `SOLID_QUEUE_IN_PUMA=1 bin/rails server`）。

最初に `bin/jobs` を起動したとき、ジョブを動かす係が PostgreSQL につなぐところで、Ruby ごと落ちました。

```text
/Users/you/.rbenv/versions/4.0.7/lib/ruby/gems/4.0.0/gems/pg-1.7.0-arm64-darwin/lib/pg/connection.rb:1033: [BUG] Segmentation fault at 0x00000001250808f3
ruby 4.0.7 (2026-09-15 revision 229531a6cf) +PRISM [arm64-darwin25]
```

**初花**: Segmentation fault……。こわい。

**マリゴールド**: macOS で、プロセスを分けた（fork した）あとに pg の gem で接続すると起きることがある問題なんだ。PostgreSQL の通信の暗号化の交渉（GSSAPI）を切ると直る。`database.yml` の接続の設定に足しておこう。

`config/database.yml`（抜粋）:

```yaml
  password: <%= ENV.fetch("DB_PASSWORD", "postgres") %>
  # macOS で、Solid Queue のワーカー（fork したプロセス）が接続時に落ちるのを防ぐ
  gssencmode: disable
```

わざと失敗するジョブ（存在しない予約の返金）を積んで、`bin/jobs` に動かしてもらいます。



**初花**: 何のジョブが、どの引数で、どんな例外で失敗したかが分かる。予約998の決済の記録がないんだ。

**マリゴールド**: 調べたら、やり直すか、捨てるかを決める。今回は存在しない予約だから、捨てよう。

|------------|--------|-------|
| 外部サービスの一時的な障害で、やり直しの回数を使い切った | 原因が直ってから、やり直す | `failed.retry` |
| 何度やっても通らない（存在しない予約・プログラムの誤り） | 原因を記録して、捨てる | `failed.discard` |
| 業務として失敗を残してある（返金に失敗した決済） | 業務の手順で対応する（20.7） | — |

⚠️ 失敗したジョブを画面で一覧にし、やり直し・捨てるを操作できる `mission_control-jobs` という gem もあります。本番で運用するなら、管理者だけが見られるようにして入れておくと便利です。

## 20.5　データ不整合を検知する

**初花**: 第16章で、「残席の人数 ＝ 有効な予約の合計」は、ずれたら検知する、って言ってたよね。

**マリゴールド**: ユースケースを通れば、ずれない。でも、コンソールで予約を直接書き換えたり、プログラムに誤りがあったりすれば、ずれる。**ずれたことに気づける** ように、突き合わせる仕組みを作ろう。

`app/infrastructure/ticketing/inventory_consistency_check.rb`:

```ruby
module Ticketing
  # 残席の「予約済みの人数」と、有効な予約の人数の合計がずれていないかを調べる（第16章の 16.8）
  class InventoryConsistencyCheck
    Mismatch = Data.define(:event_id, :recorded, :actual)

    def call
      actual = ::Reservation.active.group(:event_id).sum(:quantity)

      TicketInventory.order(:event_id).filter_map do |inventory|
        counted = actual.fetch(inventory.event_id, 0)
        next if inventory.reserved_count == counted

        Mismatch.new(event_id: inventory.event_id, recorded: inventory.reserved_count, actual: counted)
      end
    end
  end
end
```

## 20.6　マイグレーションと既存データ

**初花**: 本番のデータが入っているテーブルに、列を足したり制約を付けたりするのは、怖いね。

**マリゴールド**: 第9章と第10章で、既存のデータを移しながらテーブルを変えるマイグレーションを2つ書いたよね。第9章では「今のデータに定員を超えた予約がまぎれていたら、`CHECK` 制約に引っかかってマイグレーションが失敗する」とも話した。本当にそうなるか、確かめてみよう。

第8章の時点のアプリで、実験用のデータベースに、定員4人のイベントへ6人分の予約を入れます（`insert_all` はバリデーションを通りません）。

```text
定員 4人 / 有効な予約 6人
```

そこへ、第9章のマイグレーション（`CreateTicketInventories`）を流します。

```text
== 20261018111741 CreateTicketInventories: migrating ==========================
PG::CheckViolation: ERROR:  new row for relation "ticket_inventories" violates check constraint "reserved_count_within_capacity"
```

**初花**: 本当に止まった！ マイグレーションの中の `INSERT` が、6人の残席を作ろうとして、制約に引っかかったんだね。

**マリゴールド**: データベースのマイグレーションは、1つのトランザクションの中で動くから、途中で止まっても中途半端には残らない。そして、**今のデータが壊れていることを教えてくれた**。本番で同じことが起きたら、まず壊れているデータを直してから、もう一度流すんだ。

⚠️ この実験のように別のデータベースを作って試したら、片付けには注意してください。開発環境で `bin/rails db:drop` を流すと、テスト用のデータベースまで消えます。消えてしまったら `bin/rails db:test:prepare` で作り直します。

本番のデータを扱うマイグレーションの決めごとです。

| 決めごと | 本書の例 |
|--------|--------|
| 列を足すときは、まず空を許して足し、データを入れてから `null: false` にする | 第10章の `AddPriceToReservations` |
| 今のデータから、新しいテーブルを作る | 第9章の `CreateTicketInventories`（`INSERT ... SELECT`） |
| 制約は、今のデータが守っていることを確かめてから付ける | この節の実験 |
| 大きなテーブルのデータを書き換えるときは、少しずつ（`in_batches`）行う | うめチケットはまだ小さい |
| 戻せるように書く（`down` や `reversible`） | 第9章・第10章 |
| 流す前に、本番に近いデータで試す | この節の実験 |

## 20.7　本番障害を想定した運用演習

**初花**: 運用の演習って、何をするの？

**マリゴールド**: 「もし◯◯が起きたら」を決めて、**実際に手を動かして** 直してみるんだ。一番起きそうなのは、決済サービスのうめペイが止まることだね。止まっている間にキャンセルが来ると、返金のジョブは5回やり直したあと「返金に失敗」になる（第14章）。直ったあとに、それを見つけて、やり直す手順を作ろう。

返金に失敗した決済を、返金のジョブに積み直すユースケースです。

`app/usecases/billing/retry_failed_refunds.rb`:

```ruby
module Billing
  # 返金に失敗した決済を、返金のジョブに積み直す。決済サービスが直ったあとに、運用で使う
  class RetryFailedRefunds
    # 積み直した予約のIDの一覧を返す
    def call
      Payment.refund_failed.order(:id).map do |payment|
        RefundPaymentJob.perform_later(payment.reservation_id, payment.amount)
        payment.reservation_id
      end
    end
  end
end
```

`lib/tasks/billing.rake`:

```ruby
namespace :billing do
  desc "返金に失敗した決済を一覧にする"
  task failed_refunds: :environment do
    payments = Payment.refund_failed.order(:id)
    puts "返金に失敗した決済: #{payments.size}件"
    payments.each { |p| puts "  予約 #{p.reservation_id}: #{Money.new(p.amount)}（支払いID #{p.charge_id}）" }
  end

  desc "返金に失敗した決済を、返金のジョブに積み直す"
  task retry_failed_refunds: :environment do
    ids = Billing::RetryFailedRefunds.new.call
    puts "返金のジョブを積み直した予約: #{ids.inspect}"
  end
end
```

演習の流れを、そのままテストにしておきます。手順が変わっても、演習が通るかを毎回確かめられます。

```ruby
# 運用演習：うめペイが止まっている間にキャンセルが来て、直ったあとに返金をやり直す（docs/runbook.md）
RSpec.describe "決済サービスの障害の演習" do
  let(:event) { create(:event, price: 1500, starts_at: Time.zone.local(2026, 11, 15, 10, 0)) }
  let(:gateway) { Billing::FakePaymentGateway.new }
  let(:reservation) do
    Ticketing::ReserveSeats.new.call(event_id: event.id, name: "初花", email: "hatsuka@example.com", count: 2)
  end
  let(:payment) { Payment.find_by!(reservation_id: reservation.id) }

  before do
    allow(Billing).to receive(:gateway).and_return(gateway)
    Ticketing::PayForReservation.new.call(reservation_id: reservation.id, token: "tok_visa")
  end

  it "止まっている間のキャンセルは返金に失敗し、直ったあとに積み直すと返金される" do
    # 1. うめペイが止まる
    allow(gateway).to receive(:refund).and_raise(Billing::GatewayUnavailable, "うめペイにつながりませんでした")

    # 2. その間にキャンセルが来る。返金のジョブは5回やり直して、失敗として記録される
    perform_enqueued_jobs { Ticketing::CancelReservation.new.call(reservation_id: reservation.id) }

    expect(Payment.refund_failed.pluck(:reservation_id)).to eq([ reservation.id ])

    allow(gateway).to receive(:refund).and_call_original

    expect(payment.reload).to be_refunded
  end
end
```

`docs/runbook.md`:

````markdown
# うめチケット 運用の手順書

## 予約をたどる

業務のイベントは `log/events_{環境}.log` に1行1件の JSON で残る。予約IDでたどる。

```bash
grep '"reservation_id":1[,}]' log/events_production.log
```

| イベント | 起きたこと |
|---------|---------|
| `ticketing.reservation_created` | 申込を受け付けた（仮予約・予約確定） |
| `billing.charged` | 支払い金額を受け取った（支払いID） |
| `ticketing.reservation_confirmed` | 予約確定になった |
| `ticketing.reservation_canceled` | キャンセルされた（返金する金額） |
| `ticketing.reservation_expired` | 支払い期限を過ぎて、期限切れになった |
| `billing.refunded` | 返金した（返金ID） |
| `billing.refund_failed` | 返金を5回やり直しても失敗した |
| `ticketing.inventory_mismatch` | 残席の予約済みの人数と、有効な予約の合計がずれている |

`context` の `request_id`（画面・API）や `job_class`（ジョブ）で、どこで起きたかが分かる。

## 決済サービス（うめペイ）が止まった

1. `billing.refund_failed` が増えていないかを見る
2. `bin/rails billing:failed_refunds` で、返金に失敗した決済を一覧にする
3. うめペイが直ったことを確かめてから、`bin/rails billing:retry_failed_refunds` で積み直す
4. もう一度 `bin/rails billing:failed_refunds` を流し、0件になったことを確かめる

同じ冪等キーで頼むので、積み直しても二重に返金されない。

## 残席がずれた

1. `bin/rails ticketing:check_inventory` で、ずれているイベントを一覧にする
2. 予約IDでログをたどり、ユースケースを通らずに変わった予約を探す（コンソールでの書き換えなど）
3. 直し方を決めてから、残席か予約のどちらかを直す。直したら、もう一度 `ticketing:check_inventory` を流す

## 失敗したジョブ

```bash
bin/rails runner 'SolidQueue::FailedExecution.order(:id).each { |f| puts [f.job.class_name, f.job.arguments["arguments"].inspect, f.exception_class, f.message].join(" / ") }'
```

- 直せば通るもの（外部サービスの一時的な障害）は、原因が直ってから `retry`
- 何度やっても通らないもの（存在しない予約など）は、原因を記録してから `discard`
````

## マリゴールドの one more thing

**監視は「業務の数字」も見よう。**

サーバーのCPUやエラーの件数だけでなく、業務のイベントの件数も、監視のグラフにしておくと役に立ちます。たとえば「1時間あたりの `ticketing.reservation_created`」が急に0になったら、エラーが出ていなくても、申込の画面が壊れているかもしれません。「`ticketing.reservation_expired` が急に増えた」なら、決済の画面に何か起きている可能性があります。業務のイベントの名前を決めてあるので、こうしたグラフは、ログを集めるサービスで名前ごとに数えるだけで作れます。何を「いつもと違う」とするかは、主催者や運用の担当者と一緒に決めてください。
