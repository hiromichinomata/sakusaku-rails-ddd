# 第17章　DDDに適したテスト戦略

**初花**: テストが150件を超えたね。第1章では3件だったのに。

**マリゴールド**: 章ごとに必要なテストを足してきたからね。数が増えると、「このテストは何を守っているのか」「同じことを2か所で確かめていないか」が分かりにくくなる。この章では、ここまでのテストを **層ごとに** 整理しよう。

**初花**: 整理したら、何かいいことある？

**マリゴールド**: ルールを変えたときに、どのテストを流せばいいかがすぐ分かる。それに、コードの中身を入れ替えたときに、落ちてほしくないテストが落ちる、ということが減るよ。最後に、第1章で予告した `bin/ci` と GitHub Actions も整えよう。

---

## 17.1　ドメインモデルのユニットテスト

**初花**: まずは、層ごとにテストが何件あるかを見てみたい。

**マリゴールド**: フォルダごとに流して、件数と時間を測ってみよう。

```bash
bundle exec rspec spec/domain
```

```text
Finished in 0.00852 seconds (files took 0.08378 seconds to load)
46 examples, 0 failures
```

ほかのフォルダも同じように流した結果です。

| フォルダ | 件数 | 実行時間 | 読み込み |
|---------|-----|---------|--------|
| `spec/domain` | 46 | 0.009秒 | 0.08秒（Railsなし） |
| `spec/forms` | 3 | 0.06秒 | 0.68秒 |
| `spec/usecases` | 17 | 0.26秒 | 0.63秒 |
| `spec/infrastructure` | 28 | 0.13秒 | 0.63秒 |
| `spec/models` | 6 | 0.13秒 | 0.64秒 |
| `spec/jobs` | 9 | 0.27秒 | 0.67秒 |
| `spec/requests` | 44 | 0.95秒 | 0.64秒 |
| `spec/concurrency` | 2 | 1.14秒 | 0.62秒 |
| `spec/setup` | 3 | 0.02秒 | 0.61秒 |
| 合計 | 158 | — | — |

**初花**: ドメインのテストは46件もあるのに、合わせて0.01秒もかからない。リクエストスペックは44件で1秒近く。

**マリゴールド**: ドメインのテストは、データベースもHTTPもなく、Rubyのオブジェクトを作って確かめるだけだからね。**業務のルールの細かい組み合わせは、ここで確かめる** のが一番効率がいい。

| ドメインのテストで確かめること | 例 |
|--------------------------|----|
| ルールの境界の値 | ちょうど72時間前は返金する、1秒過ぎたら返金しない |
| 作れない値 | 0人・5人の `ReservationCount` |
| できない状態遷移 | キャンセル済みは確定できない |
| 判断の組み合わせ | 二重予約のチェック（リポジトリは `double` で答えを決め打ち） |

## 17.2　値オブジェクトと集約のテスト

**初花**: 値オブジェクトと集約で、テストの書き方は違う？

**マリゴールド**: 確かめる性質が違うんだ。値オブジェクトは「作れるか・作れないか・等しいか」、集約は「操作のあとも不変条件が守られているか」。

| | 値オブジェクト（`Money`・`ReservationCount`） | 集約（`Inventory`） | エンティティ（`Ticketing::Reservation`） |
|---|---------------------------------------|-----------------|-------------------------------|
| 作るとき | 作れる値・作れない値の境界 | 不変条件に反する状態で作れない | — |
| 操作 | 計算の結果（`Money * 2`） | 操作の結果と、失敗したときに状態が変わらないこと | 状態遷移の表の ✅ と ❌ |
| 等しさ | 中身で等しい | — | IDで等しい |
| 例 | 「0人や5人では作れない」 | 「残席を超える人数は予約できず、予約済みの人数も変わらない」 | 「キャンセル済みは、予約確定に戻せない」 |

**初花**: 集約のテストの「失敗したときに状態が変わらない」は、大事そう。

**マリゴールド**: 例外を投げる前に途中まで状態を変えてしまうと、集約が中途半端な状態で残るからね。`Inventory#reserve` は、確かめてから数を変える順番になっている。テストでも、**失敗したあとの状態** まで確かめておこう。

## 17.3　アプリケーションサービスのテスト

**初花**: ユースケースのテストは、データベースを使ってるよね。ドメインと同じように速くできないの？

**マリゴールド**: 第10章で話したとおり、ユースケースのテストで確かめたいのは **部品のつながり** なんだ。リポジトリの変換、トランザクションの範囲、データベースの制約、ドメインイベントの発行。偽物では、そこが確かめられない。

| ユースケースのテストで確かめること | 例（第11章〜第16章） |
|-------------------------------|------------------|
| 手順が最後まで動いて、保存される | 「席を押さえて、仮予約を作る」 |
| 途中で失敗したら、全部が取り消される | 「二重予約のチェックをすり抜けても、データベースが止めて、押さえた席も元に戻る」 |
| ドメインイベントが発行される | 「予約が作られたことを、ドメインイベントで知らせる」 |
| 外部サービスの呼び方 | 「支払い期限を過ぎていたら、決済サービスに頼まずに期限切れにする」 |

ルールの細かい組み合わせ（何人なら入れるか、何時なら返金するか）は、ドメインのテストに任せて、ユースケースでは **代表的な成功と失敗** を確かめます。

## 17.4　リポジトリの結合テスト

**初花**: リポジトリのテストは、`spec/infrastructure` だね。

**マリゴールド**: リポジトリのテストは、ドメインのオブジェクトとテーブルの **変換が往復できるか** を確かめる結合テストだよ。保存して読み込んだら、同じものが返ってくるか。データベースのエラーが、ドメインの言葉のエラーに変わるか。

| リポジトリのテストで確かめること | 例（第10章） |
|----------------------------|------------|
| 保存して読み込むと、同じものになる | 「保存した予約を、ドメインのオブジェクトとして読み込む」 |
| 値オブジェクトに戻る | `found.applicant.email` が `EmailAddress` |
| データベースのエラーを変換する | `RecordNotUnique` → `AlreadyReserved`、`RecordNotFound` → `Ticketing::NotFound` |

## 17.5　Railsのリクエストスペック

**初花**: リクエストスペックは44件で、2番目に多いね。全部要る？

**マリゴールド**: リクエストスペックは、第2章から **中身を入れ替えるときの安全網** になってくれた。第11章でユースケースに、第13章でフォームオブジェクトにしたときも、ほとんど落ちなかったよね。ただ、安全網だから、**利用者から見た振る舞い** だけを確かめるのがいい。

| リクエストスペックで確かめる | リクエストスペックで確かめない |
|-----------------------|-------------------------|
| どのURLに何を送ったら、どのステータスと画面・JSONが返るか | 返金のジョブが、決済サービスに何を渡したか |
| 届いたメールの件名 | ドメインイベントの中身 |
| 業務のルールの境界（第4章の R-04〜R-10） | リポジトリの変換 |

**初花**: 第4章の境界のテストは、リクエストスペックにあるよね。ドメインのテストと二重になってない？

**マリゴールド**: 確かに、第14章でドメインのテストにも同じ境界を書いた。リクエストスペックのほうは「画面から操作したときに、決めたルールどおりになるか」という **受け入れのテスト** として残しているんだ。ルールの ID（R-09 など）を書いているから、ドメインのテストとの対応も分かるよ。

## 17.6　外部サービスとの契約テスト

**初花**: 第15章の終わりで、偽物の決済の窓口と本物の窓口の振る舞いがずれるかもしれない、って言ってたよね。

**マリゴールド**: ずれると、テストは偽物で通るのに、本番の本物の窓口で壊れる。それを防ぐのが **契約テスト** だよ。窓口が守るべき約束を `shared_examples` に書いて、偽物と本物の両方に流す。

`spec/support/shared_examples/payment_gateway_contract.rb`:

```ruby
# 決済の窓口（アダプター）が守る約束。偽物と本物の両方に、同じ例を流す。
# 使う側で、gateway・valid_token・declined_token と、外の返事を用意する prepare_success を定義する。
RSpec.shared_examples "決済の窓口の約束" do
  it "支払いが通ったら、支払いIDの文字列を返す" do
    prepare_success

    charge_id = gateway.charge(amount: Money.new(3000), token: valid_token, idempotency_key: "contract-charge")

    expect(charge_id).to be_a(String).and(be_present)
  end

  it "カードが使えなければ、Billing::CardDeclined を投げる" do
    expect { gateway.charge(amount: Money.new(3000), token: declined_token, idempotency_key: "contract-declined") }
      .to raise_error(Billing::CardDeclined)
  end

  it "返金が通ったら、返金IDの文字列を返す" do
    prepare_success

    refund_id = gateway.refund(charge_id: "ch_contract", amount: Money.new(3000), idempotency_key: "contract-refund")

    expect(refund_id).to be_a(String).and(be_present)
  end

  it "金額は Money で受け取る（整数は受け取らない）" do
    prepare_success

    expect { gateway.charge(amount: 3000, token: valid_token, idempotency_key: "contract-integer") }
      .to raise_error(NoMethodError)
  end
end
```

`spec/support/` のファイルは、第2章で `rails_helper.rb` に足した行で読み込まれます。

`spec/infrastructure/billing/payment_gateway_contract_spec.rb`:

```ruby
require "rails_helper"

RSpec.describe "決済の窓口の契約" do
  describe Billing::FakePaymentGateway do
    let(:gateway) { described_class.new }
    let(:valid_token) { "tok_visa" }
    let(:declined_token) { "tok_declined" }

    def prepare_success; end

    include_examples "決済の窓口の約束"
  end

  describe Billing::UmepayGateway do
    let(:gateway) { described_class.new(api_key: "sk_test") }
    let(:valid_token) { "tok_umepay_ok" }
    let(:declined_token) { "tok_umepay_ng" }

    before do
      stub_request(:post, "https://api.umepay.example/v1/charges")
        .with(body: hash_including("source" => declined_token))
        .to_return(status: 402, body: { error: "card_declined" }.to_json)
    end

    def prepare_success
      stub_request(:post, "https://api.umepay.example/v1/charges")
        .with(body: hash_including("source" => valid_token)).to_return(status: 200, body: { id: "ch_umepay_1" }.to_json)
      stub_request(:post, "https://api.umepay.example/v1/refunds").to_return(status: 200, body: { id: "re_umepay_1" }.to_json)
    end

    include_examples "決済の窓口の約束"
  end
end
```

**初花**: 同じ4つの約束を、偽物と本物の両方が守ってる。偽物だけ整数の金額を受け付けちゃう、みたいなずれがあったら、ここで分かるんだ。

**マリゴールド**: そう。偽物は「本物と同じ約束を守る」ことを、テストで約束させておく。そうすれば、ほかのテストで偽物を安心して使えるよ。

⚠️ うめペイの側で冪等キーが本当に効くかどうかは、WebMock のスタブでは確かめられません（スタブは、こちらが決めた返事を返すだけです）。本物の決済サービスのテスト用の環境（サンドボックス）があるなら、そこに対して契約テストを時々流すと、外の仕様の変化にも気づけます。

## 17.7　テストダブルの使い分け

**初花**: `double`、`instance_double`、偽物の窓口、WebMock……。テストの中の「本物じゃないもの」がたくさん出てきたね。

**マリゴールド**: まとめて **テストダブル** と呼ぶよ。どれも「本物の代わりに置く」ものだけど、目的が違う。今のテストで使っている場所を数えてみよう。

| 種類 | 目的 | 書き方 | 使っている場所 |
|------|------|-------|-------------|
| ダミー・スタブ | 決まった答えを返す | `double("予約のリポジトリ", active_exists?: true)` | `spec/domain/ticketing/double_booking_check_spec.rb` |
| 検証つきのダブル | 本物にないメソッドを持たせない | `instance_double(Ticketing::InventoryRepository)` | `spec/requests/events_spec.rb` |
| スパイ | 呼ばれ方を、あとから確かめる | `allow(gateway).to receive(:refund)` → `have_received(:refund)` | `spec/jobs/billing/refund_payment_job_spec.rb`・`spec/usecases/ticketing/pay_for_reservation_spec.rb` |
| フェイク | 本物のように動く、軽い実装 | `Billing::FakePaymentGateway` | 決済を通るテストすべて |
| HTTPのスタブ | 外部サービスの返事を作る | `stub_request(...).to_return(...)` | `spec/infrastructure/billing/` |
| 本物を包む | 本物を動かしつつ、途中に処理を挟む | `and_wrap_original` | `spec/concurrency/`（待ち合わせ） |

**初花**: 使わないことにしたものもある？

**マリゴールド**: `allow_any_instance_of` は、第12章の一時的なスペックで使っただけで、残しているテストでは使っていないよ。「そのクラスのすべてのオブジェクト」を差し替えるので、どこで何が起きているかが見えにくくなるんだ。窓口を外から渡せる作り（第15章の `gateway:` の引数）にしておけば、使わずに済む。

| テストダブルを選ぶときの目安 | 理由 |
|------------------------|------|
| 自分たちのコード（リポジトリ・ドメイン）は、なるべく本物を使う | 偽物だと、データベースの制約やロックが再現できない（第10章） |
| 外部サービスは、必ず置き換える | テストが外の都合で落ちたり、本物の請求が起きたりしないように |
| 置き換えるなら、本物と同じ約束を守らせる | `instance_double`・契約テスト |
| 呼ばれ方を確かめるのは、それが仕事のテストだけ | 次の 17.8 |

## 17.8　実装詳細に依存しないテストを書く

**初花**: 第12章で、`have_enqueued_mail` のテストが、仕組みを変えたら落ちたよね。あれが「実装の詳しさに頼ったテスト」？

**マリゴールド**: そう。確かめたかったのは「申込者にメールが届くこと」なのに、「メールの送信ジョブが積まれること」を確かめていた。もう一つ、今のテストの中からも例を探してみよう。返金の冪等キーの書き方を、試しに `"refund-#{reservation_id}"` に変えて、全部のテストを流すよ（試したら元に戻します）。

```text
158 examples, 2 failures
```

```text
rspec ./spec/jobs/billing/refund_payment_job_spec.rb:44 # Billing::RefundPaymentJob やり直しのたびに、同じ冪等キーで頼む
rspec ./spec/requests/cancellations_spec.rb:25 # キャンセル PATCH /reservations/:id/cancel 返金は、支払った金額で決済サービスに依頼する
```

**初花**: 2つ落ちた。ジョブのテストが落ちるのは分かるけど、キャンセルのリクエストスペックも落ちてる。

**マリゴールド**: そのリクエストスペックは、第3章で書いて、第15章で書き直したこれだね。

```ruby
    it "返金は、支払った金額で決済サービスに依頼する" do
      gateway = Billing::FakePaymentGateway.new
      allow(Billing).to receive(:gateway).and_return(gateway)
      expect(gateway).to receive(:refund)
        .with(charge_id: reservation.payment.charge_id, amount: Money.new(6000),
              idempotency_key: "refund-reservation-#{reservation.id}")
        .and_call_original

      travel_to Time.zone.local(2026, 11, 10, 12, 0) do
        perform_enqueued_jobs { patch cancel_reservation_path(reservation) }
      end
    end
```

**初花**: キャンセルの画面のテストなのに、返金のジョブの中身（冪等キーの書き方）まで知ってるんだ。

**マリゴールド**: 第3章のときは、返金がコントローラの中にあったから、ここで確かめるしかなかった。でも今は、返金の頼み方を持っているのは `RefundPaymentJob` で、そのテストが同じことを確かめている。**1つのことは、それを持っている層で1回だけ確かめる** から、このリクエストスペックは消そう。キャンセルの画面としての振る舞い（返金済みになること・「6,000円を返金します」と出ること）は、「開催3日前より前なら、キャンセルして全額返金する」が確かめているよ。

`spec/requests/cancellations_spec.rb` から、「返金は、支払った金額で決済サービスに依頼する」の例を削除して、同じ実験をします。

```text
157 examples, 1 failure
```

```text
rspec ./spec/jobs/billing/refund_payment_job_spec.rb:44 # Billing::RefundPaymentJob やり直しのたびに、同じ冪等キーで頼む
```

**初花**: 今度は、冪等キーを持っているジョブのテストだけが落ちた。落ちてほしい場所だけが落ちるって、気持ちいいね。

| 実装の詳しさに頼ったテストの見分け方 | この本で見た例 | 直し方 |
|------------------------------|------------|-------|
| 中の仕組みを変えると落ちるが、利用者から見た振る舞いは変わらない | 第12章の `have_enqueued_mail` | 届いたメールの件名で確かめる |
| 否定のテストが、仕組みが変わっても通り続ける | 第12章の「お支払いのメールが積まれない」 | 結果（届いたメール）で確かめる |
| 保存の入れ物の振る舞いを、ルールとして確かめている | 第4章の R-10（`update(status:)`） | 業務の操作として確かめる（第14章） |
| 1つのことを、2つの層で確かめている | この節のリクエストスペック | 持っている層だけに残す |
| テストの準備が、昔の仕組みのまま | 第11章のファクトリで席を埋める準備 | 今の仕組みで準備する |

## ハンズオン 17-A — ドメインルールを保護する自動テスト一式

この章の成果物は「ドメインルールを保護する自動テスト一式」です。第1章で予告したとおり、`bin/ci` にテストを組み込みます。ドメインのテストを先に流して、ルールが壊れていたらすぐ分かるようにします。

`config/ci.rb`（抜粋）:

```ruby
  step "Security: Brakeman code analysis", "bin/brakeman --quiet --no-pager --exit-on-warn --exit-on-error"

  step "Tests: Domain", "bundle exec rspec spec/domain"
  step "Tests: All", "bundle exec rspec"
```

```bash
bin/ci
```

各段階の結果（抜粋）:

```text
✅ Setup passed in 2.45s
✅ Style: Ruby passed in 0.92s
✅ Security: Gem audit passed in 0.46s
✅ Security: Importmap vulnerability audit passed in 1.18s
✅ Security: Brakeman code analysis passed in 3.18s
46 examples, 0 failures
✅ Tests: Domain passed in 0.21s
158 examples, 0 failures
✅ Tests: All passed in 5.12s
✅ Continuous Integration passed in 13.51s
```

（この実行は、17.8 でリクエストスペックを1つ消す前のものです。）

GitHub Actions でも、プルリクエストのたびにテストを流します。`rails new` が作った `.github/workflows/ci.yml` には、テストのジョブがありません（`--skip-test` で作ったため）。最後に `test` のジョブを足します。PostgreSQL は、GitHub Actions の `services` で立ち上げます。

`.github/workflows/ci.yml`（抜粋）:

```yaml
  test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:18
        env:
          POSTGRES_USER: postgres
          POSTGRES_PASSWORD: postgres
        ports:
          - 5432:5432
        options: --health-cmd="pg_isready" --health-interval=10s --health-timeout=5s --health-retries=5

    env:
      RAILS_ENV: test
      DB_HOST: localhost

    steps:
      - name: Checkout code
        uses: actions/checkout@v6

      - name: Set up Ruby
        uses: ruby/setup-ruby@v1
        with:
          bundler-cache: true

      - name: Prepare database
        run: bin/rails db:test:prepare

      - name: Run domain tests
        run: bundle exec rspec spec/domain

      - name: Run all tests
        run: bundle exec rspec
```

## 層ごとのテスト

| 層 | フォルダ | 読み込むもの | 確かめること | 主なテストダブル |
|----|---------|-----------|------------|--------------|

| インフラ | `spec/infrastructure` | `rails_helper` | リポジトリの変換・外部サービスのアダプター・契約 | WebMock |
| モデル | `spec/models` | `rails_helper` | データベースの制約 | なし |
| ジョブ | `spec/jobs` | `rails_helper` | やり直し・捨てる・冪等 | 偽物の決済の窓口（見張り） |
| リクエスト | `spec/requests` | `rails_helper` | 利用者から見た振る舞い（画面・API・ステータス） | なるべく使わない |
| 並行処理 | `spec/concurrency` | `rails_helper`（トランザクションなし） | 同時の申込で整合性が崩れない | 待ち合わせ（`CyclicBarrier`） |

## 決めごと

1. ルールの細かい組み合わせは、ドメインのテストで確かめる（速い）
2. 部品のつながりは、本物のデータベースで確かめる（テスト用の偽物のリポジトリは作らない）
3. 外部サービスには、テストからつながない（WebMock）。偽物と本物の窓口は、契約テストで同じ約束を守らせる
4. 1つのことは、それを持っている層で1回だけ確かめる（冪等キーの書き方はジョブのテストだけ）
5. 否定のテスト（「〜しない」）は、仕組みが変わると何も確かめずに通ることがある。届いたメールの件名のように、結果で確かめる
6. 「今」は固定する（`spec/support/time_helpers.rb`）。ドメインには `now:` を渡す
7. 業務のルールのテストには、ルールの ID（R-01 など）を書く

## 振り返り

**初花**: テストを層で分けたら、「速いテストでルールを、遅いテストでつながりを」っていう役割分担が見えた。

**マリゴールド**: DDDで層を分けたことが、そのままテストの分け方になっているでしょう。ドメインがRailsを知らないから、ドメインのテストもRailsなしで書けた。設計とテストは、表と裏なんだ。

**初花**: 1つのテストを消して、テストが良くなったのも面白かった。増やすだけが正解じゃないんだね。

**マリゴールド**: 次の章では、テストではなく、コードのほうのよくない形を探して直すよ。DDDのパターンを使ったつもりで、かえって悪くしてしまう **アンチパターン** の章だ。

## 初花のメモ帳

- ルールの細かい組み合わせはドメインのテスト（速い）、部品のつながりは本物のデータベースのテストで確かめる
- 偽物の窓口には、本物と同じ約束を契約テストで守らせる。外部サービスにはテストからつながない
- 1つのことは、それを持っている層で1回だけ確かめる。仕組みが変わると落ちるテスト・否定のテストに気をつける

## マリゴールドの one more thing

**テストが壊れる理由を数えてみよう。**

テストが落ちたとき、その理由が「ルールが壊れた」なのか「中の書き方が変わった」なのかを、しばらく記録してみてください。後者が多いなら、テストが実装の詳しさに頼りすぎています。逆に、ルールを壊したのにどのテストも落ちなかったときは、守りたいルールのテストが抜けています。わざとコードを壊してテストが気づくかを調べる方法を **ミューテーションテスト** と呼び、Rubyでは `mutant` という gem が知られています。全部のコードに使うと時間がかかるので、コアドメインの `app/domain` だけに絞って試すのがおすすめです。
