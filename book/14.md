# 第14章　キャンセル・返金・状態遷移

**初花**: 第3章の課題一覧の1番、「キャンセル済みを支払いなしで確定に戻せる」。まだ直ってないよね。

**マリゴールド**: そう。それに、第4章から保留にしているテストが3つある。ちょうど72時間前の返金、画面とコントローラの食い違い、キャンセル済みを確定に戻せないこと。この章で全部片付けよう。

**初花**: キャンセルのコントローラも、まだ第3章の `3.days` のままだもんね。

**マリゴールド**: 予約の **状態の変わり方** をドメインに閉じ込めて、キャンセルと返金をユースケースにする。最後に、返金を決済のコンテキストに任せて、失敗したらやり直せるようにするよ。

## 14.1　予約の状態を定義する

**初花**: 状態は、仮予約・予約確定・キャンセル済み・期限切れの4つだよね。第4章で図にした。

**マリゴールド**: そう。今度は、**どの状態から、どの操作で、どの状態に行けるか** を、行けない組み合わせまで含めて表にしよう。

```text
             支払う（confirm）
  ┌────────┐ ─────────────────▶ ┌──────────┐
  │ 仮予約  │                    │ 予約確定  │
  └────────┘                    └──────────┘
    │     │                          │
    │     │ キャンセル（cancel）       │ キャンセル（cancel）
    │     ▼                          ▼
    │   ┌────────────────────────────────┐
    │   │ キャンセル済み                    │  ← ここからは、どこにも行けない
    │   └────────────────────────────────┘
    │ 支払い期限を過ぎた（expire）
    ▼
  ┌────────┐
  │ 期限切れ │  ← ここからも、どこにも行けない
  └────────┘
```

| 今の状態 ＼ 操作 | 支払う（`confirm`） | キャンセル（`cancel`） | 期限切れにする（`expire`） |
|---------------|------------------|-------------------|----------------------|
| 仮予約 | ✅ 予約確定へ（支払い期限まで） | ✅ キャンセル済みへ | ✅ 期限切れへ（支払い期限を過ぎていれば） |
| 予約確定 | ❌ | ✅ キャンセル済みへ | ❌ |
| キャンセル済み | ❌（R-10） | ❌（R-08） | ❌ |
| 期限切れ | ❌（R-10） | ❌（R-08） | ❌ |

**初花**: ❌ のほうが多いんだ。

**マリゴールド**: そうなんだ。状態の種類を決めるだけなら `enum` で済むけど、業務のルールの多くは **❌ のマス** にある。第3章では、この表のどのマスも守られていなかったんだ。

## 14.2　ステータスを自由に書き換えられない設計

**初花**: `Ticketing::Reservation` の `status` は、もう `attr_reader` だけだよね。外からは書き換えられない。

**マリゴールド**: 外からは書き換えられないけど、**変える方法もない** のが今の状態だよ。14.1 の表の ✅ のマスだけを、業務の名前のメソッドにしよう。第9章の `Inventory` と同じ考え方だね。支払い期限（15分）の決まりも、ここに1か所だけ置くよ。

```ruby
  def reservation(status)

      end
```

`app/domain/ticketing/reservation.rb`:

```ruby
module Ticketing
  # 予約。ID で見分けるエンティティ。状態は、決まった遷移のメソッドでしか変えられない
  class Reservation
    # 同じイベントに、同じメールアドレスの有効な予約がすでにある（R-03）
    class AlreadyReserved < BusinessRuleViolation
      def initialize
        super("このメールアドレスでは、すでに予約があります")
      end
    end

    # 今の状態からは、その操作ができない
    class InvalidTransition < BusinessRuleViolation
      def initialize(state_name, action)
        super("#{state_name}の予約は、#{action}できません")
      end
    end

    class PaymentDeadlinePassed < BusinessRuleViolation
      def initialize
        super("支払い期限を過ぎています")
      end
    end

    STATUS_NAMES = { pending: "仮予約", confirmed: "予約確定", canceled: "キャンセル済み", expired: "期限切れ" }.freeze
    PAYMENT_WINDOW = 15 * 60 # 支払い期限は、仮予約の作成から15分後（秒）

    attr_reader :id, :event_id, :applicant, :count, :price, :status, :reserved_at

    def self.payment_deadline_for(reserved_at)
      reserved_at + PAYMENT_WINDOW
    end

    # 申込から、新しい予約を作る。有料なら仮予約（R-05）、無料なら予約確定（R-06）
    def self.apply(event_id:, applicant:, count:, price:, reserved_at:)
      new(event_id: event_id, applicant: applicant, count: count, price: price, reserved_at: reserved_at,
          status: price.zero? ? :confirmed : :pending)
    end

    def initialize(event_id:, applicant:, count:, price:, reserved_at: nil, id: nil, status: :pending)
      @id = id
      @event_id = event_id
      @applicant = applicant
      @count = count
      @price = price
      @reserved_at = reserved_at
      @status = status
    end

    def total_price
      price * count.to_i
    end

    def payment_deadline
      self.class.payment_deadline_for(reserved_at)
    end

    def status_name
      STATUS_NAMES.fetch(status)
    end

    # 支払いが済んだ（R-05・R-10）
    def confirm(now:)
      raise InvalidTransition.new(status_name, "確定") unless status == :pending
      raise PaymentDeadlinePassed if now > payment_deadline

      @status = :confirmed
    end

    # 申込者が取りやめた（R-08）
    def cancel
      raise InvalidTransition.new(status_name, "キャンセル") unless %i[pending confirmed].include?(status)

      @status = :canceled
    end

    # 支払い期限を過ぎた（R-07）
    def expire(now:)
      raise InvalidTransition.new(status_name, "期限切れに") unless status == :pending
      raise InvalidTransition.new("支払い期限の前", "期限切れに") if now <= payment_deadline

      @status = :expired
    end

    def ==(other)
      return equal?(other) if id.nil?

      other.is_a?(Reservation) && other.id == id
    end
    alias eql? ==

    def hash
      id.nil? ? super : [ Reservation, id ].hash
    end
  end
end
```

## 14.3　状態遷移のルールを実装する

**初花**: エンティティに遷移ができたら、それを使うユースケースだね。

```ruby
module Ticketing
  # 支払いが済んだ仮予約を、予約確定にする
  class ConfirmReservation
    def initialize(reservations: ReservationRepository.new)
      @reservations = reservations
    end

    def call(reservation_id:, now: Time.current)
      ApplicationRecord.transaction do
        reservation = @reservations.find(reservation_id)
        reservation.confirm(now: now)
        @reservations.save(reservation)
        DomainEvents.publish(ReservationConfirmed.new(reservation_id: reservation.id, event_id: reservation.event_id,
                                                      occurred_at: now))
        reservation
      end
    end
  end
end
```

```ruby
module Ticketing
  # 支払い期限を過ぎた仮予約を、期限切れにして席を戻す
  class ExpireReservation
    def initialize(reservations: ReservationRepository.new, inventories: InventoryRepository.new)
      @reservations = reservations
      @inventories = inventories
    end

    def call(reservation_id:, now: Time.current)
      ApplicationRecord.transaction do
        reservation = @reservations.find(reservation_id)
        reservation.expire(now: now)
        @reservations.save(reservation)
        release_seats(reservation)
        reservation
      end
    end

    private

    def release_seats(reservation)
      inventory = @inventories.find(reservation.event_id)
      inventory.release(reservation.count)
      @inventories.save(inventory)
    end
  end
end
```

期限切れのジョブは、1件ずつ `ExpireReservation` に任せます。支払い期限の計算も、エンティティの `PAYMENT_WINDOW` を使います。

`app/jobs/expire_pending_reservations_job.rb`:

```ruby
class ExpirePendingReservationsJob < ApplicationJob
  queue_as :default

  # 支払い期限を過ぎた仮予約を、1件ずつ期限切れにする
  def perform(now: Time.current)
    deadline_passed = now - Ticketing::Reservation::PAYMENT_WINDOW
    Reservation.pending.where(created_at: ...deadline_passed).find_each do |record|
      Ticketing::ExpireReservation.new.call(reservation_id: record.id, now: now)
    end
  end
end
```

支払いのコントローラも、期限切れと確定をユースケースに任せます。

```ruby
class PaymentsController < ApplicationController
  def create
    reservation = Ticketing::ReservationRepository.new.find(params[:reservation_id])
    now = Time.current

    if reservation.status == :pending && now > reservation.payment_deadline
      Ticketing::ExpireReservation.new.call(reservation_id: reservation.id, now: now)
      redirect_to reservation_path(reservation.id), alert: "お支払いの期限を過ぎたため、予約は取り消されました。"
      return
    end

    unless reservation.status == :pending
      redirect_to reservation_path(reservation.id), alert: "この予約はお支払いできません。"
      return
    end

    amount = reservation.total_price
    charge_id = Billing::PaymentGateway.charge(amount: amount.yen, token: params[:token])
    ApplicationRecord.transaction do
      Payment.create!(reservation_id: reservation.id, amount: amount.yen, charge_id: charge_id)
      Ticketing::ConfirmReservation.new.call(reservation_id: reservation.id, now: now)
    end

    redirect_to reservation_path(reservation.id), notice: "お支払いが完了し、予約が確定しました。"
  rescue Billing::PaymentGateway::CardDeclined => e
    redirect_to reservation_path(params[:reservation_id]), alert: e.message
  end
end
```

**初花**: 決済サービスの `charge` は、トランザクションの外にあるんだね。

**マリゴールド**: 第11章の決まりどおり、外のサービスは巻き戻せないからね。支払いの流れには、まだ「お金は受け取ったのに確定に失敗したら」という穴が残っている。それは決済のアダプターを作る第15章で扱おう。

## 14.4　キャンセル期限を値オブジェクトで表現する

**初花**: いよいよ「ちょうど72時間前」だね。

**マリゴールド**: 返金期限を値オブジェクトにして、キャンセルのユースケースと予約の画面の **両方が同じものを使う** ようにしよう。第3章の食い違いは、同じルールを2か所に別々に書いたことが原因だったからね。

`app/domain/ticketing/cancellation_deadline.rb`:

```ruby
module Ticketing
  # 返金期限。開始時刻の72時間前まで（ちょうどを含む）にキャンセルすれば、全額返金する（R-09）
  class CancellationDeadline < Data.define(:starts_at)
    HOURS_BEFORE_START = 72

    def refund_until
      starts_at - (HOURS_BEFORE_START * 60 * 60)
    end

    def refundable_at?(time)
      time <= refund_until
    end
  end
end
```

`spec/domain/ticketing/cancellation_deadline_spec.rb`:

`app/usecases/ticketing/cancel_reservation.rb`:

```ruby
module Ticketing
  # 申込者のキャンセル。予約をキャンセル済みにして、席を戻し、返金するかを決める
  class CancelReservation
    # refund_amount は返金する金額。返金しないときは nil
    Result = Data.define(:reservation, :refund_amount)

    def initialize(reservations: ReservationRepository.new, inventories: InventoryRepository.new,
                   sales_infos: SalesInfoReader.new)
      @reservations = reservations
      @inventories = inventories
      @sales_infos = sales_infos
    end

    def call(reservation_id:, now: Time.current)
      ApplicationRecord.transaction do
        reservation = @reservations.find(reservation_id)
        refund_amount = refund_amount_for(reservation, now)

        reservation.cancel
        @reservations.save(reservation)
        release_seats(reservation)
        Result.new(reservation: reservation, refund_amount: refund_amount)
      end
    end

    private

    # 予約確定で、支払い金額があり、返金期限までなら全額を返金する（R-09）
    def refund_amount_for(reservation, now)
      return nil unless reservation.status == :confirmed && !reservation.total_price.zero?

      deadline = @sales_infos.find(reservation.event_id).cancellation_deadline
      reservation.total_price if deadline.refundable_at?(now)
    end

    def release_seats(reservation)
      inventory = @inventories.find(reservation.event_id)
      inventory.release(reservation.count)
      @inventories.save(inventory)
    end
  end
end
```

## 14.5　決済状態と予約状態を分離する

**初花**: キャンセルのコントローラが、まだ決済サービスを直接呼んで、`payment.update!` で返金済みにしてるね。

**マリゴールド**: そう。でも、予約の「キャンセル済み」と、決済の「返金済み」は、**別々に変わる状態** なんだ。キャンセルは一瞬で終わるけど、返金は決済サービスとのやり取りで、失敗することもある。

| | 予約の状態（`Ticketing::Reservation`） | 決済の状態（`Payment`） |
|---|----------------------------------|---------------------|
| 持つコンテキスト | 予約 | 決済 |
| 状態 | 仮予約・予約確定・キャンセル済み・期限切れ | 支払い済み・返金済み・返金に失敗 |
| 変わるきっかけ | 申込者の操作・支払い期限 | 決済サービスの結果 |
| 失敗 | 業務のルールに反したとき | 決済サービスにつながらないとき |

**初花**: キャンセル済みなのに、返金はまだ、っていう時間があるんだ。

**マリゴールド**: そう。その時間を正直に表すために、2つの状態を分けよう。予約のコンテキストは「キャンセルされた、返金するのはこの金額」という **ドメインイベント** を発行するだけにして、決済のコンテキストがそれを受け取って返金する。第12章のメールと同じ形だよ。

## 14.6　返金処理を外部決済サービスと連携する

**初花**: 決済のコンテキストの側は、何を作ればいいの？

```ruby
module Billing
  # 予約のキャンセルを受けて、決済サービスに返金を頼む。
  # 決済サービスにつながらなければ、少しずつ間をあけてやり直す。
  class RefundPaymentJob < ApplicationJob
    queue_as :default

    retry_on PaymentGateway::Unavailable, wait: :polynomially_longer, attempts: 5 do |job, _error|
      Payment.find_by!(reservation_id: job.arguments.first).update!(status: :refund_failed)
    end

    def perform(reservation_id, amount_yen)
      payment = Payment.find_by!(reservation_id: reservation_id)
      return if payment.refunded? # すでに返金済みなら、もう一度は頼まない

      refund_id = PaymentGateway.refund(charge_id: payment.charge_id, amount: amount_yen)
      payment.update!(status: :refunded, refund_id: refund_id)
    end
  end
end
```

## 14.7　二重キャンセル・二重返金への対策

**初花**: キャンセルのボタンを2回押したら？ 返金も2回されちゃう？

**マリゴールド**: 2つの段で守っているよ。まず、キャンセルそのものは、2回目がエンティティの遷移で止まる。14.3 のユースケースのテストの「2回キャンセルしても、席は2回戻らない」がそれだね。2回目は `InvalidTransition` になって、イベントも発行されないから、返金のジョブも積まれない。

**初花**: じゃあ、返金のジョブが2回動くことはない？

**マリゴールド**: ジョブは、ジョブの仕組みの都合で2回動くことがあるんだ。たとえば、返金は済んだのに、ジョブが「終わった」と記録する前にサーバーが落ちると、もう一度動く。だから、ジョブの側でも「すでに返金済みなら、もう頼まない」と確かめている。

| 二重になる場面 | 止める場所 | 確かめるテスト |
|------------|----------|------------|
| キャンセルのボタンを2回押した | エンティティの遷移（キャンセル済みはキャンセルできない） | 「2回キャンセルしても、席は2回戻らない」 |
| 返金のジョブが2回動いた | ジョブ（返金済みなら何もしない） | 「同じ返金のジョブが2回動いても…」 |
| 2回目の返金の依頼が、決済サービスに届いてしまった | 決済サービスの冪等キー | 第15章 |

## 14.8　失敗や再試行を考慮する

**初花**: さっきのテストの後ろの2つが、やり直しのテストだね。

**マリゴールド**: そう。`retry_on` は、決まったエラーが起きたら、少しずつ間をあけてジョブを積み直す Active Job の仕組みだよ。テストの `perform_enqueued_jobs` は、やり直しで積まれたジョブも動かしてくれる。

| `RefundPaymentJob` の書き方 | 意味 |
|--------------------------|------|
| `retry_on PaymentGateway::Unavailable` | 決済サービスにつながらないときだけ、やり直す |
| `wait: :polynomially_longer` | やり直すたびに、待つ時間を長くする |
| `attempts: 5` | 最初の1回を含めて、5回まで |
| ブロック（`do |job, _error| ... end`） | 5回とも失敗したら、決済を「返金に失敗」にする |

**初花**: カードが使えない（`CardDeclined`）ときは、やり直さないの？

**マリゴールド**: カードが使えないのは、何度やっても同じ結果になる失敗だからね。**やり直して直る失敗** と **やり直しても直らない失敗** を分けるのが大事なんだ。

| 失敗 | やり直す？ | 理由 |
|------|----------|------|
| 決済サービスにつながらない（`Unavailable`） | ✅ やり直す | 少し待てば直ることが多い |
| カードが使えない（`CardDeclined`） | ❌ やり直さない | 何度やっても同じ |
| 予約や決済の記録が見つからない | ❌ やり直さない | プログラムの誤り。調べる必要がある |
| 5回やり直しても失敗した | 人が調べる | 「返金に失敗」として残し、第20章の監視で気づけるようにする |

## 初花のメモ帳

- 状態遷移は表にする。ルールの多くは「できない」マスにある。できる操作だけを業務の名前のメソッドにする
- 同じ期限のルールは、値オブジェクトに1つだけ置いて、判断と画面の両方から使う
- 予約の状態と決済の状態は別に変わる。やり直して直る失敗だけをやり直し、最後は人が気づける形で残す

## マリゴールドの one more thing

**状態遷移の gem を使う方法もある。**

Rubyには、`aasm` のような状態遷移を宣言的に書ける gem があります。`event :cancel do transitions from: [:pending, :confirmed], to: :canceled end` のように書くと、遷移の表をそのままコードにでき、遷移の前後に処理を挟むこともできます。本書では、エンティティのメソッドと `raise` で書きました。遷移が数えるほどなら、gem を使わずに書くほうが、ドメイン層を Ruby だけに保てて読みやすいからです。状態が10を超えたり、主催者ごとに遷移が変わったりするようになったら、gem や、遷移の表をデータとして持つ方法を検討するとよいでしょう。
