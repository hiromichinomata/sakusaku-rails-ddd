# 第3章　Fat Modelと複雑化するビジネスロジック

**初花**: 第2章のやり方で、予約サービスは全部作れそうな気がしてきた。ルールが増えても、バリデーションを足していけばいいんだよね。

**マリゴールド**: 本当にそうか、この章で試してみよう。第1章で並べたルールを、Railsでよく見る書き方のまま一つずつ足していくよ。

**初花**: わざと下手に書くの？

**マリゴールド**: わざとではないよ。どれも、入門書や実務でよく見る素直な書き方。それでも、ルールが5つ、6つと重なると、どこで苦しくなるかが見えてくる。章の最後に、その苦しさを一覧にするのが目標だよ。

この章で足すルールです。

| ルール | 中身 |
|--------|------|
| 1回の予約人数 | 1〜4人まで |
| 二重予約の禁止 | 同じイベントに、同じメールアドレスの有効な予約は1件まで |
| 受付期間 | イベントの開始時刻まで |
| 支払い | 仮予約から15分以内に支払うと予約が確定する。無料のイベントはその場で確定 |
| 期限切れ | 15分以内に支払わなかった仮予約は、期限切れにして席を戻す |
| キャンセル・返金 | 開催3日前まではキャンセルすると全額返金。それ以降はキャンセルできるが返金しない |

## 3.2　巨大化するActive Recordモデル

**初花**: 次は二重予約の禁止。同じメールアドレスで同じイベントは1件だけ、って `uniqueness` で書けるよね。

**マリゴールド**: 書けるよ。ただ「キャンセルした人は、もう一度予約できる」としたいから、**有効な予約** の中だけで重複を調べる必要がある。そのために、予約に状態を持たせよう。

| 状態 | 値 | 意味 | 席を使うか |
|------|----|------|----------|
| お支払い待ち | `pending` | 仮予約。15分以内の支払いを待っている | 使う |
| 予約確定 | `confirmed` | 支払いが済んだ（または無料） | 使う |
| キャンセル済み | `canceled` | 参加者がキャンセルした | 使わない |
| 期限切れ | `expired` | 15分以内に支払われなかった | 使わない |

```ruby
class Reservation < ApplicationRecord
  MAX_QUANTITY = 4

  belongs_to :event

  enum :status, {
    pending: "pending",
    confirmed: "confirmed",
    canceled: "canceled",
    expired: "expired"
  }, default: :pending

  scope :active, -> { where(status: %w[pending confirmed]) }

  validates :name, presence: true
  validates :email, presence: true, format: { with: URI::MailTo::EMAIL_REGEXP }
  validates :email, uniqueness: { scope: :event_id, conditions: -> { active }, message: :already_reserved },
                    on: :create
  validates :quantity, numericality: { only_integer: true, greater_than: 0, less_than_or_equal_to: MAX_QUANTITY }
  validate :quantity_within_remaining_seats
  validate :event_accepting_reservations, on: :create

  def total_price
    event.price * quantity
  end

  private

  def quantity_within_remaining_seats
    return if event.nil? || quantity.nil?

    remaining = event.capacity - event.reservations.where.not(id: id).sum(:quantity)
    if quantity > remaining
      errors.add(:quantity, :exceeds_remaining_seats, count: remaining)
    end
  end

  def event_accepting_reservations
    return if event.nil?

    errors.add(:base, :reservation_closed) if event.starts_at <= Time.current
  end
end
```

メッセージは `ja.yml` の `reservation:` の `attributes:` に足します。`base` は「特定の項目ではなく、予約全体」のエラーです。

| 書き方 | 意味 |
|-------|------|
| `enum :status, {...}` | `pending?`・`confirmed!`・`Reservation.pending` などのメソッドができる |
| `scope :active, -> { ... }` | `Reservation.active` で「有効な予約」だけを取り出せる |
| `uniqueness: { scope: :event_id, conditions: -> { active } }` | 同じイベントの有効な予約の中で、メールアドレスが重ならない |
| `on: :create` | 新しく作るときだけチェックする（予約後にイベントが始まっても、キャンセルの更新は通す） |

## 3.3　コールバックに業務処理を記述する問題

**初花**: 支払いだね。決済サービスって、本物を使うの？

**マリゴールド**: 本書では、架空の決済サービス「うめペイ」に支払う想定にして、その窓口を手元で真似するクラスを作るよ。テスト用のカードとして、成功する `tok_visa` と、使えない `tok_declined` の2つを用意する。

`app/services/payment_gateway.rb`:

```ruby
# 本書用の架空の決済サービス「うめペイ」の代わりに、手元で動く決済の窓口。
# トークン tok_visa は成功、tok_declined はカードが使えなかったものとして扱う。
class PaymentGateway
  class CardDeclined < StandardError; end

  def self.charge(amount:, token:)
    raise CardDeclined, "カードが利用できませんでした" if token == "tok_declined"

    Rails.logger.info("[PaymentGateway] charge amount=#{amount}")
    "ch_#{SecureRandom.hex(8)}"
  end

  def self.refund(charge_id:, amount:)
    Rails.logger.info("[PaymentGateway] refund charge_id=#{charge_id} amount=#{amount}")
    "re_#{SecureRandom.hex(8)}"
  end
end
```

`charge` は「支払いID」（`ch_` で始まる文字列）を、`refund` は「返金ID」（`re_`）を返します。本物の決済サービスでも、あとで返金や問い合わせに使うためにこうしたIDを保存しておきます。

仮予約したら「お支払いのお願い」、確定したら「予約確定」のメールを送ります。

class ReservationMailer < ApplicationMailer
  def payment_request
    @reservation = params[:reservation]
    mail to: @reservation.email, subject: "【うめチケット】お支払いのお願い：#{@reservation.event.title}"
  end

  def confirmed
    @reservation = params[:reservation]

  end
end

**初花**: メールはいつ送ればいい？ 予約を保存したら、自動で送られてほしいな。

**マリゴールド**: Railsでよく使われるのは **コールバック** だね。「保存したあと」「状態が変わったあと」に、モデルが自分でメールを送るように書ける。無料のイベントをその場で確定させるのも、保存の直前のコールバックで書けるよ。

`app/models/reservation.rb`（抜粋）:

```ruby
  belongs_to :event
  has_one :payment, dependent: :destroy
...
  validate :event_accepting_reservations, on: :create

  before_create :confirm_if_free
  after_create_commit :send_payment_request_mail, if: :pending?
  after_update_commit :send_confirmed_mail, if: -> { saved_change_to_status?(to: "confirmed") }
...
  def confirm_if_free
    self.status = :confirmed if event.price.zero?
  end

  def send_payment_request_mail
    ReservationMailer.with(reservation: self).payment_request.deliver_later
  end

  def send_confirmed_mail
    ReservationMailer.with(reservation: self).confirmed.deliver_later
  end
end
```

| コールバック | 動くとき | ここでの仕事 |
|------------|---------|------------|
| `before_create` | `INSERT` の直前 | 無料なら状態を「確定」にする |
| `after_create_commit` | `INSERT` がコミットされた後 | お支払いのお願いのメール |
| `after_update_commit` | `UPDATE` がコミットされた後 | 状態が「確定」に変わったら確定メール |

`deliver_later` は、メールをその場で送らず、ジョブとして後で送るように積みます。

`app/controllers/payments_controller.rb`:

```ruby
class PaymentsController < ApplicationController
  def create
    @reservation = Reservation.find(params[:reservation_id])

    unless @reservation.pending?
      redirect_to @reservation, alert: "この予約はお支払いできません。"
      return
    end

    if @reservation.created_at < 15.minutes.ago
      @reservation.update!(status: :expired)
      redirect_to @reservation, alert: "お支払いの期限を過ぎたため、予約は取り消されました。"
      return
    end

    amount = @reservation.total_price
    charge_id = PaymentGateway.charge(amount: amount, token: params[:token])
    @reservation.create_payment!(amount: amount, charge_id: charge_id)
    @reservation.update!(status: :confirmed)

    redirect_to @reservation, notice: "お支払いが完了し、予約が確定しました。"
  rescue PaymentGateway::CardDeclined => e
    redirect_to @reservation, alert: e.message
  end
end
```

  queue_as :default

### 返金のルールだけを確かめたいのに

**初花**: 「開催3日前までは返金」のルールだけを確かめたい。小さいテストで済ませられない？

**マリゴールド**: 今のコードだと難しいんだ。返金するかどうかの判断が `ReservationsController#cancel` の中にあるから、HTTPリクエストを送るしかない。キャンセルのスペックを書くのに、何を準備したか数えてみよう。

| 返金のルールを確かめるのに要ったもの | 理由 |
|-----------------------------------|------|
| データベース | `Event`・`Reservation`・`Payment` を保存する |
| イベント・予約・支払いのデータ | `payment.present?` が条件にある |

## 初花のメモ帳

- ルールを足すと、そのルールに触れる場所すべてに影響が広がる。テストの準備データまで縛られる
- 一つのルール（期限・有効な予約・定員）が複数の場所に書かれると、直し忘れと比べ方のずれが起きる
- バリデーションは「保存する瞬間の値」しか見ない。状態の変わり方・モデルをまたぐ決まり・時間・同時実行は苦手

## マリゴールドの one more thing

**`pending` は「直すと約束したテスト」として残しておこう。**

RSpecの `pending` は、テストを飛ばす `skip` と違って、中身を毎回実行します。失敗している間は「保留」として報告され、スイートは成功のままです。そして、コードを直して **テストが通るようになると、逆に失敗として知らせて** くれます（`Expected pending '...' to fail. No error was raised.`）。第14章でキャンセル期限を直したとき、このテストが「もう `pending` を外していいよ」と教えてくれるはずです。課題一覧の13番目までを消し終えたとき、`pending` が1つも残っていない状態を目指しましょう。
