# 第10章　リポジトリと永続化

**初花**: 残席の集約はできたけど、`Inventory` はまだ Ruby のオブジェクトのままだよね。データベースに入ってない。

**マリゴールド**: そう。POROには `save` がないからね。この章では、集約をデータベースから読み込んで、変えたら保存する **リポジトリ** を作る。

**初花**: Active Record の `find` と `save` を、別のクラスに包むだけ？

**マリゴールド**: 包むだけに見えるけど、間で **ドメインの言葉とテーブルの形を変換する** のが大事な仕事なんだ。変換を書いてみると、テーブルに足りないものが見えてくるよ。

---

## 10.1　Repositoryパターンの役割

**初花**: リポジトリって、どういうものなの？

**マリゴールド**: リポジトリは、集約の **置き場所** だと思って。ユースケースからは「この予約を置いておいて」「IDが1の予約を出して」と頼むだけで、その置き場所がデータベースなのか、どのテーブルなのかは気にしない。

```text
ユースケース                リポジトリ                      Active Record / データベース
─────────                 ─────────                      ──────────────────────────
find(event_id)  ───────▶  TicketInventory を読む  ──────▶ SELECT ... FROM ticket_inventories
                ◀───────  Inventory（PORO）に変換  ◀──────  行
save(inventory) ───────▶  列の値に変換して書く   ──────▶ UPDATE ticket_inventories ...
```

| | リポジトリが受け持つ | リポジトリが受け持たない |
|---|------------------|--------------------|
| 仕事 | 集約を読み込む・保存する・ドメインの形とテーブルの形を変換する | 業務のルールの判断（残席を超えていないか） |
| 受け取る・返すもの | ドメインのオブジェクト（`Inventory`・`Ticketing::Reservation`） | Active Record のオブジェクト |
| 単位 | 集約ルートごとに1つ | テーブルごとに1つ、ではない |

**初花**: 「テーブルごとに1つではない」って？

**マリゴールド**: 集約が2つのテーブルにまたがっていても、リポジトリは1つ。逆に、集約ではない `payments` のようなテーブルには、リポジトリを作らない。**集約の単位で作る** んだ。うめチケットでは、残席と予約の2つだよ。

## 10.2　ドメインモデルとデータベースを分離する意義

**初花**: 変換って、どんなものがあるの？

**マリゴールド**: 予約のエンティティと `reservations` テーブルを並べてみよう。

| `Ticketing::Reservation` | 型 | `reservations` の列 | 型 |
|-------------------------|----|-------------------|----|
| `id` | 整数 | `id` | `bigint` |
| `event_id` | 整数 | `event_id` | `bigint` |
| `applicant.name` | 文字列 | `name` | `string` |
| `applicant.email` | `EmailAddress` | `email` | `string` |
| `count` | `ReservationCount` | `quantity` | `integer` |
| `price` | `Money` | ？ | — |
| `status` | シンボル（`:pending`） | `status` | `string` |

**初花**: `price` の列がない！ 料金は `events.price` から取ってたんだ。

**マリゴールド**: そう。第3章では `event.price * quantity` で計算していたし、第8章でも `Money.new(event.price)` だった。予約に料金を持たせようとして、初めて **テーブルに料金がない** ことに気づいたね。これで困ることはないかな？

**初花**: 試してみる。予約したあとに、主催者がイベントの料金を変えたら……。

```text
ume-tickets(dev):001> event = Event.find_by!(title: "梅酒づくりワークショップ")
ume-tickets(dev):002> reservation = Reservation.create!(event: event, name: "初花", email: "hatsuka@example.com", quantity: 2)
ume-tickets(dev):003> reservation.total_price
=> #<Money 3,000円>
ume-tickets(dev):004> event.update!(price: 2000)
=> true
ume-tickets(dev):005> reservation.reload.total_price
=> #<Money 4,000円>
```

**初花**: 3,000円の仮予約が、何もしてないのに4,000円になった！ お支払いのお願いのメールには3,000円って書いてあるのに。

**マリゴールド**: 主催者の初花なら、どうしたい？

**初花**: 申し込んだときの料金のままがいい。後から値上げされたら、申込者が困る。

**マリゴールド**: それは新しいルールだね。業務ルールの一覧に足そう。

`docs/domain/rules.md`（抜粋）:

```markdown
| R-12 | 予約の料金は、申し込んだときのイベントの料金で決まる。あとでイベントの料金が変わっても、予約の支払い金額は変わらない |
```

**初花**: ドメインモデルとテーブルを並べただけで、ルールの抜けが見つかるんだね。

**マリゴールド**: Active Record だと、モデルの属性がそのままテーブルの列だから、「本当は何を持つべきか」を考える機会が少ないんだ。ドメインモデルを先に決めて、テーブルと突き合わせると、こういう **ずれ** が見えてくる。予約に料金の列を足そう。

**マリゴールド**: いきなり `null: false` で足すと、今ある予約の行が空になって失敗するからね。今のアプリの画面からの予約は、まだ Active Record の `Reservation` で作っているので、作るときにイベントの料金を写すようにしておこう。

**マリゴールド**: バリデーションを飛ばすと、その前後のコールバックも飛ぶからね。コールバックの順番に頼る書き方は、こういうところで足をすくわれる。保存の直前に写すように、`before_create` に並べよう。

```ruby
  def total_price
    Money.new(price) * quantity
  end
```

```ruby
  def copy_price_from_event

  end

  def confirm_if_free
    self.status = :confirmed if price.zero?
  end
```

## 10.3　Active Recordを直接利用する実装との比較

**初花**: リポジトリを使うと、コードはどう変わるの？

**マリゴールド**: 同じ「予約を保存する」を、2つの書き方で並べてみよう。

```ruby
# Active Record を直接使う（第2章〜第3章）
reservation = event.reservations.build(name: "初花", email: "hatsuka@example.com", quantity: 2)
reservation.save

# リポジトリを使う（この章から）
reservation = Ticketing::Reservation.new(
  event_id: event.id,
  applicant: Ticketing::Applicant.new(name: "初花", email: "hatsuka@example.com"),
  count: Ticketing::ReservationCount.new(2),
  price: Money.new(1500)
)
saved = Ticketing::ReservationRepository.new.add(reservation)
```

| | Active Record を直接使う | リポジトリを使う |
|---|----------------------|-------------|
| 書く量 | 少ない | 多い（値オブジェクトを作る、変換を書く） |
| 正しくない値 | `save` まで分からない（`errors`） | `ReservationCount.new(5)` の時点で作れない |
| 保存の仕方 | モデルが知っている（コールバック・バリデーション） | リポジトリが知っている。ドメインのオブジェクトは知らない |
| テスト | データベースが要る | ドメインのテストはデータベースなし、リポジトリのテストだけデータベースあり |
| 向いている場所 | イベント管理のような CRUD | 予約のようなコアドメイン |

**初花**: 書く量は増えるね。

**マリゴールド**: 増えるよ。だから第7章で、リポジトリはコアドメインの集約にだけ作ると決めたんだ。イベントの登録は、今までどおり `Event.new(...).save` のままにするよ。

## 10.4　`find`・`save`・検索条件の設計

**初花**: リポジトリには、どんなメソッドを作ればいい？ Active Record みたいに `where` とか `order` も？

**マリゴールド**: 作らないよ。リポジトリのメソッドは、**ユースケースが本当に必要とするもの** だけにする。`where` を何でも受け付けると、テーブルの形がリポジトリの外に漏れてしまうからね。

| メソッド | 残席 | 予約 | 使うユースケース |
|---------|-----|-----|---------------|
| `find(id)` | イベントのIDで探す | 予約のIDで探す | 支払う・キャンセルする |
| `add(集約)` | 新しい残席を保存 | 新しい予約を保存して、IDの付いた予約を返す | イベントを登録する・申し込む |
| `save(集約)` | 変えた残席を保存 | 変えた予約を保存 | 申し込む・支払う・キャンセルする |
| `active_exists?(event_id:, email:)` | — | 同じイベント・同じメールアドレスの有効な予約があるか | 申し込む（二重予約のチェック） |

**初花**: 主催者向けに「申込の一覧」を出したくなったら？ リポジトリに `all_for_event` を足す？

**マリゴールド**: 一覧や検索のような **読むだけの画面** は、リポジトリを通さずに Active Record で直接読んでいいことにしよう。集約に組み立てる必要がないし、画面に合わせた形で読むほうが速いからね。

| 用途 | 使うもの | 理由 |
|------|---------|------|
| 集約を変える（申し込む・キャンセルする） | リポジトリ | ルールを通して変える。変換が要る |
| 画面に一覧を出す（主催者の申込一覧） | Active Record（`::Reservation.where(...)`） | 読むだけ。画面に合わせた形で読める |

## 10.5　リポジトリのインターフェースを定義する

**初花**: Javaの本だと、リポジトリはインターフェースを作って、実装を別に書くよね。Rubyでもそうする？

**マリゴールド**: 第7章で決めたとおり、実装が1つしかないうちは、インターフェース用の抽象クラスは作らないよ。Rubyは、同じ名前のメソッドを持っていれば差し替えられる（ダックタイピング）からね。その代わり、**何を受け取って、何を返し、何を投げるか** を決めておこう。

| メソッド | 受け取る | 返す | 投げる |
|---------|---------|-----|-------|
| `InventoryRepository#find(event_id)` | イベントのID | `Ticketing::Inventory` | `Ticketing::NotFound` |
| `InventoryRepository#add(inventory)` | `Ticketing::Inventory` | — | — |
| `InventoryRepository#save(inventory)` | `Ticketing::Inventory` | — | — |
| `ReservationRepository#find(id)` | 予約のID | `Ticketing::Reservation` | `Ticketing::NotFound` |
| `ReservationRepository#add(reservation)` | IDのない `Ticketing::Reservation` | IDの付いた `Ticketing::Reservation` | `Ticketing::Reservation::AlreadyReserved` |
| `ReservationRepository#save(reservation)` | IDのある `Ticketing::Reservation` | — | — |
| `ReservationRepository#active_exists?` | イベントのID・`EmailAddress` | `true` / `false` | — |

**初花**: 投げるエラーも、`ActiveRecord::RecordNotFound` じゃなくて `Ticketing::NotFound` なんだ。

**マリゴールド**: ユースケースから見ると、置き場所がデータベースかどうかは関係ないからね。Active Record のエラーをリポジトリの中で受け止めて、ドメインの言葉のエラーに変えてから外に出す。そうすれば、ユースケースは Active Record を知らなくて済む。

`app/domain/ticketing/not_found.rb`:

```ruby
module Ticketing
  # 探している集約が見つからないときのエラー
  class NotFound < StandardError; end
end
```

二重予約のエラーは、予約のエンティティの中に置きます。

`app/domain/ticketing/reservation.rb`（抜粋）:

```ruby
  class Reservation
    # 同じイベントに、同じメールアドレスの有効な予約がすでにある（R-03）
    class AlreadyReserved < BusinessRuleViolation
      def initialize
        super("このメールアドレスでは、すでに予約があります")
      end
    end
```

## 10.6　Active Recordによる永続化を実装する

**初花**: リポジトリはどこに置くんだっけ。

**マリゴールド**: インフラ層だから、`app/infrastructure/ticketing/` だよ。定数は `Ticketing::InventoryRepository` になる。

`app/infrastructure/ticketing/inventory_repository.rb`:

```ruby
module Ticketing
  # 残席（Inventory）を ticket_inventories テーブルに保存し、読み込む
  class InventoryRepository
    def find(event_id)
      to_entity(TicketInventory.find_by!(event_id: event_id))
    rescue ActiveRecord::RecordNotFound
      raise NotFound, "イベント #{event_id} の残席が見つかりません"
    end

    def add(inventory)
      TicketInventory.create!(event_id: inventory.event_id, capacity: inventory.capacity,
                              reserved_count: inventory.reserved_count)
    end

    def save(inventory)
      TicketInventory.where(event_id: inventory.event_id)
                     .update_all(capacity: inventory.capacity, reserved_count: inventory.reserved_count,
                                 updated_at: Time.current)
    end

    private

    def to_entity(record)
      Inventory.new(event_id: record.event_id, capacity: record.capacity, reserved_count: record.reserved_count)
    end
  end
end
```

`app/infrastructure/ticketing/reservation_repository.rb`:

```ruby
module Ticketing
  # 予約（Ticketing::Reservation）を reservations テーブルに保存し、読み込む
  class ReservationRepository
    def find(id)
      to_entity(::Reservation.find(id))
    rescue ActiveRecord::RecordNotFound
      raise NotFound, "予約 #{id} が見つかりません"
    end

    # 新しい予約を保存して、ID の付いた予約を返す
    def add(reservation)
      record = ::Reservation.new(event_id: reservation.event_id)
      copy(reservation, to: record)
      record.save!(validate: false)
      to_entity(record)
    rescue ActiveRecord::RecordNotUnique
      raise Reservation::AlreadyReserved
    end

    def save(reservation)
      record = ::Reservation.find(reservation.id)
      copy(reservation, to: record)
      record.save!(validate: false)
    end

    def active_exists?(event_id:, email:)
      ::Reservation.active.exists?(event_id: event_id, email: email.to_s)
    end

    private

    def copy(reservation, to:)
      to.assign_attributes(
        name: reservation.applicant.name,
        email: reservation.applicant.email.to_s,
        quantity: reservation.count.to_i,
        price: reservation.price.yen,
        status: reservation.status.to_s
      )
    end

    def to_entity(record)
      Reservation.new(
        id: record.id,
        event_id: record.event_id,
        applicant: Applicant.new(name: record.name, email: record.email),
        count: ReservationCount.new(record.quantity),
        price: Money.new(record.price),
        status: record.status.to_sym
      )
    end
  end
end
```

**初花**: `::Reservation` の `::` は？

**マリゴールド**: `module Ticketing` の中で `Reservation` と書くと、`Ticketing::Reservation`（ドメインのエンティティ）になるからね。先頭に `::` を付けると、一番外側の `Reservation`、つまり `app/models` の Active Record を指す。同じ名前の2つを、`::` で書き分けているんだ。

| 書き方（`module Ticketing` の中） | 指すもの |
|------------------------------|--------|
| `Reservation` | `Ticketing::Reservation`（ドメインのエンティティ） |
| `::Reservation` | `Reservation`（`app/models` の Active Record） |
| `Applicant`・`ReservationCount` | `Ticketing::Applicant`・`Ticketing::ReservationCount` |
| `Money` | `Money`（`Ticketing` にないので、外側を探す） |

`save!(validate: false)` にしているのは、正しいかどうかの判断をドメインのオブジェクトがすでに済ませているからです。リポジトリの仕事は保存だけで、ルールを二重に確かめません。

### イベントを登録したら、残席も作る

予約のコンテキストの残席は、イベントを登録したときに作ります。イベントと残席の保存は、同じトランザクションの中で行います。

`app/models/event.rb`（抜粋）:

```ruby
class Event < ApplicationRecord
  has_many :reservations, dependent: :destroy
  has_one :ticket_inventory, dependent: :destroy
```

`app/controllers/events_controller.rb`（抜粋）:

```ruby
  def create
    @event = Event.new(event_params)

    saved = Event.transaction do
      @event.save && Ticketing::InventoryRepository.new.add(
        Ticketing::Inventory.new(event_id: @event.id, capacity: @event.capacity)
      )
    end

    if saved
      redirect_to @event, notice: "イベントを登録しました。"
    else
      render :new, status: :unprocessable_content
    end
  end
```

## 10.7　テスト用のリポジトリを用意するべきか

**初花**: リポジトリのテストはデータベースが要るよね。ユースケースのテストでは、メモリの中だけで動く偽物のリポジトリを使えば速くならない？

**マリゴールド**: よくある考え方だね。実際に作って、本物と同じテストを流してみよう。どちらのリポジトリにも同じ例を流せるように、`shared_examples` を使うよ（確かめるための一時的なスペックです）。

```ruby
require "rails_helper"

# テスト用に、メモリの中だけで予約を持つリポジトリ
class InMemoryReservationRepository
  def initialize
    @records = {}
    @next_id = 1
  end

  def add(reservation)
    saved = Ticketing::Reservation.new(id: @next_id, event_id: reservation.event_id, applicant: reservation.applicant,
                                       count: reservation.count, price: reservation.price, status: reservation.status)
    @records[@next_id] = saved
    @next_id += 1
    saved
  end

  def find(id)
    @records.fetch(id) { raise Ticketing::NotFound }
  end
end

RSpec.describe "テスト用のリポジトリと本物の違い" do
  let(:event) { create(:event) }

  def build_reservation
    Ticketing::Reservation.new(event_id: event.id,
                               applicant: Ticketing::Applicant.new(name: "初花", email: "hatsuka@example.com"),
                               count: Ticketing::ReservationCount.new(2), price: Money.new(1500))
  end

  shared_examples "予約のリポジトリ" do
    it "保存した予約を読み込める" do
      saved = repository.add(build_reservation)

      expect(repository.find(saved.id)).to eq(saved)
    end

    it "同じメールアドレスの有効な予約は、2件目を保存できない" do
      repository.add(build_reservation)

      expect { repository.add(build_reservation) }.to raise_error(Ticketing::Reservation::AlreadyReserved)
    end
  end

  context "本物（Active Record）" do
    let(:repository) { Ticketing::ReservationRepository.new }

    include_examples "予約のリポジトリ"
  end

  context "テスト用（メモリ）" do
    let(:repository) { InMemoryReservationRepository.new }

  end
end
```

**初花**: 偽物は、二重予約を素通りさせた。データベースのユニークインデックスを知らないからだ。

| | テスト用のリポジトリ（メモリ） | 本物のリポジトリ（データベース） |

**初花**: イベントの登録で、`Event.transaction do ... end` を使ったよね。残席の保存に失敗したら、イベントはどうなるの？

**初花**: 残席の保存で例外が出たら、先に保存したイベントも巻き戻された。

**マリゴールド**: `transaction` のブロックの中で例外が出ると、その中の変更はすべて取り消される。イベントだけあって残席がない、という中途半端な状態にならないんだ。

⚠️ `instance_double` は、本物のクラスにないメソッドを偽物に持たせようとするとエラーにしてくれるテストダブルです。第17章で、テストダブルの使い分けを扱います。

例外の扱いを、層ごとに整理しておきます。

| 起きること | どこで起きるか | 外に出すエラー |
|----------|------------|-------------|
| 残席を超える | ドメイン（`Inventory#reserve`） | `Ticketing::Inventory::NotEnoughSeats` |
| 予約が見つからない | リポジトリ（`find`） | `Ticketing::NotFound`（`ActiveRecord::RecordNotFound` から変換） |
| 二重予約 | データベース → リポジトリ（`add`） | `Ticketing::Reservation::AlreadyReserved`（`ActiveRecord::RecordNotUnique` から変換） |
| データベースが落ちている | Active Record | `ActiveRecord::ConnectionNotEstablished`（変換しない。予期しない障害として扱う） |

**初花**: データベースが落ちたときのエラーは、変換しないんだ。

**マリゴールド**: それは業務のルールの話ではなく、システムの障害だからね。ドメインの言葉にしてしまうと、かえって原因が分かりにくくなる。**業務として起こりうること** だけをドメインのエラーにする。それ以外は、そのまま上に投げて、第20章のログと監視で拾うよ。

## マリゴールドの one more thing

**読むだけの画面には、専用の読み込みを作ってもいい。**

10.4 で、一覧や検索のような読むだけの画面は、リポジトリを通さずに Active Record で読むことにしました。これをもう一歩進めると、「変えるためのモデル（集約）」と「読むためのモデル（画面に合わせた形）」をはっきり分ける **CQRS**（Command Query Responsibility Segregation）という考え方になります。たとえば主催者の申込一覧なら、予約・支払い・イベントを結合した、画面の列そのままの読み込み用のクラスを作ります。集約のルールを読み込みの都合で歪めずに済み、画面も速くなります。うめチケットでは、第19章でN+1クエリを扱うときに、この考え方をもう一度使います。
