# 第13章　コントローラとドメインモデルを接続する

**初花**: 第11章で画面からの申込をユースケースにつないだけど、コントローラはまだ Active Record の `Reservation` をフォームに使い回してるよね。

**マリゴールド**: そう。入力の形を確かめるためだけに、保存のための入れ物を借りている。この章では、入力を受け取る専用の **フォームオブジェクト** を作って、コントローラを薄くしよう。

**初花**: それと、スマホのアプリから予約したい、って言われたら？

**マリゴールド**: いい質問。同じユースケースを、HTMLの画面とJSONのAPIの両方から使えるようにするよ。そのとき大事なのが、**入力の誤り** と **業務のルールの誤り** を分けて、それぞれ正しいHTTPのステータスで返すことなんだ。

---

## 13.1　コントローラを薄く保つ

**初花**: 薄いコントローラって、どのくらい薄ければいいの？

**マリゴールド**: コントローラの仕事は、HTTPと業務の **通訳** だけにする。業務の判断が出てきたら、それはコントローラの仕事ではないよ。

| コントローラの仕事 | コントローラの仕事ではない |
|----------------|----------------------|
| リクエストのパラメータを受け取る | 残席が足りるかを判断する |
| 入力の形を確かめて、ユースケースの引数にする | 返金するかを判断する |
| ユースケースを呼ぶ | トランザクションの範囲を決める |
| 結果やエラーを、画面・JSON・ステータスにする | メールを送る |

第11章のときの `ReservationsController#create` は、次の形でした。

```ruby
  def create
    @event = Event.find(params[:event_id])
    @reservation = @event.reservations.build(reservation_params)
    return render_event_page unless @reservation.valid?

    reservation = Ticketing::ReserveSeats.new.call(
      event_id: @event.id, name: @reservation.name, email: @reservation.email, count: @reservation.quantity
    )
    notice = reservation.status == :confirmed ? "予約が確定しました。" : "仮予約しました。15分以内にお支払いください。"
    redirect_to reservation_path(reservation.id), notice: notice
  rescue Ticketing::Inventory::NotEnoughSeats => e
    @reservation.errors.add(:quantity, :exceeds_remaining_seats, count: e.remaining_seats)
    render_event_page
  rescue Ticketing::BusinessRuleViolation => e
    @reservation.errors.add(:base, e.message)
    render_event_page
  end
```

**初花**: 業務の判断はユースケースに移ったけど、「入力の形を確かめる」「エラーを画面の言葉にする」のために、Active Record の予約を作ってるんだね。

**マリゴールド**: そう。しかも `@event.reservations.build` は、保存しないのにイベントの予約の一覧に1件足してしまう。入力のための入れ物を、別に用意しよう。

## 13.2　リクエストパラメータをドメインモデルへ変換する

**初花**: パラメータを、直接 `Ticketing::Applicant` や `ReservationCount` にしちゃだめ？

**マリゴールド**: 値オブジェクトは、正しくない値だと例外で止まるよね。第8章で「値オブジェクトの例外はプログラムの誤りを止めるためのもの」と話した。利用者の入力の誤りには、**項目ごとに、分かる言葉で** 理由を返したい。その役目を持つのがフォームオブジェクトだよ。

```text
パラメータ（文字列）        フォームオブジェクト              ユースケース            ドメイン
{ "quantity" => "2" }  ─▶  ReservationForm               ─▶  ReserveSeats      ─▶  ReservationCount.new(2)
                           入力の形を確かめる（空・形式・範囲）    手順を並べる            業務のルール
                           誤りは項目ごとのメッセージに
```

`app/forms/reservation_form.rb`:

```ruby
# 申込のフォーム。画面や API から届いた入力の形を確かめ、ユースケースに渡す値にする
class ReservationForm
  include ActiveModel::Model
  include ActiveModel::Attributes

  attribute :name, :string
  attribute :email, :string
  attribute :quantity, :integer, default: 1

  validates :name, presence: true
  validates :email, presence: true, format: { with: URI::MailTo::EMAIL_REGEXP }
  validates :quantity, numericality: { only_integer: true, greater_than: 0,
                                       less_than_or_equal_to: Ticketing::ReservationCount::MAX }

  # ユースケースの引数にする
  def to_h
    { name: name, email: email, count: quantity }
  end

  # 業務のルールに反したことを、フォームのエラーとして表す
  def add_business_error(error)
    case error
    when Ticketing::Inventory::NotEnoughSeats
      errors.add(:quantity, :exceeds_remaining_seats, count: error.remaining_seats)
    when Ticketing::Reservation::AlreadyReserved
      errors.add(:email, :already_reserved)
    else
      errors.add(:base, error.message)
    end
  end
end
```

| 書き方 | 意味 |
|-------|------|
| `include ActiveModel::Model` | `valid?`・`errors`・`form_with` で使える形を持つ |
| `attribute :quantity, :integer` | `"2"` を `2` に変換して持つ |
| `less_than_or_equal_to: Ticketing::ReservationCount::MAX` | 上限の数は、ドメインの値オブジェクトと同じものを使う |
| `to_h` | フォームの言葉（`quantity`）を、ユースケースの言葉（`count`）に変える |

フォームは Active Record ではないので、項目名とメッセージの日本語は `activemodel:` に書きます。`ja.yml` の `reservation_statuses:` の前に足します。

`config/locales/ja.yml`（抜粋）:

```yaml

    attributes:
      reservation_form:
        name: お名前
        email: メールアドレス
        quantity: 人数
    errors:
      models:
        reservation_form:

            email:

```

## 13.3　フォームオブジェクトとドメインモデルの役割

**初花**: フォームにも「1〜4人」のチェックがあって、`ReservationCount` にもある。二重に書いてない？

**マリゴールド**: 同じ数を使っているけど、役割が違うんだ。フォームは「利用者に直してもらうため」、値オブジェクトは「ありえない値を作らせないため」。フォームを通らない呼び方（ジョブやコンソール）でも、値オブジェクトが最後に守るよ。

| | フォームオブジェクト | ドメインモデル |
|---|-----------------|-------------|
| 置き場所 | `app/forms/`（プレゼンテーション層） | `app/domain/` |
| 確かめるもの | 入力の形（空・形式・範囲） | 業務のルール（残席・二重予約・受付期間） |
| 誤りの表し方 | `errors` に項目ごとのメッセージ | 例外（`BusinessRuleViolation` など） |
| 知っているもの | 画面の項目名（`quantity`）、Rails の翻訳 | 業務の言葉（`count`） |
| 画面ごとに | 作り分けてよい（申込の画面と、主催者の代理入力の画面） | 1つ |

**初花**: 画面ごとに作り分けていいのは便利だね。主催者が電話で受けた申込を入れる画面なら、メールアドレスを空でもいいことにする、とか。

**マリゴールド**: そう。でもその場合でも、ドメインの `Applicant` はメールアドレスを求めるから、代理入力の画面には「メールアドレスのない申込者をどう扱うか」という **業務の議論** が先に要る。フォームはあくまで入口の都合で、ルールそのものはドメインで決めるんだ。

コントローラを、フォームオブジェクトを使う形に直します。

`app/controllers/reservations_controller.rb`（抜粋）:

```ruby
  def create
    @event = Event.find(params[:event_id])
    @form = ReservationForm.new(reservation_params)
    return render_event_page unless @form.valid?

    reservation = Ticketing::ReserveSeats.new.call(event_id: @event.id, **@form.to_h)
    redirect_to reservation_path(reservation.id), notice: reserved_notice(reservation)
  rescue Ticketing::BusinessRuleViolation => e
    @form.add_business_error(e)
    render_event_page
  end
```

`app/controllers/reservations_controller.rb`（抜粋）:

```ruby

    reservation.status == :confirmed ? "予約が確定しました。" : "仮予約しました。15分以内にお支払いください。"
```

## 13.4　バリデーションエラーと業務エラーを分ける

**初花**: 入力の誤りと業務の誤り、画面にはどっちも赤いメッセージで出るよね。分ける意味ある？

**マリゴールド**: 利用者にとっての意味が違うんだ。並べてみよう。

| | 入力の誤り（バリデーションエラー） | 業務の誤り（業務エラー） |
|---|---------------------------|---------------------|
| 例 | 名前が空、人数が5人 | 残席が足りない、二重予約、受付終了 |
| 誰が直せるか | 申込者が入力を直せば通る | 入力を直しても通らない（状況が変わらない限り） |
| 同じ入力でもう一度送ったら | 何度でも同じ誤り | 誰かがキャンセルすれば通るかもしれない |
| 確かめる場所 | フォームオブジェクト | ドメイン |
| 確かめるのに要るもの | 入力だけ | データベースの今の状態 |

**初花**: 業務の誤りは、「今の状態」とぶつかってるんだ。

**マリゴールド**: そう。だから、HTTPのステータスも分けたほうが、受け取った側が次にどうすればいいかを判断しやすい。特にAPIでは大事だよ。

## 13.5　HTTPステータスコードへ変換する

**初花**: ステータスって、422以外に何を使えばいい？

**マリゴールド**: うめチケットで使うステータスを決めよう。

| 起きたこと | ステータス | 意味 |
|----------|----------|------|
| 申し込めた | 201 Created | 予約が作られた |
| 入力の誤り | 422 Unprocessable Content | 送られた内容を処理できない。入力を直せば通る |
| 残席が足りない・二重予約・受付終了 | 409 Conflict | 今の状態とぶつかった |
| イベントがない | 404 Not Found | 対象が見つからない |

**初花**: HTMLの画面でも、業務の誤りは409で返すの？

**マリゴールド**: 画面では、入力したフォームをエラーつきで表示し直したいよね。Railsのフォームは、表示し直すときに422を返す約束になっているから、画面では **どちらの誤りも422でフォームを出し直す**。409は、プログラムが読むAPIで使おう。

| | 入力の誤り | 業務の誤り |
|---|----------|----------|
| HTMLの画面 | 422（フォームをエラーつきで表示し直す） | 422（同じ） |
| JSONのAPI | 422（項目ごとのエラー） | 409（エラーコードとメッセージ） |

ドメインのエラーとステータスの対応表は、プレゼンテーション層の concern にまとめます。

`app/controllers/concerns/domain_error_responses.rb`:

```ruby
# ドメインのエラーを、HTTP のステータスとエラーコードに変える。
# この対応表はプレゼンテーション層だけが持ち、ドメイン層は HTTP を知らない。
module DomainErrorResponses
  def domain_error_response(error)
    case error
    when Ticketing::Inventory::NotEnoughSeats then [ :conflict, "not_enough_seats" ]
    when Ticketing::Reservation::AlreadyReserved then [ :conflict, "already_reserved" ]
    when Ticketing::SalesPeriod::Closed then [ :conflict, "sales_closed" ]
    when Ticketing::NotFound then [ :not_found, "not_found" ]
    else [ :unprocessable_content, "business_rule_violation" ]
    end
  end
end
```

**初花**: エラーコードの `not_enough_seats` みたいな文字列は、何に使うの？

**マリゴールド**: APIを使うスマホのアプリが、**メッセージの文章ではなくコードで分岐できる** ようにするためだよ。メッセージの文章は、あとで言い回しを直すかもしれないけど、コードは約束として変えない。

## 13.6　HTMLとJSON APIの両方に対応する

**初花**: API用のコントローラは、今の `ReservationsController` に `respond_to` を足す？

**マリゴールド**: 分けて作ろう。APIはCSRFのトークンもブラウザの確認も要らないし、エラーの返し方も違うからね。Railsには、APIのための軽い親クラス `ActionController::API` があるよ。

`app/controllers/api/base_controller.rb`:

```ruby
module Api
  # JSON の API の親コントローラ。画面用の機能（CSRF の確認・ブラウザの確認）は持たない
  class BaseController < ActionController::API
    include DomainErrorResponses

    rescue_from Ticketing::BusinessRuleViolation, Ticketing::NotFound do |error|
      status, code = domain_error_response(error)
      render json: { error: { code: code, message: error.message } }, status: status
    end
  end
end
```

`app/controllers/api/reservations_controller.rb`:

```ruby
module Api
  class ReservationsController < BaseController
    def create
      form = ReservationForm.new(params.expect(reservation: %i[name email quantity]))
      unless form.valid?
        render json: { errors: form.errors.to_hash(true) }, status: :unprocessable_content
        return
      end

      reservation = Ticketing::ReserveSeats.new.call(event_id: params[:event_id], **form.to_h)
      render json: {
        reservation: { id: reservation.id, status: reservation.status, total_price: reservation.total_price.yen }
      }, status: :created
    end
  end
end
```

**初花**: 画面のコントローラと見比べると、使ってる部品は同じだね。フォームオブジェクトとユースケース。違うのは、結果を `redirect_to` にするか `render json:` にするかだけ。

**マリゴールド**: それが、ユースケースをHTTPから切り離した効果だよ。入口が増えても、業務の手順は1つのまま。

## 13.7　ドメイン層からHTTPやRails固有の例外を切り離す

**初花**: 409や404は、コントローラの concern にだけ書いてあるんだよね。ドメインのほうには本当に出てこない？

**マリゴールド**: 探して確かめよう。HTTPのステータスや、Rails・Active Record・コントローラの名前が `app/domain` に出てくるかを調べるよ。

```bash
grep -rn -E "ActiveRecord|ActionController|Rails\.|render|redirect_to|:conflict|:not_found|:unprocessable_content" app/domain
```

（何も表示されません。）

**初花**: 1行も出てこない。

**マリゴールド**: ドメインは「残席が足りない」と言うだけで、それが409なのか、画面のエラーなのか、ジョブのやり直しなのかは知らない。**どう伝えるかは、伝える側（プレゼンテーション層）が決める**。だから、新しい入口（ジョブ・API・コンソール）を足しても、ドメインは1行も変わらないんだ。

| 層 | 知っているエラー | 例 |
|----|--------------|----|
| ドメイン | 業務のルールのエラー | `Ticketing::Inventory::NotEnoughSeats` |
| インフラ（リポジトリ） | Active Record のエラーを、ドメインのエラーに変える | `RecordNotUnique` → `AlreadyReserved`、`RecordNotFound` → `Ticketing::NotFound` |
| アプリケーション（ユースケース） | ドメインのエラーを、そのまま上に投げる | — |
| プレゼンテーション | ドメインのエラーを、HTTP・画面に変える | `NotEnoughSeats` → 409・`not_enough_seats`／フォームのエラー |

## 初花のメモ帳

- コントローラは HTTP と業務の通訳。入力をフォームオブジェクトで確かめて、ユースケースに渡し、結果を返す
- 入力の誤りは「入力を直せば通る」、業務の誤りは「今の状態とぶつかった」。APIでは422と409に分ける
- ドメインのエラーを HTTP に変える対応表は、プレゼンテーション層だけが持つ。ドメインは HTTP を知らない

## マリゴールドの one more thing

**エラーの形は、標準の形式にそろえることもできる。**

この章のAPIは、エラーを `{"error": {"code": ..., "message": ...}}` という自分たちの形で返しました。HTTPのAPIのエラーには、**RFC 9457（Problem Details for HTTP APIs）** という標準の形式もあります。`type`（エラーの種類を表すURI）・`title`・`status`・`detail` を持つJSONを、`application/problem+json` という種類で返す決まりです。APIを外の会社にも使ってもらうなら、標準の形にそろえておくと、受け取る側の実装が楽になります。エラーコードの一覧を、`docs/` に用語集と同じように残しておくのもよいでしょう。
