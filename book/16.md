# 第16章　並行処理とデータ整合性

**初花**: 第2章のログで、「`SUM` で数えてから `INSERT` する」順番を覚えておいて、って言われたよね。第11章のユースケースの最後にも、⚠️ があった。

**マリゴールド**: 「同時に来た2つの申込が同じ残席を読むと、両方とも残席ありと判断してしまう」だね。この章では、それを **実際に起こして** から直すよ。

**初花**: わざと起こすの？ どうやって？

**マリゴールド**: 2つのスレッドで同時に申し込むテストを書くんだ。並行処理のバグは、本番でまれにしか起きないから、再現できるテストがないと直ったかどうかも分からない。最後に、通信のやり直しで同じ申込が2回届く場合も扱おう。

---

## 16.1　同時予約で定員を超える仕組み

**初花**: 同時の申込って、テストでどうやって作るの？

**マリゴールド**: まず、同時の申込をテストで作る道具を用意しよう。2つのスレッドで、それぞれ別のデータベース接続を使って、同じユースケースを呼ぶよ。

`spec/support/concurrency_helpers.rb`:

```ruby
module ConcurrencyHelpers
  # ブロックを、別々のスレッド（別々のデータベース接続）で同時に動かし、それぞれの結果か例外を返す
  def run_concurrently(count)
    threads = Array.new(count) do |index|
      Thread.new do
        ActiveRecord::Base.connection_pool.with_connection { yield(index) }
      rescue => e
        e
      end
    end
    threads.map(&:value)
  end

  # 2つのスレッドが、ここまで来るまで互いに待つ（最大1秒）
  def wait_for_each_other(barrier)
    barrier.wait(1)
  end
end

RSpec.configure do |config|
  config.include ConcurrencyHelpers, :concurrency

  # 別のスレッドから見えるように、このテストではトランザクションを使わず、終わったらテーブルを空にする
  config.around(:each, :concurrency) do |example|
    example.run
  ensure
    connection = ActiveRecord::Base.connection
    connection.truncate_tables(*(connection.tables - %w[schema_migrations ar_internal_metadata]))
  end
end
```

**初花**: トランザクションを使わないのは、なんで？ 今までのテストは全部、トランザクションで巻き戻してたよね。

**マリゴールド**: テストのトランザクションの中で作ったデータは、**コミットされていないから、別の接続からは見えない** んだ。2つのスレッドが同じイベントを読めるように、このテストだけは本当にコミットして、終わったらテーブルを空にするよ。

ただ、2つのスレッドを同時に動かしても、たまたま1人目が書き終えてから2人目が読むこともあります。必ず競合させるために、**2人とも残席を読み終えるまで、どちらも先に進まない** ように待ち合わせます。`Concurrent::CyclicBarrier` は、Railsが使っている `concurrent-ruby` に入っている待ち合わせの道具です。

`spec/concurrency/reserve_seats_concurrency_spec.rb`:

```ruby
require "rails_helper"

RSpec.describe "同時の申込", :concurrency do
  self.use_transactional_tests = false

  let(:event) { create(:event, capacity: 4, price: 1500) }

  before do # 先客が3人。残り1席
    3.times do |index|
      Ticketing::ReserveSeats.new.call(event_id: event.id, name: "先客#{index}", email: "first#{index}@example.com", count: 1)
    end
  end

  # 2人とも残席を読み終えてから書き込むように、読んだところで待ち合わせる
  def inventories_that_wait(barrier)
    Ticketing::InventoryRepository.new.tap do |repository|
      allow(repository).to receive(:find).and_wrap_original do |original, *args, **options|
        original.call(*args, **options).tap { wait_for_each_other(barrier) }
      end
    end
  end

  it "残り1席に2人が同時に申し込んでも、定員を超えない" do
    barrier = Concurrent::CyclicBarrier.new(2)
    inventories = inventories_that_wait(barrier)

    results = run_concurrently(2) do |index|
      Ticketing::ReserveSeats.new(inventories: inventories)
                             .call(event_id: event.id, name: "申込者#{index}", email: "attendee#{index}@example.com", count: 1)
    end

    reserved = Reservation.active.where(event: event).sum(:quantity)
    puts "成功: #{results.count { |r| r.is_a?(Ticketing::Reservation) }}件 / " \
         "有効な予約の人数: #{reserved}人 / 残席の予約済みの人数: #{event.ticket_inventory.reload.reserved_count}人（定員4人）"
    expect(reserved).to be <= 4
  end
end
```

**初花**: 先客の3人を、ユースケースで申し込んでるんだね。`reserved_count` を3にするだけじゃだめ？

**マリゴールド**: 最初はそう書いて試したんだけど、それだと「有効な予約」が1件もないから、結果がおかしくなった。

```text
成功: 2件 / 有効な予約の人数: 2人 / 残席の予約済みの人数: 4人（定員4人）
```

**初花**: 2人とも成功してるのに、有効な予約は2人だけ。先客の3人がいないからだ。これだとテストは通っちゃうね。

**マリゴールド**: 並行処理のテストは、**準備も本物の手順で作る** のが大事なんだ。先客もユースケースで申し込むと、こうなる。


## 16.2　Rubyの処理順とデータベースの競合

**初花**: でも、申込のユースケースはトランザクションの中だったよね。トランザクションがあれば、途中で割り込まれないんじゃないの？

**マリゴールド**: そう思いがちなんだ。時間の流れに並べてみよう。

```text
         申込者A（スレッド1）                         申込者B（スレッド2）
時刻 1   BEGIN
時刻 2   SELECT 残席 → 予約済み3人                     BEGIN
時刻 3                                              SELECT 残席 → 予約済み3人
時刻 4   Inventory#reserve(1) → 4人（Rubyの中で）
時刻 5                                              Inventory#reserve(1) → 4人（Rubyの中で）
時刻 6   UPDATE 残席 SET 予約済み = 4
時刻 7   INSERT 予約A
時刻 8   COMMIT
時刻 9                                              UPDATE 残席 SET 予約済み = 4   ← Aの更新を上書き
時刻 10                                             INSERT 予約B
時刻 11                                             COMMIT
```

**初花**: Bは、時刻3で「3人」を読んだあと、Aが4人にしたことを知らないまま、自分も4人と書いてる。

**マリゴールド**: トランザクションは「**途中で失敗したら全部取り消す**」ことは保証してくれる。でも「**読んでから書くまでの間に、ほかの人が同じ行を変えない**」ことは、何もしなければ保証してくれないんだ。しかも残席の判断（時刻4・5）はRubyの中で行っているから、データベースは「4人と書く」ことしか知らない。

| 保証されること | 保証されないこと |
|------------|--------------|
| トランザクションの中の変更が、全部そろって残るか、全部消えるか | 読んだ値が、書き込むときにもまだ正しいか |
| コミットしていない変更は、ほかの人から見えない | ほかの人のコミットを、自分のトランザクションの途中で見るかどうか |

## 16.3　トランザクション分離とロックの基礎

**初花**: 「ほかの人のコミットを途中で見るかどうか」って？

**マリゴールド**: **トランザクションの分離レベル** という設定で決まるんだ。PostgreSQLの標準は READ COMMITTED で、「SQLを実行した時点でコミット済みのもの」を見る。

| 分離レベル | 読むもの | 失われた更新 |
|----------|--------|-----------|
| READ COMMITTED（PostgreSQLの標準） | そのSQLの時点でコミット済みのもの | 起きる（16.1） |
| REPEATABLE READ | トランザクションの最初の時点のもの | 起きない代わりに、2人目はエラー（直列化の失敗）になり、やり直しが要る |
| SERIALIZABLE | 順番に1つずつ実行したのと同じ結果になるように | 起きない代わりに、エラーとやり直しが増える |

**初花**: 分離レベルを上げれば解決？

**マリゴールド**: 解決するけど、アプリ全体のすべてのトランザクションに影響するし、エラーになったときのやり直しも全部に書く必要がある。もっと狙いを絞ったやり方があるよ。**変えるつもりで読む行に、ロックをかける** んだ。

## 16.4　楽観ロックと悲観ロック

**初花**: ロックって、どんな種類があるの？

**マリゴールド**: ロックには2つの考え方があるよ。

| | 悲観ロック | 楽観ロック |
|---|---------|---------|
| 考え方 | 競合は起きるもの。読むときに鍵をかけて、ほかの人を待たせる | 競合はめったに起きない。書くときに、読んだあと変わっていないかを確かめる |
| SQL | `SELECT ... FOR UPDATE` | `UPDATE ... WHERE lock_version = 読んだときの番号` |
| 競合したとき | 2人目は、1人目が終わるまで待つ | 2人目はエラーになる。読み直してやり直す |
| 向いている場面 | 同じ行に申込が集中する（人気のイベントの残席） | 同じ行を同時に変えることがまれ（イベントの説明の編集） |

**初花**: 残席は、人気のイベントだと一度にたくさんの申込が来るよね。悲観ロックかな。

**マリゴールド**: そう。それに、残席を変えるトランザクションは短い（読んで、1を足して、書くだけ）から、待たせても長くはならない。リポジトリに、ロックをかけて読む引数を足そう。

`app/infrastructure/ticketing/inventory_repository.rb`（抜粋）:

```ruby
    # lock: true なら、トランザクションが終わるまで、ほかの人がこの残席を読んで変えるのを待たせる
    def find(event_id, lock: false)
      to_entity(TicketInventory.lock(lock).find_by!(event_id: event_id))
```

```bash
bin/rails runner 'puts TicketInventory.lock(true).where(event_id: 1).limit(1).to_sql; puts TicketInventory.lock(false).where(event_id: 1).limit(1).to_sql'
```

```text
SELECT "ticket_inventories".* FROM "ticket_inventories" WHERE "ticket_inventories"."event_id" = 1 LIMIT 1 FOR UPDATE
SELECT "ticket_inventories".* FROM "ticket_inventories" WHERE "ticket_inventories"."event_id" = 1 LIMIT 1
```

残席を変えるユースケース（申込・キャンセル・期限切れ）では、ロックをかけて読みます。

`app/usecases/ticketing/reserve_seats.rb`（抜粋）:

```ruby
        inventory = @inventories.find(event_id, lock: true)
```

`app/usecases/ticketing/cancel_reservation.rb`（抜粋）:

```ruby
      inventory = @inventories.find(reservation.event_id, lock: true)
```

`app/usecases/ticketing/expire_reservation.rb`（抜粋）:

```ruby
      inventory = @inventories.find(reservation.event_id, lock: true)
```

2人目が受け取ったエラーも確かめるように、スペックの最後に1行足します。

`spec/concurrency/reserve_seats_concurrency_spec.rb`（抜粋）:

```ruby

    expect(results.grep(Exception).map(&:class)).to eq([ Ticketing::Inventory::NotEnoughSeats ])
```

```text
1 example, 0 failures
```

**初花**: 成功は1件、もう1人は `NotEnoughSeats`。直った！ でも、1.12秒もかかってる。

**マリゴールド**: 1人目は、残席を読んで鍵をかけたあと、待ち合わせで2人目を待つよね。でも2人目は、1人目の鍵が外れるまで `SELECT ... FOR UPDATE` で止まっているから、待ち合わせの場所まで来られない。1人目が待ち合わせを1秒であきらめて先に進み、コミットして鍵を外すと、2人目が「予約済み4人」を読んで、残席が足りないと分かるんだ。**2人目が待たされた** ことが、時間に出ているよ。

```text
         申込者A                                   申込者B
時刻 1   BEGIN
時刻 2   SELECT 残席 FOR UPDATE → 3人（鍵をかける）     BEGIN
時刻 3                                            SELECT 残席 FOR UPDATE → 待つ……
時刻 4   UPDATE 残席 SET 予約済み = 4
時刻 5   INSERT 予約A
時刻 6   COMMIT（鍵を外す）
時刻 7                                            → 4人（Aの更新のあとの値を読む）
時刻 8                                            Inventory#reserve(1) → NotEnoughSeats
時刻 9                                            ROLLBACK
```

### 楽観ロックも試してみる

楽観ロックは、Active Record の機能で試せます。`lock_version` という整数の列があると、Active Record は更新のたびにその番号を確かめて、1つ増やします。アプリには入れずに、一時的に次のマイグレーションを流して試します（試したらロールバックします）。

```ruby
class AddLockVersionToTicketInventories < ActiveRecord::Migration[8.1]
  def change
    add_column :ticket_inventories, :lock_version, :integer, null: false, default: 0
  end
end
```

同じ残席を2回読んでから、それぞれ更新します。

```text
ume-tickets(dev):001> first = TicketInventory.find_by!(event_id: 3)
ume-tickets(dev):002> second = TicketInventory.find_by!(event_id: 3)
ume-tickets(dev):003> first.update!(reserved_count: first.reserved_count + 1)
  TicketInventory Update (1.1ms)  UPDATE "ticket_inventories" SET "reserved_count" = 4, "updated_at" = '2026-10-18 12:02:47.182314', "lock_version" = 2 WHERE "ticket_inventories"."id" = 3 AND "ticket_inventories"."lock_version" = 1
=> true
ume-tickets(dev):004> second.update!(reserved_count: second.reserved_count + 1)
  TicketInventory Update (1.0ms)  UPDATE "ticket_inventories" SET "reserved_count" = 4, "updated_at" = '2026-10-18 12:02:47.185955', "lock_version" = 2 WHERE "ticket_inventories"."id" = 3 AND "ticket_inventories"."lock_version" = 1
(ume-tickets):4:in '<main>': Attempted to update a stale object: TicketInventory. (ActiveRecord::StaleObjectError)
```

**初花**: 2回目の `UPDATE` は、`lock_version = 1` の行を探してるけど、1回目で2になってるから、当てはまる行がない。それで `StaleObjectError`。

**マリゴールド**: 楽観ロックでは、2人目は待たされない代わりにエラーになる。残席のように申込が集中する行だと、エラーとやり直しが増えるから、本書では悲観ロックにしたんだ。

⚠️ 悲観ロックをかけたトランザクションの中で、決済サービスのような遅い外部の処理を呼ぶと、その間ずっとほかの申込が待たされます。第11章で決めたとおり、外部の呼び出しはトランザクションの外に置きます。

## 16.5　データベース制約を併用する

**初花**: 第9章の `CHECK` 制約（予約済みの人数は定員以下）は、16.1 の5人を止められなかったよね。

**マリゴールド**: 残席の行に書かれた値は「4人」だったからね。`CHECK` は、**書かれた値** しか見ない。失われた更新では、正しく見える値が書かれてしまうから、`CHECK` では気づけないんだ。

| 守り方 | 16.1 の「失われた更新」を | 理由 |
|-------|------------------|------|
| `CHECK (reserved_count BETWEEN 0 AND capacity)` | 止められない | 書かれた値（4人）は正しく見える |
| 悲観ロック（`FOR UPDATE`） | ✅ 止める | 2人目は、1人目の更新のあとの値を読む |
| 条件付きの更新（下の例） | ✅ 止める | 足す計算をデータベースの中で行う |

**初花**: 条件付きの更新って？

**マリゴールド**: 「今の値に1を足して、定員を超えないときだけ書く」を、1つの `UPDATE` でデータベースにやってもらう方法だよ。

```bash
bin/rails runner '
reserve_one = -> { TicketInventory.where(event_id: 3).where("reserved_count + 1 <= capacity").update_all("reserved_count = reserved_count + 1") }
TicketInventory.find_by!(event_id: 3).update!(reserved_count: 3)
puts "1回目: #{reserve_one.call}行を更新"
puts "2回目: #{reserve_one.call}行を更新"
puts "予約済みの人数: #{TicketInventory.find_by!(event_id: 3).reserved_count}人（定員4人）"
'
```

```text
1回目: 1行を更新
2回目: 0行を更新
予約済みの人数: 4人（定員4人）
```

**初花**: 2回目は、条件に合わないから0行。Rubyで読んでから書くんじゃなくて、データベースが読んで書くから、間に割り込まれないんだね。

**マリゴールド**: 速くて強い方法だよ。ただ、「残席を超えない」という業務のルールが、Rubyの `Inventory#reserve` ではなくSQLの中に移ってしまう。本書では、ルールを集約に置いたまま、悲観ロックで守ることにしたよ。

### 二重予約の同時の申込

もう一つの同時の問題、二重予約も確かめます。同じメールアドレスで2人（同じ人が2つのタブで）同時に申し込んだ場合です。

`spec/concurrency/double_booking_concurrency_spec.rb`:

```ruby
require "rails_helper"

RSpec.describe "同じメールアドレスの同時の申込", :concurrency do
  self.use_transactional_tests = false

  let(:event) { create(:event, capacity: 4, price: 1500) }

  it "二重予約のチェックを2人ともすり抜けても、データベースが1件だけにする" do
    barrier = Concurrent::CyclicBarrier.new(2)
    reservations = Ticketing::ReservationRepository.new
    allow(reservations).to receive(:active_exists?).and_wrap_original do |original, **options|
      original.call(**options).tap { wait_for_each_other(barrier) }
    end

    results = run_concurrently(2) do
      Ticketing::ReserveSeats.new(reservations: reservations)
                             .call(event_id: event.id, name: "初花", email: "hatsuka@example.com", count: 1)
    end

    expect(results.grep(Exception).map(&:class)).to eq([ Ticketing::Reservation::AlreadyReserved ])
    expect(Reservation.where(event: event).count).to eq(1)
    expect(event.ticket_inventory.reload.reserved_count).to eq(1)
  end
end
```

```bash
bundle exec rspec spec/concurrency --format documentation
```

```text
Finished in 1.16 seconds (files took 0.63335 seconds to load)
```

**初花**: 二重予約のチェック（`active_exists?`）は2人とも「ない」と答えたのに、データベースの部分ユニークインデックスが2件目を止めて、押さえた席も戻ってる。

**マリゴールド**: 第9章で作った制約と、第10章でリポジトリが `RecordNotUnique` を `AlreadyReserved` に変えたこと、第11章のトランザクションが、ここで全部つながったね。**チェックは理由を伝えるため、制約は同時でも守るため**。第2章から言ってきた役割分担だよ。

## 16.6　重複リクエストと冪等性キー

**初花**: 同時の申込とは別に、同じ申込が2回届くこともあるよね。第15章の支払いみたいに。

**マリゴールド**: APIのクライアント（スマホのアプリ）は、通信が切れると申込を送り直すことがある。1回目が届いていたら、2件の予約になってしまう。同じメールアドレスなら二重予約で止まるけど、それだと **1回目の結果（予約のID）が分からない**。第15章でうめペイがしてくれたことを、今度はうめチケットのAPIでやろう。

| | 送り直しが届いたとき | クライアントが受け取るもの |
|---|------------------|---------------------|
| 何もしない | 二重予約として 409 | 「すでに予約があります」。1回目の予約のIDは分からない |
| `Idempotency-Key` で覚えておく | 1回目の応答をそのまま返す | 1回目と同じ 201 と予約のID |

```ruby
# Idempotency-Key ヘッダーが同じリクエストには、最初の応答をそのまま返す。
# 通信が切れて、クライアントが同じ申込を送り直しても、2回申し込まれないようにする。
module IdempotentRequest
  def idempotently(&)
    key = request.headers["Idempotency-Key"]
    return yield if key.blank?

    record = IdempotencyKey.find_by(key: key)
    return render(json: record.response_body, status: record.response_status) if record&.completed?
    return render_in_progress if record

    run_once(IdempotencyKey.create!(key: key, request_path: request.path), &)
  rescue ActiveRecord::RecordNotUnique
    render_in_progress # 同じキーのリクエストが、ちょうど同時に来た
  end

  private

  def run_once(record)
    yield
    record.update!(response_status: response.status, response_body: JSON.parse(response.body))
  rescue StandardError
    record.destroy! # 応答を返せなかったので、同じキーでやり直せるようにする
    raise
  end

  def render_in_progress
    render json: { error: { code: "request_in_progress", message: "同じ申込を処理しています" } }, status: :conflict
  end
end
```

| 場面 | 動き |
|------|------|
| キーがない | ふつうに申し込む |
| 初めてのキー | キーを記録してから申し込み、応答を覚える |
| 応答を覚えているキー | 覚えている応答を、そのまま返す |
| 同じキーが処理中（同時に2つ届いた） | 409 `request_in_progress` |
| 業務のエラー（残席が足りないなど）になった | キーを消す。同じキーでやり直せる |

**初花**: 業務のエラーのときにキーを消すのはなんで？ 同じ答えを返せばいいんじゃない？

**マリゴールド**: 残席が足りないのは、**今の状態** とぶつかったからだよね（第13章）。キャンセルが出て席が空けば、同じ申込が通るかもしれない。だから、業務のエラーは覚えずに、やり直せるようにしているんだ。一方、入力の誤り（422）は何度送っても同じだから、覚えておいてもいい。

## 16.7　並行実行テストを作る

**初花**: 並行処理のテストって、書くのが難しいね。

**マリゴールド**: コツは3つだよ。この章のテストを振り返ってみよう。

| コツ | この章では | 理由 |
|-----|---------|------|
| 別々のデータベース接続で動かす | `run_concurrently` で、スレッドごとに `with_connection` | 1つの接続では、同時にならない |
| テストのトランザクションを使わない | `self.use_transactional_tests = false` と、テーブルを空にする `around` | コミットしないと、別の接続から見えない |
| 必ず競合する場所で待ち合わせる | `CyclicBarrier` を、読んだ直後（`find`・`active_exists?`）に置く | たまたま順番に動くと、バグがあっても通ってしまう |
| 準備も本物の手順で作る | 先客もユースケースで申し込む | 16.1 の最初の試しのように、準備が不自然だと結果も不自然になる |

**初花**: 待ち合わせの場所を間違えたら？

**マリゴールド**: 「読んでから書くまでの間」に置かないと、競合を作れない。並行処理のテストを書くときは、16.2 のような **時刻の表を先に描いて**、どこで待ち合わせれば悪い順番になるかを決めるといいよ。

⚠️ 並行処理のテストは、テーブルを空にするので、ほかのテストより遅くなります。`:concurrency` のタグを付けておくと、`bundle exec rspec --tag concurrency` でこれだけを流したり、`--tag ~concurrency` で外したりできます。

## 16.8　集約の整合性をどこまで保証するか

**初花**: これで、全部の整合性が守れた？

**マリゴールド**: どこまでを **すぐに**（同じトランザクションで）守り、どこからを **少し遅れて** 守るかを、表にしておこう。全部をすぐに守ろうとすると、ロックが広がって遅くなるからね。

| 整合性 | 守り方 | いつ |
|-------|-------|-----|
| 予約済みの人数は定員以下（R-01） | 残席の集約 ＋ 悲観ロック ＋ `CHECK` | すぐに |
| 二重予約しない（R-03） | ドメインサービス ＋ 部分ユニークインデックス | すぐに |
| 残席の予約済みの人数 ＝ 有効な予約の人数の合計 | 申込・キャンセル・期限切れを同じトランザクションで | すぐに（ずれたら第20章で検知） |
| 予約が作られたらメールが届く | ドメインイベント ＋ ジョブ | 少し遅れて |
| キャンセルしたら返金される | ドメインイベント ＋ ジョブ ＋ 冪等キー | 少し遅れて（失敗したら記録） |
| 同じ申込が2回届いても1件 | `Idempotency-Key` | すぐに |

**初花**: 「残席の人数 ＝ 予約の合計」は、すぐに守ってるのに、ずれたら検知、って書いてある。

**マリゴールド**: 手順は全部そろえたけど、誰かがコンソールで予約の状態を直接書き換えたら、ずれてしまうからね。**仕組みで守ったうえで、守れなかったときに気づける** ようにしておく。それが第20章の運用の話だよ。

## 初花のメモ帳

- トランザクションは「全部か無しか」を守るが、「読んでから書くまでの間」は守らない。失われた更新は `CHECK` でも気づけない
- 申込が集中する行は悲観ロック（`FOR UPDATE`）、まれな競合は楽観ロック（`lock_version`）。ロックの中で外部を呼ばない
- 並行処理のテストは、別の接続・トランザクションなし・読んだ直後の待ち合わせ・本物の手順の準備で書く

## マリゴールドの one more thing

**人気のイベントでは、ロックの「待ち」そのものが問題になる。**

悲観ロックは、残席の1行を順番に使う仕組みです。定員1万人の人気のイベントの発売開始に、数万の申込が一度に来ると、全員がその1行の前に並ぶことになり、待ち時間がどんどん延びます。こうした場面では、残席を複数の行に分けて持つ（10席ずつの束にする）、申込をいったんキューに並べて順番に処理する、抽選にして発売開始の瞬間の取り合いをなくす、といった方法が使われます。どれを選ぶかは、技術だけでなく「公平な申込とは何か」という業務の判断です。第21章で、抽選販売を足すときに、この話をもう一度します。
