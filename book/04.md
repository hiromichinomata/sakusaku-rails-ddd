# 第4章　ドメインとユビキタス言語

**初花**: 第3章の最後の「ちょうど3日前」、ずっと気になってる。早くコードを直したいな。

**マリゴールド**: 直す前に、正しい答えを決めないといけないよ。画面とコントローラのどちらが正しいのか、今のチームの誰も言えなかったでしょう。

**初花**: うん。「開催3日前まで」の「まで」に、ちょうどを含むのかどうか。コードを読んでも答えはなかった。

**マリゴールド**: 答えはコードの外、**業務** の側にあるんだ。この章では、うめチケットの業務で使う言葉を一つずつ決めて、用語集とルールの一覧を作る。最後に、決めた言葉のとおりに動くかをテストで確かめるよ。

---

## 4.1　ドメインとは何か

**初花**: DDDの「ドメイン」って、`example.com` のドメインとは違うんだよね？

**マリゴールド**: 違うよ。ソフトウェアで解決しようとしている **業務の領域** のこと。うめチケットなら「イベントの席を予約して、お金を受け取って、取り消しや返金に対応する」という仕事の世界全体だね。

| | 例 |
|---|----|
| ドメイン（業務の領域） | イベントの予約・チケット販売 |
| ドメインの知識 | 「仮予約は15分で取り消す」「開催3日前までは返金する」 |
| ドメインの専門家 | 主催者、窓口でキャンセルの電話を受けている人 |
| ソフトウェア | うめチケット（Railsアプリ） |

**初花**: ドメインの専門家って、うめチケットだと誰になるの？

**マリゴールド**: 主催者だね。初花も、道場の体験会を主催するなら専門家の一人だよ。「キャンセルの連絡がギリギリに来たら、返金する？」と聞かれたら、答えられるでしょう。

**初花**: 答えられる。開始の3日前ちょうどなら返金する。それより後なら、準備しちゃってるから返金しない。

**マリゴールド**: それがドメインの知識。第3章のコードは、その知識をRubyで書いたつもりだったけど、書いた人によって少しずつ違う形になっていた。DDDでは、ソフトウェアの中心に **ドメインの知識を正確に写したモデル** を置くことを目指すんだ。

| DDDでよく使う言葉 | 意味 |
|------------------|------|
| ドメイン | 解決したい業務の領域 |
| ドメインモデル | ドメインの知識を、概念とルールの形で表したもの（図・文章・コード） |
| ユビキタス言語 | チームの全員（開発者も主催者も）が同じ意味で使う言葉。コードにもそのまま使う |

## 4.2　技術用語と業務用語の違い

**初花**: ユビキタス言語って、用語をそろえるってこと？ 今のコードでも、だいたい通じてると思うけど。

**マリゴールド**: 第3章のコードと、初花が主催者として話す言葉を並べてみよう。

| コード・画面の言葉 | 初花（主催者）の言葉 | ずれ |
|-----------------|-------------------|------|
| `Reservation` の `name`・`email` | 申し込んだ人 | 予約に参加者の名前が入っているように見える。実際は申し込んで支払う人 |
| `quantity` | 人数 | 「数量」だとチケットの枚数にも、商品の数にも読める |
| `status: "pending"` | 仮予約 | 画面では「お支払い待ち」、メールでは「仮予約」と、表示が二通り |
| `Reservation.active` | 席を押さえている予約 | 「アクティブ」は業務の言葉ではない。何が含まれるかがコードを読まないと分からない |
| `PaymentGateway.charge` | 支払い | `charge` は「請求」にも「課金」にも訳せる |
| `starts_at - 3.days > Time.current` | 3日前まで | 「3日前」が72時間前か、カレンダーの3日前か、ちょうどを含むか、決まっていない |

**初花**: 確かに、`active` は自分でも「有効なやつ」くらいにしか説明できない。

**マリゴールド**: 技術の言葉は、コードを書く人どうしでは便利なんだ。でも、主催者と話すときには通じないし、通じないまま実装すると、第3章の「ちょうど3日前」のように、**業務の意味を誰も決めないままコードが答えを出してしまう**。

| | 技術用語 | 業務用語 |
|---|---------|---------|
| 例 | `pending`・`active`・`quantity`・`charge` | 仮予約・席を押さえている予約・人数・支払い |
| 通じる相手 | 開発者 | 主催者・窓口・開発者 |
| 決める人 | 実装した人 | 業務を知っている人と、開発者で一緒に |
| ずれたとき | バグやテストの失敗で気づく | 問い合わせやクレームで気づく |

ユビキタス言語は、業務の言葉を開発者が覚えることでも、開発者の言葉を主催者に押しつけることでもありません。**両者で同じ言葉を決めて、会話にもコードにもそれを使う** ことです。

## 4.3　顧客・イベント主催者・参加者の用語を整理する

**初花**: まずは「人」の言葉から整理しようか。主催者、お客さん、参加者……。

**マリゴールド**: 「お客さん」や「顧客」は、誰を指すかな。初花とマリゴールドの2人分を、初花が申し込んで支払った場合で考えてみて。

**初花**: お金を払ったのはわたしだから、顧客はわたし？ でも、当日来るのは2人とも。マリゴールドは顧客じゃないの？

**マリゴールド**: そこが曖昧なところ。「顧客にメールを送る」と言われたら、初花だけに送るのか、2人に送るのか分からない。役割で分けて、別々の名前を付けよう。

| 用語 | 意味 | 例 |
|------|------|----|
| 主催者 | イベントを企画し、登録する人・団体 | 梅酒づくりワークショップを開く公民館 |
| 申込者 | 予約を申し込み、支払う人。名前とメールアドレスで表す | 2人分を申し込んだ初花 |
| 参加者 | イベントに実際に来る人。1件の予約に1〜4人 | 初花とマリゴールド |
| ~~顧客~~ | 使わない（申込者と参加者のどちらか分からない） | — |

**初花**: 今のアプリで名前とメールアドレスを入れているのは、申込者なんだね。参加者一人ひとりの名前は持っていない。

**マリゴールド**: そう。だから `Reservation#name` は、本当は「申込者の名前」。コードの名前を変えるのは第8章で値オブジェクトを作るときにして、まずは用語集に「今のコードでは `name`・`email`」と書いておこう。

## 4.4　「予約」「申込」「購入」を区別する

**初花**: 次は「予約」。でも、予約、申込、購入って、だいたい同じ意味じゃない？

**マリゴールド**: 日常会話では混ざるね。うめチケットで、それぞれが **いつのこと** を指すか、時間の流れに並べてみよう。

```text
申込者の操作      申し込む           支払う                 キャンセルする
                    │                  │                         │
                    ▼                  ▼                         ▼
予約の状態     ┌─────────┐       ┌───────────┐            ┌──────────────┐
               │ 仮予約   │──────▶│ 予約確定   │───────────▶│ キャンセル済み │
               └─────────┘       └───────────┘            └──────────────┘
                    │   ▲  無料イベントは申し込んだ時点で予約確定
                    │   └──────────────────────────────────
                    │ 15分以内に支払わない
                    ▼
               ┌─────────┐
               │ 期限切れ │
               └─────────┘
```

| 用語 | 指すもの | 本書での扱い |
|------|---------|------------|
| 申込（申し込む） | 申込者が「席を押さえてほしい」と依頼する **行為** | 予約を作るきっかけ |
| 予約 | 申込によって作られる **記録**。仮予約から始まり、確定・キャンセル・期限切れのどれかで終わる | `Reservation` |
| 仮予約 | 支払いを待っている予約。席は押さえている | 画面の表示も「仮予約」にそろえる |
| 予約確定 | 支払いが済んだ予約。無料イベントは申込と同時 | — |
| ~~購入~~ | 使わない（無料イベントには購入がない。「予約確定」でそろえる） | — |

**初花**: 「購入」を使わないのは意外。チケット販売のサービスなのに。

**マリゴールド**: 有料のイベントだけなら「購入」でも通じるんだ。でも、梅林ガイドツアーのような無料のイベントでは、何も買っていないのに予約は確定する。「購入完了メール」が無料のイベントに届いたら変でしょう。全部のイベントで同じ言葉が使えるように、「予約確定」にそろえるよ。

**初花**: もう一つ。キャンセル済みと期限切れは、どっちも「取り消された予約」だよね。同じでよくない？

**マリゴールド**: 結果は似ているけど、**誰が取り消したか** が違うんだ。キャンセルは申込者が自分で取り消した。期限切れは、支払いがないのでシステムが取り消した。主催者に「キャンセルが多いイベント」を聞かれたとき、期限切れが混ざっていたら答えを間違えるよ。

| | キャンセル済み | 期限切れ |
|---|--------------|---------|
| 取り消した人 | 申込者 | システム（支払い期限を過ぎた） |
| 支払い | 済んでいることがある（返金の対象） | 必ず未払い |
| 席 | 戻す | 戻す |

### 画面の言葉をそろえる

第3章で、予約の状態の表示を「お支払い待ち」にしていました。用語集に合わせて直します。

`config/locales/ja.yml`（抜粋）:

```yaml
  reservation_statuses:
    pending: 仮予約（お支払い待ち）
    confirmed: 予約確定
    canceled: キャンセル済み
    expired: 期限切れ
```

テストの説明も仕様を表す文章なので、同じ言葉にそろえます。

`spec/requests/payments_spec.rb`（抜粋）:

```ruby
    it "カードが使えなければ、仮予約のまま" do
```

`spec/jobs/expire_pending_reservations_job_spec.rb`（抜粋）:

```ruby
  it "支払い期限を過ぎた仮予約を、期限切れにする" do
```

## 4.5　ビジネスルールを文章にする

**初花**: 言葉がそろったら、次はルールだね。

**マリゴールド**: 第3章で足したルールを、決めた言葉だけを使って文章にしよう。コードの書き方ではなく、主催者が読んで「そう、それ」と言える文にするのがコツだよ。

| 書き方 | 例 |
|-------|----|
| ❌ コードを日本語にしただけ | `status` が `pending` で `created_at` が15分前より古いものは `expired` にする |
| ❌ 曖昧なまま | 3日前までならキャンセルすると返金する |
| ✅ 用語集の言葉で、境界まで決める | 開始時刻の72時間前まで（ちょうどを含む）に予約確定をキャンセルすると、支払った全額を返金する |

**初花**: 「3日前」を「72時間前」に言い換えたのはなんで？

**マリゴールド**: 「3日前」には二通りの読み方があるからだよ。11月15日10時のイベントなら、「11月12日10時」と読む人と、「11月12日いっぱい」と読む人がいる。主催者の初花は、どっちのつもりだった？

**初花**: 開始の時刻から数えて3日だから、12日の10時。……そうか、「12日いっぱい」と思う人もいるのか。

**マリゴールド**: だから、誤解されない「72時間前」と書く。そして「まで」がちょうどを含むことも書く。決めたことは、理由と一緒に残しておこう。

| 曖昧だったこと | 決めたこと | 理由 |
|--------------|-----------|------|
| 「3日前」はいつか | 開始時刻の72時間前 | 主催者（初花）の意図。カレンダーの日付で数えると時差や日付の区切りで揺れる |
| 「〜まで」にちょうどを含むか | 含む | 申込者に有利な側にそろえる。画面の案内（`>=`）と同じ |
| 受付期間の終わり | 開始時刻の前まで。ちょうどからは受け付けない | 始まったイベントには申し込めない |
| 支払い期限 | 仮予約の作成から15分後。ちょうどまでは支払える | 「〜まで」はちょうどを含む、にそろえる |

ルールに番号を振って、一覧にします。アプリの `docs/domain/` に置きます。

`docs/domain/rules.md`:

```markdown
# うめチケット 業務ルール一覧

ルールには ID を振り、テスト（`spec/requests/business_rules_spec.rb`）の説明に同じ ID を書く。

| ID | ルール |
|----|-------|
| R-01 | 有効な予約の人数の合計は、イベントの定員を超えない |
| R-02 | 1件の予約の人数は1〜4人 |
| R-03 | 同じイベントに、同じメールアドレスの有効な予約は1件まで |
| R-04 | 申込は、イベントの開始時刻の前まで受け付ける。開始時刻ちょうどからは受け付けない |
| R-05 | 有料イベントの申込は仮予約になる。仮予約の作成から15分後まで（ちょうどを含む）に支払うと、予約確定になる |
| R-06 | 無料イベントの申込は、その場で予約確定になる |
| R-07 | 支払い期限を過ぎた仮予約は期限切れになり、席を戻す |
| R-08 | キャンセルできるのは、仮予約と予約確定だけ |
| R-09 | 開始時刻の72時間前まで（ちょうどを含む）に予約確定をキャンセルすると、支払った全額を返金する。それより後は返金しない |
| R-10 | キャンセル済み・期限切れの予約は、予約確定に戻せない |
| R-11 | 主催者は、定員を予約済みの人数より少なくできない |
```

**初花**: R-10 は、第3章でコンソールから「確定」に戻せちゃったやつだね。

**マリゴールド**: そう。あれは「バリデーションで書けなかった」のではなく、そもそも **ルールとして誰も書いていなかった** んだ。文章にすると、抜けていたルールが見つかるよ。

## 4.6　用語集を作成する

**初花**: 用語集は、どこに置けばいい？ Wikiとか？

**マリゴールド**: コードと一緒に、リポジトリの中に置くのがおすすめ。コードの名前を変えるときに、同じプルリクエストで用語集も直せるからね。

`docs/domain/glossary.md`:

```markdown
# うめチケット 用語集

業務で使う言葉と、コードでの名前の対応。迷ったら、この表の言葉で話し、この表の名前で書く。

## 人

| 用語 | 意味 | コードでの名前 | 使わない言葉 |
|------|------|--------------|-------------|
| 主催者 | イベントを企画し、登録する人・団体 | `organizer` | 管理者、オーナー |
| 申込者 | 予約を申し込み、支払う人。名前とメールアドレスで表す | `applicant`（今は `Reservation#name`・`#email`） | 顧客、ユーザー、会員 |
| 参加者 | イベントに実際に来る人。1件の予約に1〜4人 | `attendee` | お客さん |

## 予約のライフサイクル

| 用語 | 意味 | コードでの名前 |
|------|------|--------------|
| 申込（申し込む） | 申込者が、席を確保するよう依頼すること | `reserve` |
| 予約 | 申込によって作られる記録。仮予約から、確定・キャンセル・期限切れのどれかで終わる | `Reservation` |
| 仮予約 | 有料イベントで、支払いを待っている予約。席は確保されている | `pending` |
| 予約確定 | 支払いが済んだ（無料なら申込と同時の）予約 | `confirmed` |
| キャンセル | 申込者が予約を取りやめること。仮予約・予約確定のときだけできる | `cancel` / `canceled` |
| 期限切れ | 支払い期限までに支払われなかった仮予約 | `expire` / `expired` |
| 有効な予約 | 席を使っている予約。仮予約と予約確定 | `active` |

## 席とお金

| 用語 | 意味 | コードでの名前 |
|------|------|--------------|
| 定員 | イベントに入れる参加者の上限 | `capacity` |
| 人数 | 1件の予約の参加者の数（1〜4） | `quantity`（第8章で見直す） |
| 予約済みの人数 | 有効な予約の人数の合計 | `reserved_count` |
| 残席 | 定員 − 予約済みの人数 | `remaining_seats` |
| 料金 | 参加者1人あたりの金額（円） | `price` |
| 支払い金額 | 料金 × 人数 | `total_price` |
| 支払い | 決済サービスで支払い金額を受け取ること | `Payment`・`charge` |
| 返金 | 支払い金額を申込者に戻すこと。全額だけで、一部の返金はない | `refund` |

## 期限

| 用語 | 意味 |
|------|------|
| 受付期間 | 申込を受け付ける期間。イベントの開始時刻の前まで（開始時刻ちょうどからは受け付けない） |
| 支払い期限 | 仮予約の作成から15分後。ちょうど15分後までは支払える |
| 返金期限 | 開始時刻の72時間前。ちょうど72時間前までにキャンセルすれば全額返金する |

## 決めたこと

- 「顧客」は、申込者と参加者のどちらを指すか分からないので使わない
- 「購入」は使わない。支払いのない無料イベントもあるので、「予約確定」で揃える
- 「3日前」は、カレンダーの日付ではなく **開始時刻の72時間前** とする（主催者に確認済み）
- 「〜まで」の期限は、**ちょうどの時刻を含む**
```

**初花**: 「使わない言葉」の列があるのがいいね。つい「お客さん」って言っちゃいそうだから。

**マリゴールド**: 用語集は、増やすより **揺れをなくす** ためのものなんだ。「有効な予約」のように、コードの名前（`active`）と業務の言葉がまだ一致していないものも、正直に書いておく。一致させるのは、後の章の仕事だよ。

| 用語集に書くもの | 書かなくていいもの |
|----------------|------------------|
| 業務で意味が決まっている言葉 | Railsの仕組みの言葉（コントローラ、マイグレーション） |
| 似ていて混ざりやすい言葉の区別 | 辞書を引けば分かる一般的な言葉 |
| 境界（ちょうどを含むか、何時から何時まで） | 実装の方法（どのテーブルに入るか） |
| 使わないと決めた言葉と、その理由 | — |

## 4.7　用語の曖昧さをテストケースに変換する

**初花**: ルールが決まったら、あとは第14章でコードを直すだけ？

**マリゴールド**: その前に、決めたことを **テストにしておく** よ。文書は読まれなくなることがあるけど、テストは毎回実行される。特に、今回議論になった「ちょうど」の境界は、テストにしないとまた揺れるからね。

テストの説明には、ルールの ID を書きます。テストの結果から、どのルールの話かをすぐにたどれるようにするためです。

`spec/requests/business_rules_spec.rb`:

```ruby
require "rails_helper"

# docs/domain/rules.md の「〜まで」「ちょうど」の解釈を、境界の時刻で確かめる
RSpec.describe "業務ルールの境界", type: :request do
  let(:starts_at) { Time.zone.local(2026, 11, 15, 10, 0) }
  let(:event) { create(:event, price: 1500, starts_at: starts_at) }

  def reserve
    post event_reservations_path(event),
         params: { reservation: { name: "初花", email: "hatsuka@example.com", quantity: 1 } }
  end

  def pay(reservation)
    post reservation_payment_path(reservation), params: { token: "tok_visa" }
  end

  describe "R-04 申込は開始時刻の前まで" do
    it "開始時刻の1分前は申し込める" do
      travel_to(starts_at - 1.minute) { expect { reserve }.to change(Reservation, :count).by(1) }
    end

    it "開始時刻ちょうどは申し込めない" do
      travel_to(starts_at) { expect { reserve }.not_to change(Reservation, :count) }
    end
  end

  describe "R-05 支払いは仮予約から15分後まで（ちょうどを含む）" do
    let(:reservation) { create(:reservation, event: event, created_at: Time.current) }

    it "ちょうど15分後は支払える" do
      travel_to(reservation.created_at + 15.minutes) { pay(reservation) }

      expect(reservation.reload).to be_confirmed
    end

    it "15分1秒後は支払えない" do
      travel_to(reservation.created_at + 15.minutes + 1.second) { pay(reservation) }

      expect(reservation.reload).to be_expired
    end
  end

  describe "R-07 支払い期限を過ぎた仮予約は期限切れ" do
    let!(:reservation) { create(:reservation, event: event, created_at: Time.current) }

    it "ちょうど15分後は、まだ期限切れにしない" do
      travel_to(reservation.created_at + 15.minutes) { ExpirePendingReservationsJob.perform_now }

      expect(reservation.reload).to be_pending
    end
  end

  describe "R-09 返金は開始時刻の72時間前まで（ちょうどを含む）" do
    let(:reservation) { create(:reservation, event: event, quantity: 2) }

    before { pay(reservation) }

    it "ちょうど72時間前のキャンセルは、全額返金する" do
      travel_to(starts_at - 72.hours) { patch cancel_reservation_path(reservation) }

      expect(reservation.reload.payment).to be_refunded
    end

    it "72時間前を1分過ぎたキャンセルは、返金しない" do
      travel_to(starts_at - 72.hours + 1.minute) { patch cancel_reservation_path(reservation) }

      expect(reservation.reload.payment).to be_paid
    end
  end

  describe "R-10 キャンセル済みは予約確定に戻せない" do
    it "キャンセル済みの予約を確定に書き換えられない" do
      reservation = create(:reservation, event: event, status: "canceled")

      expect(reservation.update(status: "confirmed")).to be(false)
    end
  end
end
```

## マリゴールドの one more thing

**用語集は、コードのレビューでも使える。**

プルリクエストで新しいクラスやメソッドの名前が出てきたら、用語集に載っている言葉かどうかを確かめてみてください。載っていない言葉なら、「業務の言葉で言うと何か」をチームで話すきっかけになります。逆に、話し合って新しい言葉を決めたら、そのプルリクエストで用語集も一緒に直します。コードと用語集が同じリポジトリにあると、この2つを同時に変えられます。第8章からは、用語集の「コードでの名前」の列をコードに反映していきます。
