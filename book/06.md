# 第6章　境界づけられたコンテキスト

**初花**: 前の章で、`Event` の `starts_at` が、告知では「いつ開くか」、販売では「受付の締め切り」になってたよね。あれがずっと引っかかってる。

**マリゴールド**: 同じデータでも、使う仕事によって意味が変わる。この章では、その意味の境目に線を引くよ。DDDで一番大事な考え方の一つ、**境界づけられたコンテキスト**（Bounded Context）だ。

**初花**: 名前が難しそう。

**マリゴールド**: 中身はシンプルだよ。「この言葉は、この線の内側ではこの意味」と決めること。線の引き方を決めたら、最後にRubyのモジュールにも線を引いてみよう。

---

## 6.1　同じ言葉でも文脈によって意味が変わる

**初花**: 用語集で言葉はそろえたよね。それでも意味が変わるの？

**マリゴールド**: 用語集は「うめチケットの中で、同じ言葉を同じ意味で使おう」という約束だった。でも、仕事が違うと、同じ言葉に **違う関心** が向くんだ。3つの言葉で比べてみよう。

| 言葉 | イベント管理で | 予約で | 決済で |
|------|-------------|-------|-------|
| イベント | 告知する内容（タイトル・説明・会場・日時） | 席を売る対象（定員・残席・受付期間・返金期限） | 出てこない（金額と支払いIDだけ） |
| キャンセル | 主催者がイベントそのものを中止すること | 申込者が予約を取りやめること | 出てこない（「返金」として頼まれる） |
| 支払い | 出てこない | 仮予約が予約確定になる **条件** | カードからお金を受け取る **手続き** |

**初花**: 「キャンセル」が、主催者と申込者で違う意味になってる。イベントの中止もキャンセルって言うもんね。

**マリゴールド**: そう。もし一つのモデルに全部を詰めると、`cancel` というメソッドが「イベントの中止」なのか「予約の取りやめ」なのか分からなくなる。だから、言葉の意味が変わる場所で **モデルを分ける** んだ。

---

## 6.2　Bounded Contextの基本

**初花**: 「モデルを分ける」って、つまり境界づけられたコンテキストのこと？

**マリゴールド**: そう。境界づけられたコンテキストは、**一つのモデルが、一つの意味で通用する範囲** のことだよ。その範囲の中では、用語集の言葉が一つの意味だけを持つ。

| 言葉 | 意味 |
|------|------|
| 境界づけられたコンテキスト | 一つのモデルと、その言葉が通用する範囲。コードでは、モジュールやパッケージ、ときには別のアプリになる |
| サブドメイン（第5章） | 業務の側の分け方。「どんな仕事があるか」 |
| コンテキスト | 設計の側の分け方。「どこでモデルを分けるか」 |

**初花**: サブドメインとコンテキストって、同じものじゃないの？

**マリゴールド**: きれいに1対1になるのが理想だけど、必ずではないんだ。サブドメインは **問題の側**、コンテキストは **解決の側** の線だよ。うめチケットは小さいサービスだから、ほぼ1対1にしよう。

```text
問題の側（サブドメイン）              解決の側（コンテキスト）
┌──────────────┐                 ┌──────────────────┐
│ イベント管理   │ ──────────────▶ │ イベント管理        │
├──────────────┤                 ├──────────────────┤
│ 予約          │ ──────────────▶ │ 予約（Ticketing）   │
├──────────────┤                 ├──────────────────┤
│ 決済          │ ──────────────▶ │ 決済（Billing）     │
├──────────────┤                 ├──────────────────┤
│ 通知          │ ──────────────▶ │ 通知（Notification）│
└──────────────┘                 └──────────────────┘
```

コンテキストの中のモデルは、外の都合に合わせなくて構いません。予約のコンテキストの「イベント」は、タイトルや説明を持たず、定員と受付期間だけを持っていてよいのです。

## 6.3　イベント管理・予約・決済の境界を設計する

**初花**: じゃあ、3つのコンテキストで、それぞれ何を持つか決めればいいんだね。

**マリゴールド**: 中身・言葉・扱わないこと、の3つで決めよう。「扱わないこと」を書くのがコツだよ。

| コンテキスト | 持つもの | このコンテキストの言葉 | 扱わないこと |
|-------------|---------|-------------------|------------|
| イベント管理 | イベントのタイトル・説明・会場・開始日時・定員・料金 | 主催者・イベント・公開 | 誰が予約したか、残り何席か |
| 予約（Ticketing） | 残席（定員と予約済みの人数）、予約、申込者、受付期間、支払い期限、返金期限 | 申込者・参加者・仮予約・予約確定・キャンセル・期限切れ・残席 | カードの番号、決済サービスの使い方 |
| 決済（Billing） | 支払い金額、支払いID、返金ID | 支払い・返金 | 予約のルール（15分・72時間前） |
| 通知（Notification） | 宛先・件名・本文 | 送る | 予約の状態がどう変わるか |

**初花**: 決済が予約のルールを知らない、っていうのが面白い。返金するかどうかは、予約の側が決めるんだ。

**マリゴールド**: そう。決済は「この支払いIDで、この金額を返して」と頼まれたら返すだけ。72時間前かどうかは、予約のコンテキストの言葉だからね。こうしておけば、決済サービスを別の会社に変えても、返金のルールは一行も変わらないよ。

**初花**: 予約のコンテキストの「残席」は、イベント管理の「定員」とは別物なの？

**マリゴールド**: 元になるのは同じ数字だよ。イベント管理は「定員20人」を告知に載せて、予約は「定員20人のうち予約済みが18人、残席が2席」を守る。予約の側の言葉は「残席」で、その中に定員と予約済みの人数がある。このモデルは第9章で作るよ。

## 6.4　コンテキストマップを描く

**初花**: コンテキストが4つになったけど、それぞれはどうつながるの？

**マリゴールド**: コンテキストを分けたら、それぞれが **どうつながっているか** を図にするよ。これがコンテキストマップ。

```text
              ┌──────────────────────┐
              │ イベント管理（支援）   │
              └──────────┬───────────┘
                         │ 上流（U）→ 下流（D）
                         ▼
              ┌──────────────────────┐
              │ 予約（コア）          │
              └───┬──────────────┬───┘
                  │              │ 予約で起きたことを知らせる
                  │              ▼
                  │   ┌──────────────────────┐
                  │   │ 通知（汎用）          │
                  │   └──────────────────────┘
                  │ 支払い・返金を頼む
                  ▼
              ┌──────────────────────┐        ┌──────────────────────┐
              │ 決済（汎用）          │───────▶│ うめペイ（外部）      │
              └──────────────────────┘        └──────────────────────┘
```

**初花**: 上流・下流って、川みたいだね。

**マリゴールド**: 「影響が流れる向き」を表すんだ。上流が変わると、下流が影響を受ける。イベント管理で開始日時が変われば、予約の受付期間や返金期限も変わるでしょう。だから、イベント管理が上流で、予約が下流。

つながり方には名前が付いています。うめチケットで使うものだけを挙げます。

| パターン | 意味 | うめチケットでは |
|---------|------|---------------|
| 顧客／供給者 | 下流（顧客）の要望を、上流（供給者）が聞いてくれる関係 | イベント管理 → 予約、決済 → 予約 |
| 公開された言語 | 上流が、決まった形の情報（イベントなど）を公開し、下流が受け取る | 予約 → 通知（ドメインイベント、第12章） |
| 腐敗防止層 | 外部の言葉や形を、自分のモデルに持ち込まないための変換の層 | 決済 → うめペイ |
| 順応者 | 上流の形に、そのまま合わせる | 使わない |

**初花**: 腐敗防止層って、すごい名前……。

**マリゴールド**: 外のモデルが中に入り込んで、自分のモデルを「腐らせる」のを防ぐ層、という意味だよ。うめペイが `charge` や `token` という言葉を使っていても、予約のコンテキストには「支払い」としてしか見せない。今の `PaymentGateway` は、そのための窓口の始まりなんだ。

## 6.5　コンテキスト間の依存関係を整理する

**初花**: 図の矢印は、コードの依存の向きと同じ？

**マリゴールド**: 同じにしたい、という目標だよ。今のコードの依存を調べて、図とずれているところを探そう。

| 今のコード | 依存の向き | 図と比べて |
|----------|----------|----------|
| `Reservation belongs_to :event` | 予約 → イベント管理 | ✅ 下流が上流を参照している |
| `PaymentsController` が `PaymentGateway.charge` を呼ぶ | 予約 → 決済 | ✅ 予約が決済に頼んでいる |
| `Payment belongs_to :reservation` | 決済 → 予約 | ⚠️ 決済が予約のことを知っている |
| `Reservation` のコールバックが `ReservationMailer` を呼ぶ | 予約 → 通知 | ⚠️ 予約が通知のことを知っている（図では、通知が予約の出来事を受け取る） |
| `ReservationMailer` が `reservation.event.title` を読む | 通知 → 予約・イベント管理 | ✅ 下流が上流を読んでいる |
| `Event#reserved_count` が予約を数える | イベント管理 → 予約 | ⚠️ 上流が下流の中身を数えている |

**初花**: ⚠️ が3つ。予約がメールを送るのは、自然な気がしたけど。

**マリゴールド**: 予約が「メールを送れ」と命令していると、通知の仕方を変えるたびに予約のモデルを開くことになる。SMSで送りたい、主催者にも知らせたい、と増えるたびにね。予約は「予約が確定した」という **出来事を知らせるだけ** にして、通知が自分で受け取る形にすれば、向きが図とそろう。それが第12章のドメインイベントだよ。

| ⚠️ の依存 | 直し方 | 扱う章 |
|----------|-------|-------|
| 決済 → 予約（`Payment belongs_to :reservation`） | 決済は支払いIDと金額だけを持つ。予約の側が支払いIDを覚える | 第14章・第15章 |
| 予約 → 通知（コールバックからメール） | 予約はドメインイベントを発行し、通知が購読する | 第12章 |
| イベント管理 → 予約（`Event#reserved_count`） | 予約済みの人数は、予約のコンテキストの「残席」が持つ | 第9章 |

## 6.6　すべてを1つのモデルにまとめない理由

**初花**: 分けるとファイルが増えるよね。全部 `Event` と `Reservation` に入れておくほうが、探しやすくない？

**マリゴールド**: 小さいうちはね。でも、`Event` を変える理由を数えてみて。

| `Event` を変える理由 | どの仕事から来るか |
|-------------------|----------------|
| 告知に「持ち物」の欄を足したい | イベント管理 |
| 主催者がイベントを中止できるようにしたい | イベント管理 |
| 定員を予約済みの人数より減らせないようにしたい | 予約 |
| 残席の数え方を、合計（`SUM`）から数える列に変えたい | 予約 |
| 主催者ごとに返金期限を変えたい | 予約 |

**初花**: 告知の都合と、販売の都合が、同じファイルにどんどん入ってくる。

**マリゴールド**: 変える理由が複数あるモデルは、一つの変更が別の仕事を壊しやすい。告知の欄を足したついでに、残席の数え方を壊してしまうかもしれない。分けておけば、**変更の影響が、その仕事の中で止まる** んだ。

| | 1つの大きなモデル | コンテキストごとのモデル |
|---|-----------------|---------------------|
| 最初の作りやすさ | ✅ 速い | ファイルが増える |
| 言葉の意味 | 混ざる（「キャンセル」が2つの意味） | コンテキストの中では1つ |
| 変更の影響 | ほかの仕事に広がる | そのコンテキストの中で止まる |
| テスト | 関係ない準備が増える | そのコンテキストの準備だけで済む |
| 向いている場所 | 支援・汎用のサブドメイン | コアドメイン |

⚠️ コンテキストを分けることは、すぐにデータベースやアプリを分けることではありません。本書では、1つのRailsアプリ・1つのデータベースのまま、まずはモジュールで分けます。アプリを分ける話は、付録Iで扱います。

## 6.7　Railsのモジュール構成へ落とし込む

**初花**: 線を引いたら、コードにも線を引くんだよね。どうやって？

**マリゴールド**: Rubyの **モジュール**（名前空間）を使うよ。コンテキストごとにモジュールを決めておけば、`Billing::PaymentGateway` のように、名前を見ただけでどのコンテキストのものか分かる。

| コンテキスト | モジュール | いつ作るか |
|-------------|----------|----------|
| イベント管理 | なし（Railsの標準の場所のまま） | — |
| 予約 | `Ticketing` | 第8章から |
| 決済 | `Billing` | この章 |
| 通知 | `Notification` | 第12章から |

**初花**: イベント管理は、モジュールを作らないの？

**マリゴールド**: 第5章で、イベント管理は普通のRailsのMVCのままにすると決めたからね。`Event` も `EventsController` も、今のままで十分だよ。

### `PaymentGateway` を `Billing` に移す

まずは決済の窓口を、`Billing` モジュールに移します。Railsは、**フォルダの名前とモジュールの名前を対応させて** ファイルを自動で読み込みます（この仕組みを Zeitwerk と呼びます）。

| ファイルの場所 | 定義する定数 |
|-------------|------------|
| `app/services/payment_gateway.rb` | `PaymentGateway` |
| `app/services/billing/payment_gateway.rb` | `Billing::PaymentGateway` |

フォルダを作って、ファイルを移します。

```bash
mkdir -p app/services/billing
git mv app/services/payment_gateway.rb app/services/billing/payment_gateway.rb
```

Zeitwerk の対応が正しいかは、`bin/rails zeitwerk:check` で確かめられます。

```bash
bin/rails zeitwerk:check
```

```text
expected file app/services/billing/payment_gateway.rb to define constant Billing::PaymentGateway, but didn't
Hold on, I am eager loading the application.
```

**初花**: 怒られた。`billing/` に置いたのに、中身がまだ `class PaymentGateway` のままだからだ。

**マリゴールド**: そう。フォルダとモジュールの名前がそろっていないと、Railsはファイルを見つけられない。中身を `module Billing` で包もう。

`app/services/billing/payment_gateway.rb`:

```ruby
module Billing
  # 本書用の架空の決済サービス「うめペイ」の代わりに、手元で動く決済の窓口。
  # トークン tok_visa は成功、tok_declined はカードが使えなかったものとして扱う。
  class PaymentGateway
    class CardDeclined < StandardError; end

    def self.charge(amount:, token:)
      raise CardDeclined, "カードが利用できませんでした" if token == "tok_declined"

      Rails.logger.info("[PaymentGateway] charge amount=#{amount}")
      "ch_#{SecureRandom.hex(8)}"
    end

    def self.refund(charge_id:, amount:)
      Rails.logger.info("[PaymentGateway] refund charge_id=#{charge_id} amount=#{amount}")
      "re_#{SecureRandom.hex(8)}"
    end
  end
end
```

```text
Hold on, I am eager loading the application.
All is good!
```

テストを流すと、呼び出している側が古い名前のままなので落ちます。

```text
     NameError:
       uninitialized constant PaymentsController::PaymentGateway
```

```text
37 examples, 10 failures, 1 pending
```

呼び出している3か所を `Billing::PaymentGateway` に直します。

`app/controllers/payments_controller.rb`（抜粋）:

```ruby
    charge_id = Billing::PaymentGateway.charge(amount: amount, token: params[:token])
    @reservation.create_payment!(amount: amount, charge_id: charge_id)
    @reservation.update!(status: :confirmed)

    redirect_to @reservation, notice: "お支払いが完了し、予約が確定しました。"
  rescue Billing::PaymentGateway::CardDeclined => e
```

`app/controllers/reservations_controller.rb`（抜粋）:

```ruby
      refund_id = Billing::PaymentGateway.refund(charge_id: payment.charge_id, amount: payment.amount)
```

`spec/requests/cancellations_spec.rb`（抜粋）:

```ruby
      expect(Billing::PaymentGateway).to receive(:refund)
```

```text
Finished in 0.89238 seconds (files took 0.60567 seconds to load)
37 examples, 0 failures, 3 pending
```

**初花**: 呼び出す側に `Billing::` が付いたから、コントローラを読んだだけで「ここで決済のコンテキストに頼んでる」って分かるようになった。

**マリゴールド**: それがモジュールで線を引く効果だよ。ただ、まだ線を引いただけで、`Billing` の外から中身を何でも呼べてしまう。どこからどこへの依存を許すかのルールをテストで守る方法は、第19章で扱おう。

## ハンズオン 6-A — コンテキストマップとコードの境界

この章の成果物は「コンテキストマップとコードの境界」です。コンテキストマップを、アプリの `docs/domain/` に置きます。

`docs/domain/context_map.md`:

````markdown
# うめチケット コンテキストマップ

```text
              ┌──────────────────────┐
              │ イベント管理（支援）   │  告知としてのイベント
              │ EventManagement      │  タイトル・説明・会場・日時・定員・料金
              └──────────┬───────────┘
                         │ 上流（U）: イベントの開始日時・定員・料金を渡す
                         │ 下流（D）: 予約は、自分の言葉（残席・受付期間・返金期限）に読み替える
                         ▼
              ┌──────────────────────┐
              │ 予約（コア）          │  販売の対象としてのイベント（残席）と予約
              │ Ticketing            │  仮予約・確定・キャンセル・期限切れ
              └───┬──────────────┬───┘
                  │              │ 予約で起きたこと（予約された・確定した・キャンセルされた）を知らせる
                  │              ▼
                  │   ┌──────────────────────┐
                  │   │ 通知（汎用）          │  メールの宛先・件名・本文
                  │   │ Notification         │
                  │   └──────────────────────┘
                  │ 支払い・返金を頼む（金額と支払いIDだけを渡す）
                  ▼
              ┌──────────────────────┐        ┌──────────────────────┐
              │ 決済（汎用）          │───────▶│ うめペイ（外部）      │
              │ Billing              │ 腐敗防止層 │ charge・refund の API │
              └──────────────────────┘        └──────────────────────┘
```

| 関係 | 上流 → 下流 | パターン | 決めたこと |
|------|-----------|---------|-----------|
| イベント管理 → 予約 | イベント管理が上流 | 顧客／供給者 | 予約は、イベントの開始日時・定員・料金だけを受け取り、自分のモデルに読み替える |
| 予約 → 通知 | 予約が上流 | 公開された言語（ドメインイベント） | 通知は、予約で起きたことを受け取ってメールを送る。予約は通知のことを知らない |
| 予約 → 決済 | 決済が上流 | 顧客／供給者 | 予約は、金額と支払いIDだけで決済に頼む。決済は予約のルールを知らない |
| 決済 → うめペイ | うめペイが上流 | 腐敗防止層 | うめペイの言葉（charge・token）を `Billing` の中に閉じ込める |

## コードの境界（第6章の時点）

| コンテキスト | Ruby のモジュール | 今あるコード |
|-------------|-----------------|------------|
| イベント管理 | なし（Rails の標準の場所） | `Event`・`EventsController` |
| 予約 | `Ticketing`（第8章から） | `Reservation`・`ReservationsController`・`PaymentsController` の判断 |
| 決済 | `Billing` | `Billing::PaymentGateway`・`Payment` |
| 通知 | `Notification`（第12章から） | `ReservationMailer` |
````

## マリゴールドの one more thing

**コンテキストマップは、組織の地図でもある。**

コンテキストの境目は、多くの場合、チームや担当者の境目と重なります。「イベント管理の画面はAさんのチーム、予約と決済はBさんのチーム」となっていれば、上流・下流の関係は、そのままチーム同士の頼みごとの関係になります。顧客／供給者の関係なら、下流のチームが「この情報がほしい」と頼めば上流のチームが応える。順応者なら、下流が上流に合わせるしかない。コンテキストマップを描くと、コードの依存だけでなく、「誰に相談すればいいか」も見えてきます。うめチケットを一人で作っている間は、未来の自分への地図だと思って描いておきましょう。
