# 付録E　ドメインモデル設計チェックリスト

**初花**: 新しい機能を設計するときに、確かめることを一覧にしておきたい。

**マリゴールド**: 付録Eは、本書で身につけた考え方を **チェックリスト** にしたものだよ。全部に「はい」と答える必要はないけど、「いいえ」のところは、理由を言えるようにしておこう。

---

## E.1　作り始める前に（言葉とルール）

- [ ] 新しい言葉を、用語集（`docs/domain/glossary.md`）に足した。「使わない言葉」も決めた（第4章）
- [ ] 業務ルールを、ID を振った文章にした。「〜まで」が、ちょうどを含むかどうかも書いた（第4章）
- [ ] あいまいなルールを、境界の値のテストにした（第4章）
- [ ] その機能が、どのサブドメインのものかを決めた。コアでなければ、普通の Rails で作ることを考えた（第5章）
- [ ] どのコンテキストの言葉で話しているかを決めた。同じ言葉が、コンテキストによって違う意味になっていない（第6章）

## E.2　部品を選ぶ（エンティティ・値オブジェクト・集約）

- [ ] ID で見分けるもの（エンティティ）と、中身で見分けるもの（値オブジェクト）を分けた（第8章）
- [ ] 値オブジェクトは、作るときに正しさを確かめ、作ったあとは変わらない（第8章）
- [ ] 「いつでも成り立っていなければならない条件」を書き出し、それを守る集約を決めた（第9章）
- [ ] 集約は、その条件を守るのに要るものだけを持っている。大きすぎない（第9章）
- [ ] 集約の外からは、集約ルートのメソッドを通してだけ変える（第9章）
- [ ] 状態があるものは、遷移の表を作り、遷移のメソッドの外から状態を変えられない（第14章）
- [ ] 期限・金額・人数のような値は、数値のままではなく値オブジェクトで持つ（第8章・第14章）
- [ ] 主催者ごと・イベントごとに変わるルールは、定数ではなく値で受け取る（第21章）

## E.3　手順と保存（ユースケース・リポジトリ）

- [ ] ユースケースは、手順を組み立てるだけで、業務の判断はドメインに任せている（第11章）
- [ ] どのエンティティにも置けない判断だけを、ドメインサービスにした。名前だけのサービスになっていない（第11章・第18章）
- [ ] トランザクションは、ユースケースで開いている（第11章）
- [ ] 1回のトランザクションで変える集約は、原則1つ。例外にするときは理由を書いた（第9章・第16章）
- [ ] リポジトリは、コアドメインの集約にだけ作った。Active Record を包んだだけのリポジトリはない（第10章・第18章）
- [ ] ドメイン層は「今」や乱数を自分で取りに行かず、引数で受け取る（第7章・第21章）

## E.4　つなぐ（イベント・外部サービス・画面）

- [ ] 「起きたこと」に、ほかのコンテキストが反応するなら、ドメインイベントにした。名前は過去形（第12章）
- [ ] イベントは、トランザクションのコミットのあとで届く（第12章）
- [ ] 保存の入れ物（Active Record）に、業務の判断をするコールバックを書いていない（第18章）
- [ ] 外部サービスの言葉は、アダプターの中に閉じ込めた（第15章）
- [ ] ジョブとリトライで2回動いても、結果が1回分と同じ（冪等）（第15章）
- [ ] 入力の形の誤りと、業務の誤りを分けた。HTTP のステータスへの変換は、コントローラだけが持つ（第13章）
- [ ] ほかのコンテキストのテーブルに書き込んでいない。関連付けは、同じコンテキストの中だけ（第18章・第19章）

## E.5　並行処理と整合性

- [ ] 同時に2人が操作したら何が起きるかを考えた（第16章）
- [ ] 守らなければならない条件は、データベースの制約でも守った（第9章・第16章）
- [ ] 送り直しで2回処理されないように、冪等キーやユニーク制約を使った（第16章）
- [ ] すぐに揃わなくてよい整合性（あとで揃う）を、業務の人と合意した（第16章・第21章）

## E.6　テストと運用

- [ ] ルールの細かい組み合わせは、ドメインのテスト（Rails なし）で確かめた（第17章）
- [ ] 部品のつながりは、本物のデータベースで確かめた（第17章）
- [ ] テストに、ルールの ID（R-01 など）を書いた（第17章）
- [ ] 実装の詳細ではなく、結果で確かめている（第17章）
- [ ] 依存のルールを、テストで守らせている（第19章）
- [ ] 業務のイベントがログに残り、予約 ID でたどれる（第20章）
- [ ] 失敗したときのやり直しの手順が、手順書にある（第20章）

## E.7　やりすぎていないか

- [ ] 実装が1つしかないのに、インターフェース用の抽象クラスを作っていない（第7章）
- [ ] CRUD だけの機能に、ユースケースやリポジトリを挟んでいない（第7章）
- [ ] 同じになったと分かる前に、共通の部品にまとめていない（第21章）
- [ ] 設計の判断を、ほかに考えた案と割り切りとともに ADR に残した（第21章）
