# 第9章　集約と集約ルート

**初花**: 値オブジェクトで、1件の予約の中のルールはまとまった。でも定員は、予約を全部足さないと分からないんだよね。

**マリゴールド**: そう。「予約済みの人数の合計は、定員を超えない」というルールは、1つのオブジェクトの中には収まらない。第3章では、それを `Reservation` と `Event` の両側でバラバラに守っていたよね。

**初花**: 片方を直し忘れて、キャンセルした席が戻らなかったやつだ。

**マリゴールド**: この章では、そういうルールを **一か所だけで守る** ための単位、**集約** を作るよ。どこまでを1つの集約にするかを考えて、最後にデータベースの制約とも組み合わせよう。

---

## 9.1　集約とは何か

**初花**: 集約って、オブジェクトをまとめたもの？

**マリゴールド**: 「**一緒に変えないとルールが崩れるもの** を、ひとまとまりとして扱う単位」だよ。まとまりには入口が1つだけあって、外からはその入口を通してしか中を変えられない。その入口のエンティティを **集約ルート** と呼ぶ。

| 言葉 | 意味 | うめチケットでは |
|------|------|---------------|
| 集約 | 一緒に変えないとルールが崩れるもののまとまり | 残席（定員と予約済みの人数） |
| 集約ルート | 集約の入口になるエンティティ。外からはここだけを触る | `Ticketing::Inventory` |
| 不変条件 | 集約がいつも守っているルール | 予約済みの人数は 0 以上、定員以下（R-01） |

**初花**: 不変条件は、値オブジェクトのときにも出てきたね。

**マリゴールド**: 値オブジェクトの不変条件は「作ったときに正しければ、ずっと正しい」だった。集約の不変条件は「**状態が変わっても、変わったあとも正しい**」。予約が入ったり、キャンセルで席が戻ったりしても、ずっと守られている必要があるんだ。

集約を作るときの決まりです。

| 決まり | 理由 |
|-------|------|
| 外からは集約ルートのメソッドだけで変える | ルールを確かめる場所を1つにする |
| 集約の中は、1回の変更でまとめて正しくする | 途中の状態（席だけ増えて、予約がない）を外に見せない |
| ほかの集約は、IDで参照する | 集約どうしが絡まって、大きくなりすぎないようにする |
| 1回のトランザクションでは、できるだけ1つの集約だけを変える | 同時に変える範囲を小さくする（9.6） |

## 9.2　集約ルートによる状態変更の制御

**初花**: 残席の集約は、何ができればいい？

**マリゴールド**: 残席が変わるのは、予約が入ったとき、キャンセルか期限切れで席が戻ったとき、主催者が定員を変えたとき。この3つの操作を、集約ルートのメソッドにするよ。

| 操作 | メソッド | 守るルール |
|------|---------|----------|
| 予約が入る | `reserve(count)` | 残席を超えない（R-01） |
| 席が戻る | `release(count)` | 予約済みの人数は 0 より下にならない |
| 定員を変える | `change_capacity(new_capacity)` | 予約済みの人数より少なくできない（R-11） |

ルールに反する操作には、業務の言葉の名前を付けたエラーを用意します。ドメイン層のエラーの親クラスを作っておきます。

`app/domain/ticketing/business_rule_violation.rb`:

```ruby
module Ticketing
  # 業務のルールに反する操作をしたときのエラーの親クラス
  class BusinessRuleViolation < StandardError; end
end
```

`spec/domain/ticketing/inventory_spec.rb`:

require "domain_helper"

RSpec.describe Ticketing::Inventory do
  def count(value) = Ticketing::ReservationCount.new(value)

  let(:inventory) { described_class.new(event_id: 1, capacity: 20, reserved_count: 18) }

  it "残席は、定員 − 予約済みの人数" do
    expect(inventory.remaining_seats).to eq(2)
  end

  describe "#reserve" do
    it "残席の範囲なら、予約済みの人数が増える" do
      inventory.reserve(count(2))

      expect(inventory.reserved_count).to eq(20)
      expect(inventory.remaining_seats).to eq(0)
    end

    it "残席を超える人数は予約できず、予約済みの人数も変わらない" do
      expect { inventory.reserve(count(3)) }
        .to raise_error(Ticketing::Inventory::NotEnoughSeats, "残りの席数（2席）を超えています")

      expect(inventory.reserved_count).to eq(18)
    end
  end

  describe "#release" do
    it "キャンセルや期限切れで、席を戻す" do
      inventory.release(count(4))

      expect(inventory.reserved_count).to eq(14)
    end
  end

  describe "#change_capacity" do
    it "予約済みの人数ちょうどまでは減らせる（R-11）" do
      inventory.change_capacity(18)

      expect(inventory.capacity).to eq(18)
    end

    it "予約済みの人数より少なくはできない（R-11）" do
      expect { inventory.change_capacity(17) }
        .to raise_error(Ticketing::Inventory::CapacityBelowReserved, "定員は予約済みの人数（18人）より少なくできません")
    end
  end

  it "予約済みの人数が定員を超えた残席は作れない" do
    expect { described_class.new(event_id: 1, capacity: 20, reserved_count: 21) }.to raise_error(ArgumentError)
  end
end

`app/domain/ticketing/inventory.rb`:

```ruby
module Ticketing
  # 残席。イベントごとに、定員と予約済みの人数を持つ集約ルート。
  # 「予約済みの人数は定員を超えない（R-01）」をこのクラスだけで守る。
  class Inventory
    class NotEnoughSeats < BusinessRuleViolation
      def initialize(remaining_seats)
        super("残りの席数（#{remaining_seats}席）を超えています")
      end
    end

    class CapacityBelowReserved < BusinessRuleViolation
      def initialize(reserved_count)
        super("定員は予約済みの人数（#{reserved_count}人）より少なくできません")
      end
    end

    attr_reader :event_id, :capacity, :reserved_count

    def initialize(event_id:, capacity:, reserved_count: 0)
      unless reserved_count.between?(0, capacity)
        raise ArgumentError, "予約済みの人数（#{reserved_count}）が定員（#{capacity}）の範囲にありません"
      end

      @event_id = event_id
      @capacity = capacity
      @reserved_count = reserved_count
    end

    def remaining_seats
      capacity - reserved_count
    end

    def reserve(count)
      raise NotEnoughSeats, remaining_seats if count.to_i > remaining_seats

      @reserved_count += count.to_i
    end

    def release(count)
      @reserved_count = [ reserved_count - count.to_i, 0 ].max
    end

    def change_capacity(new_capacity)
      raise CapacityBelowReserved, reserved_count if new_capacity < reserved_count

      @capacity = new_capacity
    end
  end
end
```

**初花**: 第3章で `Reservation` と `Event` のバリデーションに分かれてた定員のルールが、`Inventory` の3つのメソッドに全部入った。

## 9.3　イベントと定員をどうモデル化するか

**初花**: でも、残席の集約に、予約そのものは入ってないよね。数だけ。予約を全部持たせたほうが、正確じゃない？

**マリゴールド**: いい疑問だね。実はいくつかの案があるんだ。並べて比べてみよう。

| 案 | 集約 | 定員のチェック | 困るところ |
|----|------|------------|----------|
| A | イベントが予約の一覧をまるごと持つ | 一覧の人数を合計する | 予約のたびに、そのイベントの予約を全部読み込む |
| B | 残席（定員と予約済みの人数）と、予約を別の集約にする | 予約済みの人数と比べる | 予約済みの人数と、実際の予約がずれないように守る必要がある |
| C | 予約だけ。定員はデータベースで `SUM` する | `SUM` してから保存する | 第3章と同じ。数えてから保存するまでに割り込まれる |

**初花**: Aは、予約が増えるほど重くなるのか。

**マリゴールド**: 定員1,000人のイベントなら、1件の予約のために1,000件を読み込むことになる。しかも、予約を1件変えるだけでも、イベント全体を1つの集約として扱うことになるんだ。案Aを、試しにコードにしてみよう。

次のスクリプトを `event_seats_demo.rb` として保存して実行します（試したら消します）。

```ruby
Dir["app/domain/**/*.rb"].sort.each { |file| require_relative file }

# 案A: イベントが、予約の一覧をまるごと持つ集約
class EventSeats
  def initialize(capacity:, reservations: [])
    @capacity = capacity
    @reservations = reservations
  end

  attr_reader :reservations

  def reserved_count
    @reservations.sum { |reservation| reservation.count.to_i }
  end

  def reserve(reservation)
    raise "残りの席数を超えています" if reserved_count + reservation.count.to_i > @capacity

    @reservations << reservation
  end
end

def reservation(count)
  Ticketing::Reservation.new(event_id: 1, applicant: Ticketing::Applicant.new(name: "初花", email: "hatsuka@example.com"),
                             count: Ticketing::ReservationCount.new(count), price: Money.new(1500))
end

seats = EventSeats.new(capacity: 4)
seats.reserve(reservation(4))
begin
  seats.reserve(reservation(1))
rescue => e
  puts "reserve: #{e.message}"
end

seats.reservations << reservation(4)
puts "予約済み: #{seats.reserved_count}人（定員4人）"
```

```

予約済み: 8人（定員4人）
```

**初花**: `reserve` では止まったのに、最後の行で8人になってる！ 定員4人なのに。

**マリゴールド**: `reservations` で、集約の **中の配列そのもの** を外に渡してしまったからね。受け取った側が `<<` で足せば、`reserve` のチェックを通らずに中身が変わる。この話は 9.5 で続けよう。本書は案Bにするよ。

| 本書の選択（案B） | 理由 |
|---------------|------|
| 残席を集約ルート `Inventory` にする | 定員のチェックに要るのは「予約済みの人数」だけ。予約の中身は要らない |
| 予約は、別の集約 `Ticketing::Reservation` にする | 予約ごとに、支払い・キャンセルと別々に変わる |
| 予約は残席を `event_id` で参照する | 集約どうしはIDでつなぐ（9.1の決まり） |
| 予約済みの人数と実際の予約のずれは、同じトランザクションで変えて防ぐ | 9.6 |

## 9.4　予約数の整合性を守る

**初花**: 案Bだと、予約が入ったら `Inventory` の人数を増やして、予約も作る。2つの集約を変えるんだね。

**マリゴールド**: そう。それぞれの操作で、どちらの集約がどう変わるかを整理しておこう。

| 業務の操作 | `Inventory`（残席） | `Ticketing::Reservation`（予約） |
|----------|------------------|-------------------------------|
| 申し込む | `reserve(count)` で人数を増やす | 仮予約（または予約確定）を作る |
| 支払う | 変わらない | 予約確定にする |
| キャンセルする | `release(count)` で席を戻す | キャンセル済みにする |
| 期限切れにする | `release(count)` で席を戻す | 期限切れにする |
| 主催者が定員を変える | `change_capacity` | 変わらない |

**初花**: 「予約済みの人数」と「有効な予約の人数の合計」は、いつも同じじゃないといけないんだよね。

**マリゴールド**: そう。第3章では `SUM` で毎回数え直していたからずれようがなかったけど、案Bでは数を **覚えておく** ぶん、ずれる可能性が生まれる。だから、2つの集約を変える操作は、必ず同じ手順で、同じトランザクションの中で行うことにするんだ。その手順をまとめるのが、第11章のユースケースだよ。

| ずれの原因 | 防ぎ方 | 扱う章 |
|----------|-------|-------|
| 席を増やしたのに、予約の保存に失敗した | 同じトランザクションで保存する | 第11章 |
| キャンセルしたのに、席を戻し忘れた | キャンセルの手順を1つのユースケースにまとめる | 第14章 |
| 同時に来た2つの申込が、同じ残席を読んだ | ロックで順番にする | 第16章 |
| それでもずれた | 定期的に数え直して検知する | 第20章 |

## 9.5　外部から内部オブジェクトを直接変更させない

**初花**: さっきの案Aの「8人」問題、どうすれば防げた？

**マリゴールド**: 中の配列を渡すときに、**凍らせた写し** を渡すんだ。`event_seats_demo.rb` の `attr_reader :reservations` を、次のように書き換えて試そう。最後の行も、エラーを表示するように `begin` で囲むよ。

```ruby
  def reservations
    @reservations.dup.freeze
  end
```

```ruby
begin
  seats.reservations << reservation(4)
rescue => e
  puts "#{e.class}: #{e.message.lines.first.strip}"
end
puts "予約済み: #{seats.reserved_count}人（定員4人）"
```

予約済み: 4人（定員4人）

**初花**: 今度は `FrozenError` で止まって、4人のまま。

**マリゴールド**: 集約の外に出すものは、**読むためだけ** に渡す。変えたいときは、必ず集約ルートのメソッドを呼んでもらう。本書の `Inventory` は、そもそも人数を書き換えるメソッドを持っていないよ。

```ruby
inventory = Ticketing::Inventory.new(event_id: 1, capacity: 4, reserved_count: 4)
inventory.reserved_count = 0
```

```text
NoMethodError: undefined method 'reserved_count=' for an instance of Ticketing::Inventory
```

| 外に出すもの | 書き方 | 例 |
|------------|-------|----|
| 数や値オブジェクト | そのまま返してよい（変えられない） | `remaining_seats`・`capacity` |
| 中の配列やハッシュ | 凍らせた写しを返す（`dup.freeze`） | 案Aの `reservations` |
| 中のエンティティ | 返さない。集約ルートのメソッドで操作してもらう | — |
| 状態を変える操作 | `attr_writer` を作らず、業務の名前のメソッドにする | `reserve`・`release`・`change_capacity` |

**初花**: Active Record のモデルだと、全部の列に `=` が付いてるもんね。`reservation.status = "confirmed"` も書けちゃう。

**マリゴールド**: そう。第3章の「キャンセル済みを確定に戻せた」問題の根っこは、そこにあるんだ。予約の状態の変え方は、第14章でこの章と同じ考え方で閉じるよ。

## 9.6　トランザクション境界を設計する

**初花**: 申し込むときは、`Inventory` と予約の2つの集約を変えるよね。9.1の「1回のトランザクションで1つの集約だけ」の決まりに反してない？

**マリゴールド**: 鋭いね。DDDの本では、集約をまたぐ変更は別々のトランザクションにして、少し遅れて整合させる（**結果整合性**）ことが勧められているんだ。でも、それには仕組みが要る。うめチケットで、どちらにするかを比べよう。

| | 同じトランザクションで変える | 別々のトランザクションにする（結果整合性） |
|---|------------------------|-----------------------------------|
| やり方 | 席を増やして、予約を作って、まとめてコミット | 席を増やしてコミット。そのあとイベントを受けて予約を作る |
| 途中で失敗したら | 両方とも元に戻る | 席だけ増えたままになる。直す仕組みが要る |
| 同時の申込への影響 | 2つの集約を同時にロックする | 小さい範囲だけロックする |
| 向いている場面 | 同じデータベースで、すぐに整合している必要がある | 別のサービス・別のデータベースにまたがる |

**初花**: うめチケットは1つのデータベースだし、席だけ増えて予約がない状態は困る。同じトランザクションがよさそう。

**マリゴールド**: 本書もそうするよ。決まりを破るのではなく、**理由があって選ぶ** ことが大事なんだ。決めたことを、操作ごとに表にしておこう。

| 業務の操作 | 変える集約 | トランザクション |
|----------|----------|--------------|
| 申し込む | `Inventory` ＋ 新しい予約 | 1つ（第11章） |
| 支払う | 予約 | 1つ。決済サービスの呼び出しはトランザクションの外（第15章） |
| キャンセルする | 予約 ＋ `Inventory` | 1つ。返金の依頼はトランザクションの外（第14章） |
| 期限切れにする | 予約 ＋ `Inventory` | 予約1件ごとに1つ（第14章） |
| メールを送る | なし | トランザクションの外。コミットのあと（第12章） |

**初花**: 決済サービスやメールは、トランザクションの外なんだ。

**マリゴールド**: データベースのトランザクションは、外のサービスまでは巻き戻せないからね。「返金はしたのに、キャンセルの保存は失敗した」が起きたら、もう取り消せない。外とのやり取りをどこに置くかは、第12章と第15章で詳しく考えるよ。

## 9.7　集約を大きくしすぎない

**初花**: 集約って、大きいほうが守れるルールが増えて安心な気がする。

**マリゴールド**: 守れるルールは増えるけど、代わりに払うものも増えるんだ。案Aと案Bで比べてみよう。

| | 案A（イベント＋予約の一覧） | 案B（残席だけ） |
|---|----------------------|-------------|
| 1回の申込で読み込むもの | そのイベントの予約すべて | 残席の1行 |
| 守れるルール | 定員・二重予約（一覧を見れば分かる） | 定員だけ |
| 予約1件の支払いで変わる範囲 | イベント全体 | 予約1件 |
| 同時の申込（第16章） | イベント全体を取り合う | 残席の1行を取り合う |
| 二重予約のルール | 集約の中で守れる | 集約の外で守る（9.8） |

**初花**: 案Bだと、二重予約は守れないんだ。

**マリゴールド**: 残席は予約の中身を知らないからね。そのルールは、データベースのユニーク制約と、第11章のドメインサービスで守る。**集約に入れるのは、本当に一緒に変えないと崩れるものだけ**。それ以外のルールは、集約の外の別の仕組みで守るほうが、集約を小さく保てるよ。

| 集約を小さくする目安 | うめチケットでは |
|-----------------|---------------|
| 不変条件に要るデータだけを入れる | 定員のチェックに要るのは、定員と予約済みの人数だけ |
| ほかの集約はIDで参照する | 予約は `event_id` で残席を参照する |
| 一覧で守るしかないルールは、データベースの制約やドメインサービスに任せる | 二重予約（R-03） |

## 9.8　データベース制約とドメインルールの役割分担

**初花**: 残席は、どのテーブルに保存するの？ `events` に列を足す？

**マリゴールド**: 第6章を思い出して。残席は予約のコンテキストの言葉で、`events` はイベント管理のテーブルだったよね。予約のコンテキスト用に、`ticket_inventories` テーブルを作ろう。そして、ドメインのルールと同じことを、**データベースにも最後の砦として** 書いておくよ。

今あるイベントの残席は、有効な予約の人数を合計して作ります。

`db/migrate/20261018111741_create_ticket_inventories.rb`:

```ruby
class CreateTicketInventories < ActiveRecord::Migration[8.1]
  def change
    create_table :ticket_inventories do |t|
      t.references :event, null: false, foreign_key: true, index: { unique: true }
      t.integer :capacity, null: false
      t.integer :reserved_count, null: false, default: 0

      t.timestamps
    end
    add_check_constraint :ticket_inventories, "reserved_count BETWEEN 0 AND capacity",
                         name: "reserved_count_within_capacity"

    reversible do |direction|
      direction.up do
        # 今あるイベントの残席を、有効な予約の人数の合計から作る
        execute <<~SQL
          INSERT INTO ticket_inventories (event_id, capacity, reserved_count, created_at, updated_at)
          SELECT events.id,
                 events.capacity,
                 COALESCE(SUM(reservations.quantity) FILTER (WHERE reservations.status IN ('pending', 'confirmed')), 0),
                 NOW(),
                 NOW()
          FROM events
          LEFT JOIN reservations ON reservations.event_id = events.id
          GROUP BY events.id
        SQL
      end
    end
  end
end
```

二重予約（R-03）は、残席の集約では守れないので、予約のテーブルの **部分ユニークインデックス** で守ります。有効な予約（仮予約と予約確定）の中だけで、イベントとメールアドレスの組を重ならないようにします。

| | ドメインのルール | データベースの制約 |
|---|-------------|---------------|
| 場所 | `Inventory#reserve`・ドメインサービス | `CHECK`・ユニークインデックス・外部キー |

| 破られたとき | `Ticketing::Inventory::NotEnoughSeats` | `ActiveRecord::CheckViolation`・`ActiveRecord::RecordNotUnique` |
| 書けるルール | どんなルールでも | 1行の中・1つの表の中で判断できるもの |
| 同時の操作 | 単独では防げない（第16章） | 防げる |

## 振り返り

**初花**: 集約って、大きくまとめるものだと思ってたけど、逆だった。「本当に一緒に変えないと崩れるものだけ」を入れて、小さくするんだね。

**マリゴールド**: そう。残席には予約の中身が入っていないけど、定員のルールを守るにはそれで十分。二重予約は、データベースの制約に任せた。ルールごとに、一番守りやすい場所を選んだんだ。

**初花**: 申し込むときに2つの集約を同じトランザクションで変えるのは、決まりを破ってるみたいで少しドキドキした。

**マリゴールド**: 破ったのではなく、理由があって選んだからね。表に残しておけば、後で変えたくなったときに、何を気にすればいいか分かる。次の章では、集約を読み込んで保存するリポジトリを作ろう。

## 初花のメモ帳

- 集約は「一緒に変えないとルールが崩れるもの」のまとまり。外からは集約ルートのメソッドだけで変える
- 集約に入れるのは不変条件に要るデータだけ。ほかの集約はIDで参照する。中のものは凍らせた写しで渡す
- ドメインのルールは理由を伝え、データベースの制約はどんな経路でも壊れたデータを入れない。両方で守る

## マリゴールドの one more thing

**定員は、`events` と `ticket_inventories` の両方に入っている。**

イベント管理の `events.capacity` は「告知に載せる定員」、予約の `ticket_inventories.capacity` は「席を売る上限」です。今は同じ数字ですが、主催者が定員を変えたとき、2つをどうそろえるかを決める必要があります。予約のコンテキストが下流なので、イベント管理で変わった定員を受け取って、`Inventory#change_capacity` で R-11 を確かめてから反映する、という流れになります。同じ数字を2か所に持つのは、コンテキストを分けた代わりに払う手間です。どこまで分けるかは、第18章の「一つのテーブルを全コンテキストで共有する問題」で、もう一度考えます。
