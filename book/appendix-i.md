# 付録I　発展課題：複数コンテキストへの分割

**初花**: うめチケットは、4つのコンテキストを1つの Rails アプリに入れたままだよね。いつか、別々のアプリに分けることになるの？

**マリゴールド**: 分けなくて済むなら、分けないほうがいいよ。付録Iは、**分けたくなったときに、どこから、どう分けるか** を考える発展課題だね。答えのコードは載せないから、本編の設計を手がかりに考えてみて。

---

## I.1　今の境界を確かめる

うめチケットのコンテキストは、1つのアプリの中で、次の3つで分かれています。

| 分け方 | 今の形 | 章 |
|-------|-------|----|
| 名前 | Ruby のモジュール（`Ticketing`・`Billing`・`Notification`・`Audit`） | 6 |
| 依存の向き | 依存のルールのテスト（`spec/architecture/dependency_rules_spec.rb`） | 19 |
| データ | ほかのコンテキストのテーブルに書き込まない。関連付けは同じコンテキストの中だけ | 18・19 |
| やり取り | 予約 → 決済は `Billing::ChargeReservation`。予約 → 通知・決済の返金は、ドメインイベント | 12・14・18 |

**初花**: 1つのアプリの中でも、もう「分けたとき」と同じやり取りの形になってるんだ。

**マリゴールド**: そこがポイントだよ。この形を **モジュラーモノリス** と呼ぶことがある。デプロイは1つのまま、中の境界を守る。別のアプリに分けるのは、この境界が守られていると確かめてからだね。

---

## I.2　分けたくなる理由と、分けない理由

| 分けたくなる理由 | 分ける前に試すこと |
|--------------|---------------|
| 決済だけ、別のチームが担当することになった | 依存のルールのテストとコードの持ち主（CODEOWNERS など）で、フォルダごとに担当を分ける |
| 発売の瞬間だけ、申込に負荷が集中する | 申込の処理だけを速くする（ロックの範囲、インデックス、ジョブへの切り出し）。Web のプロセスを増やす |
| 決済の変更を、予約と別の日にリリースしたい | 機能フラグで、リリースと公開を分ける |
| 監査のログを、別のデータベースに残したい | Rails の複数データベースで、テーブルの置き場所だけを分ける |

| 分けると増えること | 本書で見た、1つのアプリでの対応 |
|---------------|--------------------------|
| ネットワーク越しの呼び出しの失敗とタイムアウト | うめペイとの間だけで扱った（第15章） |
| 1つのトランザクションで揃えられないこと | 申込の残席と予約は、同じトランザクション（第11章） |
| イベントの配送の保証（Outbox などが必須になる） | コミットのあとの配送と、失敗の記録・積み直し（第12章・第20章） |
| テストとデプロイの手間 | `bin/ci` 1つ（第17章） |

## I.3　課題1：決済のコンテキストを切り出すとしたら

決済（`Billing`）を、別の Rails アプリ（決済のサービス）に分けるとします。次の問いに答えてください。

1. 予約から決済への呼び出し（`Billing::ChargeReservation`）は、何に置き換わりますか
2. キャンセルの返金（`ReservationCanceled` → `Billing::RefundSubscriber`）は、どう届けますか
3. 決済の記録（`payments`）を、予約の画面で表示しているところはありますか
4. 偽物の決済の窓口と契約テストは、どちらのアプリに置きますか

**手がかり**

- 1は、HTTP の API になります。第15章で、うめペイに対して考えたこと（タイムアウト・やり直し・冪等キー）が、そのまま **自分たちの決済のサービス** に対しても必要になります。予約のコンテキストから見ると、決済のサービスも「外部サービス」の1つになり、腐敗防止層（アダプター）を置く場所が増えます
- 2は、プロセスの中の `ActiveSupport::Notifications` では届きません。メッセージのキューなどでイベントを送ることになり、送り損ねないために Outbox パターン（第12章）が必要になります。イベントの中身（`reservation_id`・`refund_amount`）は、もう「公開された言語」なので、変えるときは両方のアプリの合意が要ります
- 3は、`grep -rn "Payment" app/views app/controllers` で探せます。表示に使っているなら、決済のサービスの API から読むか、予約の側に必要な値（支払い済みかどうか）だけを持つようにします
- 4は、契約（決済の窓口が守る約束）を決済のサービスの側が持ち、予約の側のテストでは、その約束を守る偽物を使うのが自然です（第17章）

## I.4　課題2：通知のコンテキストを切り出すとしたら

通知（`Notification`）を分けるのは、決済よりも簡単です。理由を考えてください。

**手がかり**

- 予約から通知へのやり取りは、すでにドメインイベントだけです（コンテキストマップの「公開された言語」。第6章・第12章）
- 通知は、予約に何も返しません。メールが少し遅れて届いても、業務として困りにくいです（第16章の「あとで揃う整合性」）
- 一方で、メールの本文に表示している値（イベントの名前・支払い期限）を、通知の側がどこから読むかは決める必要があります。イベントに必要な値を全部載せるか、通知の側から予約の API を呼ぶかで、イベントの大きさと、やり取りの回数が変わります

## I.5　課題3：分ける順番を決める

4つのコンテキストを、分けやすい順に並べ、理由を書いてください。

**解答の一例**

| 順番 | コンテキスト | 理由 |
|-----|-----------|------|
| 1 | 監査（`Audit`） | イベントを受け取って書くだけ。誰にも何も返さない |
| 2 | 通知（`Notification`） | イベントを受け取ってメールを送るだけ。遅れても困りにくい |
| 3 | 決済（`Billing`） | 予約から同期で呼ばれる。失敗とやり直しの扱いが増える |
| — | 予約（`Ticketing`）とイベント管理 | 申込のたびにイベントの料金・開始時刻・主催者のルールを読む（`SalesInfoReader`）。分けると、申込のたびにネットワーク越しの呼び出しが要る。分けるなら、イベント管理の変更をイベントで受け取り、予約の側に写しを持つ形を考える |

**初花**: 分けやすいのは、**イベントを受け取るだけで、何も返さない** コンテキストなんだね。

**マリゴールド**: そう。逆に、同じトランザクションで揃えたいものや、毎回読まなければならないものは、分けると難しくなる。コンテキストマップの矢印の種類（同期の呼び出しか、イベントか）を見れば、分けやすさの見当がつくよ。本編で境界を守ってきたのは、分けるためというより、**分けなくても困らないようにするため** なんだ。
