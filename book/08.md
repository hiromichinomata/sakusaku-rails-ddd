# 第8章　エンティティと値オブジェクト

**初花**: いよいよ `app/domain` にコードを書くんだね。何から作る？

**マリゴールド**: 一番小さな部品からだよ。DDDのドメインモデルは、大きく分けると **エンティティ** と **値オブジェクト** の組み合わせでできている。この章では予約をエンティティにして、金額・人数・メールアドレスを値オブジェクトにする。

**初花**: 第3章の課題一覧の「金額が整数 × 整数」も、この章で消せる？

**マリゴールド**: 消せるよ。最後に今のRailsアプリから使って、課題一覧に印を付けよう。

## 8.1　エンティティと値オブジェクトの違い

**初花**: エンティティと値オブジェクトって、どう違うの？

**マリゴールド**: 「**何で見分けるか**」が違うんだ。初花の予約は、あとで人数を3人に変えても「初花の予約」のままでしょう。でも、1,500円と1,500円は、どちらの1,500円かを気にしないよね。

| | エンティティ | 値オブジェクト |
|---|------------|-------------|
| 見分け方 | 識別子（ID） | 中身の値 |
| 中身が変わったら | 同じものが変化した（予約の人数が変わった） | 別の値になった（1,500円が3,000円になった） |
| 変更 | 状態が変わる（仮予約 → 予約確定） | 変えない。新しい値を作る |
| うめチケットの例 | 予約・イベント | 金額・人数・メールアドレス・申込者 |

**初花**: 申込者も値オブジェクトなんだ。人なのに。

**マリゴールド**: うめチケットの予約では、申込者を「名前とメールアドレスの組」として扱っているからね。申込者を会員として登録して、名前を変えても同じ人として追いかけたいなら、エンティティになる。**同じ「人」でも、コンテキストの扱い方で決まる** んだ。

## 8.2　識別子と同一性

**初花**: Active Record のモデルは、エンティティなの？

**マリゴールド**: コンソールで確かめてみよう。同じ予約を2回読み込んで比べるよ。

```text
ume-tickets(dev):003> a = Reservation.find(1)
ume-tickets(dev):004> b = Reservation.find(1)
ume-tickets(dev):005> a == b
=> true
ume-tickets(dev):006> a.equal?(b)
=> false
ume-tickets(dev):007> b.quantity = 3
=> 3
ume-tickets(dev):008> a == b
=> true
ume-tickets(dev):009> Reservation.new == Reservation.new
=> false
```

（予約を1件作った最初の2行の出力は省略しています。）

**初花**: `a` と `b` は別のオブジェクト（`equal?` が `false`）なのに、`==` は `true`。人数を変えても `true` のまま。

**マリゴールド**: Active Record の `==` は、**同じクラスで同じIDなら同じ** と判断するんだ。だから Active Record のモデルは、最初からエンティティとして振る舞っている。まだ保存していない（IDのない）レコードどうしは、別のものとして扱われるよ。

| 比べ方 | 意味 | `a`（id: 1）と `b`（id: 1） |
|-------|------|------------------------|
| `equal?` | まったく同じオブジェクトか | `false` |
| `==` | 業務として同じものか | `true`（IDが同じ） |

POROで書くエンティティにも、同じ振る舞いを自分で持たせます。

## 8.3　予約をエンティティとして表現する

**初花**: `Ticketing::Reservation` を作るんだよね。Active Record の `Reservation` と名前がかぶらない？

**マリゴールド**: 名前空間が違うから大丈夫。`Ticketing::Reservation` は予約のコンテキストのドメインモデル、`::Reservation`（`app/models`）はデータベースの行を表す入れ物。第10章で、この2つをリポジトリでつなぐよ。

まず、Railsを読み込まずにドメイン層のスペックを動かすための準備です。

`spec/domain_helper.rb`:

| `bundle exec rspec`（全部） | 最初に読み込まれたほう。どちらでも同じファイルが1回だけ読み込まれる |

## 8.4　金額を値オブジェクトにする

**初花**: 料金は `1500` の整数のままだけど、これで困ることある？

**マリゴールド**: 画面から届く値は文字列だったよね。整数のつもりで扱っていた値が、どこかで文字列や小数になったら、どうなるか試してみよう。

```bash
ruby -e 'p "1500" * 2; p 1500 * 2.5; p -1500 * 2; p 1500 + 3'
```

```text
"15001500"
3750.0
-3000
1503
```

**初花**: `"1500" * 2` が `"15001500"`！ エラーにもならないんだ。

**マリゴールド**: Rubyとしては正しい計算なんだ。文字列の掛け算は繰り返し、小数も負の数も計算できる。`1500 + 3` も、「1,500円に3人を足した」のか「3円を足した」のか、コードからは分からない。**金額に許される計算** を決めた型を作ろう。

| 金額として | 許す | 許さない |
|----------|------|--------|
| 値 | 0以上の整数（円） | 負の数・小数・文字列 |
| 足し算 | 金額 ＋ 金額 | 金額 ＋ 整数 |
| 掛け算 | 金額 × 整数（人数） | 金額 × 小数 |
| 表示 | 「3,000円」 | — |

`spec/domain/money_spec.rb`:

```ruby
require "domain_helper"

RSpec.describe Money do
  describe "作るとき" do
    it "0以上の整数（円）で作れる" do
      expect(Money.new(1500).yen).to eq(1500)
      expect(Money.new(0)).to be_zero
    end

    it "負の数は金額にならない" do
      expect { Money.new(-100) }.to raise_error(ArgumentError, "金額は0以上の整数（円）で指定してください: -100")
    end

    it "文字列や小数は金額にならない" do
      expect { Money.new("1500") }.to raise_error(ArgumentError)
      expect { Money.new(1500.5) }.to raise_error(ArgumentError)
    end
  end

  describe "計算" do
    it "足し算は金額どうしでする" do
      expect(Money.new(1500) + Money.new(500)).to eq(Money.new(2000))
    end

    it "掛け算は整数とする" do
      expect(Money.new(1500) * 2).to eq(Money.new(3000))
      expect { Money.new(1500) * 2.5 }.to raise_error(ArgumentError)
    end

    it "大きさを比べられる" do
      expect(Money.new(1500)).to be > Money.new(1000)
    end
  end

  it "3桁区切りと「円」を付けて表示する" do
    expect(Money.new(1_234_567).to_s).to eq("1,234,567円")
  end
end
```

金額は予約のコンテキストだけでなく、決済でも使います。どのコンテキストでも同じ意味で使う値なので、`app/domain/` の直下に置きます。

`app/domain/money.rb`:

```ruby
# 金額（円）。0以上の整数だけを持つ値オブジェクト
class Money
  include Comparable

  attr_reader :yen

  def initialize(yen)
    unless yen.is_a?(Integer) && yen >= 0
      raise ArgumentError, "金額は0以上の整数（円）で指定してください: #{yen.inspect}"
    end

    @yen = yen
    freeze
  end

  def +(other)
    Money.new(yen + other.yen)
  end

  def *(times)
    raise ArgumentError, "金額に掛けられるのは整数だけです: #{times.inspect}" unless times.is_a?(Integer)

    Money.new(yen * times)
  end

  def <=>(other)
    yen <=> other.yen if other.is_a?(Money)
  end

  def ==(other)
    other.is_a?(Money) && yen == other.yen
  end
  alias eql? ==

  def hash
    [ Money, yen ].hash
  end

  def zero?
    yen.zero?
  end

  def to_s
    "#{yen.to_s.reverse.scan(/\d{1,3}/).join(',').reverse}円"
  end

  def inspect
    "#<Money #{self}>"
  end
end
```

    文字列や小数は金額にならない
  計算

## 8.5　メールアドレスや予約人数を型で表現する

**初花**: 人数も、1〜4人の範囲をバリデーションで守ってたよね。それも型にする？

**マリゴールド**: そう。人数・メールアドレス・申込者を値オブジェクトにしよう。Rubyの `Data.define` を使うと、`==` や `hash` を自分で書かなくても、中身で比べる値オブジェクトを作れるよ。

| 値オブジェクト | 置き場所 | 持つ値 | 決まり |
|-------------|---------|-------|------|
| `EmailAddress` | `app/domain/`（共有） | 文字列 | 前後の空白を取り、小文字にそろえる。形が正しいこと |
| `Ticketing::ReservationCount` | `app/domain/ticketing/` | 整数 | 1〜4人 |
| `Ticketing::Applicant` | `app/domain/ticketing/` | 名前・メールアドレス | 名前が空でないこと |

`spec/domain/email_address_spec.rb`:

```ruby
require "domain_helper"

RSpec.describe EmailAddress do
  it "前後の空白を取り、小文字にそろえる" do
    expect(EmailAddress.new(" Hatsuka@Example.COM ").value).to eq("hatsuka@example.com")
  end

  it "そろえたあとの値が同じなら、同じメールアドレス" do
    expect(EmailAddress.new("Hatsuka@example.com")).to eq(EmailAddress.new("hatsuka@example.com"))
  end

  it "形が正しくなければ作れない" do
    expect { EmailAddress.new("hatsuka.example.com") }
      .to raise_error(ArgumentError, "メールアドレスの形が正しくありません: \"hatsuka.example.com\"")
  end
end
```

`app/domain/email_address.rb`:

```ruby
require "uri"

# メールアドレス。前後の空白を取り、小文字にそろえて持つ値オブジェクト
class EmailAddress < Data.define(:value)
  def initialize(value:)
    normalized = value.to_s.strip.downcase
    unless normalized.match?(URI::MailTo::EMAIL_REGEXP)
      raise ArgumentError, "メールアドレスの形が正しくありません: #{value.inspect}"
    end

    super(value: normalized)
  end

  def to_s
    value
  end
end
```

**初花**: 小文字にそろえるのは、二重予約のチェックのため？

**マリゴールド**: そう。今のアプリだと、`Hatsuka@example.com` と `hatsuka@example.com` は別のアドレスとして予約できてしまう。メールアドレスの「同じ」を値オブジェクトで決めておけば、二重予約のルールが正しく働くようになるよ。

`spec/domain/ticketing/reservation_count_spec.rb`:

```ruby

RSpec.describe Ticketing::ReservationCount do

  end

  it "0人や5人では作れない" do
    expect { described_class.new(0) }.to raise_error(ArgumentError, "人数は1〜4人で指定してください: 0")
    expect { described_class.new(5) }.to raise_error(ArgumentError, "人数は1〜4人で指定してください: 5")
  end

  it "整数でなければ作れない" do
    expect { described_class.new("2") }.to raise_error(ArgumentError)
  end
end
```

`app/domain/ticketing/reservation_count.rb`:

```ruby
module Ticketing
  # 1件の予約の人数（1〜4人）
  class ReservationCount < Data.define(:value)
    MIN = 1
    MAX = 4

    def initialize(value:)
      unless value.is_a?(Integer) && value.between?(MIN, MAX)
        raise ArgumentError, "人数は#{MIN}〜#{MAX}人で指定してください: #{value.inspect}"
      end

      super
    end

    def to_i
      value
    end

    def to_s
      "#{value}人"
    end
  end
end
```

⚠️ `ReservationCount = Data.define(:value) do ... end` のようにブロックの中で `MAX = 4` と書くと、定数は `Data` のクラスではなく外側の `Ticketing` に定義されてしまいます。本書では `class ReservationCount < Data.define(:value)` の形で書きます。

**初花**: エンティティの中に、もう「1〜4人」のチェックがない。でも、5人の予約は作れない。

**マリゴールド**: `ReservationCount` を作れた時点で、1〜4人であることが **保証されている** からだよ。エンティティは「人数は `ReservationCount` で受け取る」と決めるだけでいい。ルールが、それを一番よく知っている値オブジェクトに集まったんだ。

## 8.6　不変条件をコンストラクタで守る

**初花**: 値オブジェクトは、作るときにチェックするんだね。作ったあとに値を書き換えたらどうなるの？

**マリゴールド**: 試してみよう。値オブジェクトは「作るときに正しければ、ずっと正しい」ようにしてあるんだ。ドメイン層のファイルだけを読み込んで、Railsなしで動かすよ。

アプリのフォルダで、次のスクリプトを `invariants.rb` として保存して実行します（試したら消します）。

```ruby
require_relative "app/domain/money"
require_relative "app/domain/ticketing/reservation_count"

price = Money.new(1500)
p price
p price.frozen?

begin
  price.instance_variable_set(:@yen, -1)
rescue => e
  puts "#{e.class}: #{e.message}"
end

count = Ticketing::ReservationCount.new(2)
p count
p count.with(value: 3)

begin
  count.with(value: 5)
rescue => e
  puts "#{e.class}: #{e.message}"
end

begin
  Ticketing::ReservationCount.new(0)
rescue => e
  puts "#{e.class}: #{e.message}"
end
```

```bash
ruby invariants.rb
```

```text
#<Money 1,500円>
true
FrozenError: can't modify frozen Money: #<Money 1,500円>
#<data Ticketing::ReservationCount value=2>
#<data Ticketing::ReservationCount value=3>
ArgumentError: 人数は1〜4人で指定してください: 5
ArgumentError: 人数は1〜4人で指定してください: 0
```

**初花**: `freeze` してあるから、無理やり書き換えようとしても `FrozenError`。`with` で別の値を作ろうとしたときも、ちゃんと4人までのチェックが働いてる。

**マリゴールド**: `Data` の `with` は、新しい値を作るときに `initialize` を通るからね。**作る道が一つしかなくて、その道でチェックしている**。だから、どこから作っても1〜4人の外の人数は存在できない。これを **不変条件** と呼ぶよ。

| 守り方 | 第3章（Active Record） | この章（値オブジェクト） |
|-------|---------------------|---------------------|
| いつチェックするか | `save` のとき（`valid?`） | 作るとき（`new`） |
| すり抜けられるか | `save(validate: false)`・`update_column` で飛ばせる | 作れないので、正しくない値は存在しない |
| エラーの形 | `errors` にメッセージが入る | 例外（`ArgumentError`） |
| 向いている使い方 | 利用者の入力を確かめて、理由を返す | 業務のルールとして、ありえない値を作らせない |

⚠️ 値オブジェクトの例外は「プログラムの誤り」を止めるためのものです。利用者の入力の誤りを画面に表示するのは、引き続きフォームのバリデーションの役目です。入力の検証と業務のルールの分け方は第13章で扱います。

## 8.7　`==` と等価性を実装する

**初花**: `Money` には `==` のほかに、`eql?` と `hash` も書いたよね。`==` だけじゃ足りないの？

**マリゴールド**: `==` だけを書いたクラスと比べてみよう。`uniq` やハッシュのキーで違いが出るよ。

次のスクリプトを `equality_demo.rb` として保存して実行します（試したら消します）。

```ruby
require_relative "app/domain/money"

# == だけを定義した金額
class OnlyEqualMoney
  attr_reader :yen

  def initialize(yen)
    @yen = yen
  end

  def ==(other)
    other.is_a?(OnlyEqualMoney) && yen == other.yen
  end
end

p OnlyEqualMoney.new(1500) == OnlyEqualMoney.new(1500)
p [OnlyEqualMoney.new(1500), OnlyEqualMoney.new(1500)].uniq.size
p({ OnlyEqualMoney.new(1500) => "大人" }[OnlyEqualMoney.new(1500)])

p Money.new(1500) == Money.new(1500)
p [Money.new(1500), Money.new(1500)].uniq.size
p({ Money.new(1500) => "大人" }[Money.new(1500)])
```

```text
true
2
nil
true
1
"大人"
```

**初花**: `==` だけだと、`uniq` しても2つのまま、ハッシュのキーで探しても見つからない！

**マリゴールド**: `uniq` やハッシュは、`==` ではなく `hash` と `eql?` で同じかどうかを判断するからね。値オブジェクトを「中身で比べる」なら、3つをそろえて書く必要があるんだ。

| メソッド | 使われる場所 | `Money` での中身 |
|---------|------------|----------------|
| `==` | `a == b`、RSpec の `eq` | 金額が同じなら `true` |
| `eql?` | ハッシュのキーの比較、`uniq` | `==` と同じ（`alias`） |
| `hash` | ハッシュのキー、`uniq`、`Set` | `[Money, yen].hash`（同じ金額なら同じ数） |

`Data.define` で作った値オブジェクトは、この3つを最初から持っています。エンティティは、IDで比べるように自分で書きました。

```ruby
Dir["app/domain/**/*.rb"].sort.each { |file| require_relative file }

p [EmailAddress.new("hatsuka@example.com"), EmailAddress.new("Hatsuka@Example.com")].uniq.size

applicant = Ticketing::Applicant.new(name: "初花", email: "hatsuka@example.com")
first = Ticketing::Reservation.new(id: 1, event_id: 1, applicant: applicant,
                                   count: Ticketing::ReservationCount.new(2), price: Money.new(1500))
changed = Ticketing::Reservation.new(id: 1, event_id: 1, applicant: applicant,
                                     count: Ticketing::ReservationCount.new(3), price: Money.new(1500))
p [first, changed].uniq.size
```

```text
1
1
```

| | 等しいとき | 書き方 |
|---|----------|------|
| 値オブジェクト（`Money`） | 中身（金額）が同じ | `==`・`eql?`・`hash` を自分で書く |
| 値オブジェクト（`Data.define`） | すべての属性が同じ | 自動で用意される |
| エンティティ（`Ticketing::Reservation`） | IDが同じ | `==`・`eql?`・`hash` をIDで書く |

## ハンズオン 8-A — 値オブジェクトをRailsのアプリから使う

この章の成果物は「`Money`、`ReservationCount` などのドメインモデル」です。作った値オブジェクトを、今のRailsのアプリから使ってみます。ドメイン層はRailsを知りませんが、Railsの側からドメイン層を使うのは自由です。

人数の上限は、Active Record のモデルにも `MAX_QUANTITY = 4` として書いていました。これを `ReservationCount::MAX` にそろえ、支払い金額を `Money` で返すようにします。

`app/models/reservation.rb`（抜粋）:

```ruby
class Reservation < ApplicationRecord
  belongs_to :event
...
  validates :quantity, numericality: { only_integer: true, greater_than: 0, less_than_or_equal_to: Ticketing::ReservationCount::MAX }
...
  def total_price
    Money.new(event.price) * quantity
  end
```

## 振り返り

**初花**: 値オブジェクトって、ただの小さなクラスだと思ってた。でも「作れた時点で正しい」っていうのは強いね。エンティティから人数のチェックが消えた。

**マリゴールド**: ルールを持つ場所が、ルールの中身に一番近い型に移ったからね。`Money` も `ReservationCount` も、ほかのクラスに「正しいかどうか」を気にさせない。

**初花**: でも、定員のルールはまだ `Reservation` のバリデーションにあるよね。残りの席は、1つの予約だけ見ても分からない。

**マリゴールド**: そこが次の章の主役だよ。予約が何件もあって、その合計が定員を超えないこと。一つのオブジェクトの中に収まらないルールを守るために、**集約** を作ろう。

## 初花のメモ帳

- エンティティはIDで、値オブジェクトは中身で見分ける。同じ「人」でもコンテキストの扱い方で決まる
- 値オブジェクトは作るときにチェックして、作ったら変えない（`freeze`・`Data`）。正しくない値は存在できない
- 中身で比べるなら `==`・`eql?`・`hash` をそろえる。`Data.define` なら最初からそろっている

## マリゴールドの one more thing

**Active Record にも、値オブジェクトを属性として扱う仕組みがある。**

Rails には、列の値を自分のクラスに変換して読み書きする **Attributes API**（`attribute :price, MoneyType.new`）があります。`ActiveRecord::Type::Value` を継承した型クラスを作ると、`event.price` が整数ではなく `Money` を返すようにできます。本書のコアドメインでは、リポジトリで Active Record とドメインのオブジェクトを変換するので使いませんが、支援サブドメインのように Active Record をそのままモデルとして使う場所では便利です。第19章の「Active Record モデルに残してよいロジック」で、この使い分けをもう一度考えます。
