# 第19章　Railsらしさを損なわない実践的なアーキテクチャ

**初花**: 層を分けて、コンテキストを分けて、だいぶ「Railsっぽくない」フォルダが増えたね。`app/domain`・`app/usecases`・`app/infrastructure`。

**マリゴールド**: そうだね。でも、イベント管理は今も普通のRailsのMVCだし、コントローラ・ビュー・マイグレーション・ジョブも、Railsの作法のままだよ。この章では、**どこまでRailsらしさを残し、どこで線を引くか** をもう一度整理しよう。

**初花**: 線を引いたあと、それを守り続けるのも大変そう。

**マリゴールド**: だから、線をテストで守る方法も作るよ。それと、Railsのアプリでよく問題になる N+1 クエリも、うめチケットで起こして直そう。

---

## 19.1　すべてを純粋なRubyオブジェクトにする必要はあるか

**初花**: DDDなら、全部のモデルをPOROにしたほうがきれいじゃない？

**マリゴールド**: 第7章で「コアドメインだけPOROにする」と決めたよね。今のうめチケットで、どこがPOROで、どこが Active Record かを並べてみよう。

| | PORO（`app/domain`） | Active Record（`app/models`） |
|---|-------------------|---------------------------|
| 予約（コア） | `Ticketing::Reservation`・`Inventory`・値オブジェクト | `Reservation`・`TicketInventory`（保存の入れ物） |
| イベント管理（支援） | — | `Event`（モデルそのもの） |
| 決済（汎用） | — | `Payment`（モデルそのもの） |
| 共有の値 | `Money`・`EmailAddress` | — |

**初花**: POROにしたのは、予約のルールのところだけなんだ。

**マリゴールド**: POROにすると、リポジトリでの変換の手間が増える。その手間に見合うのは、ルールが多くて、よく変わって、速いテストで守りたい場所だけなんだ。

| POROにすると得をする | Active Record のままで十分 |
|-------------------|----------------------|
| ルールが多い（残席・状態遷移・期限） | 入力して保存するだけ（イベントの登録） |
| ルールがよく変わる（第21章の主催者ごとのルール） | 外部サービスの記録を残すだけ（決済の記録） |
| テーブルの形とモデルの形が違う（予約の料金・申込者） | テーブルの形がそのままモデルの形 |
| Railsなしで速くテストしたい | データベースを含めてテストすればよい |

## 19.2　Active Recordモデルに残してよいロジック

**初花**: 予約の Active Record（`Reservation`）には、`total_price` と `payment_deadline` が残ってるよね。これはいいの？

**マリゴールド**: どちらも **画面やメールで表示するための読み取り** で、中身はドメインの決まり（`Money`・`Ticketing::Reservation.payment_deadline_for`）を呼んでいるだけだよね。ルールを持っているのはドメインで、Active Record は表示の都合で取り次いでいる。それなら問題ないよ。

| Active Record に残してよい | Active Record に書かない |
|------------------------|---------------------|
| スコープ（`Reservation.active`・`pending`） | 状態を変える業務の判断（第14章） |
| 表示のための読み取り（ドメインの決まりを呼ぶ） | 外への副作用のコールバック（第12章・第18章） |
| 支援・汎用のコンテキストのバリデーション（`Event` の入力のチェック） | コアドメインの業務のルール（定員・二重予約） |
| 関連付け（同じコンテキストの中だけ） | ほかのコンテキストへの関連付け（第18章） |

**初花**: イベント管理の `Event` は、今もバリデーションを持ってるね。定員の変更のルール（R-11）も。

**マリゴールド**: `Event` は支援サブドメインのモデルそのものだからね。ただ R-11 は、第9章で残席の集約（`Inventory#change_capacity`）にも書いた。主催者が定員を変える画面を作るときに、どちらで守るかを決めよう。第21章で扱うよ。

## 19.4　Rails Engineやモジュラーモノリスの活用

**初花**: コンテキストごとに、もっとはっきり分けることはできないの？ フォルダだと、うっかり中身を呼べちゃう。

**マリゴールド**: 1つのRailsアプリのまま、コンテキストを **部品として分ける** 方法があるよ。アプリを1つのまま保ちつつ、中をはっきり分けた形を **モジュラーモノリス** と呼ぶんだ。

| 分け方 | やり方 | 線の強さ | 手間 |
|-------|------|--------|-----|
| 名前空間とフォルダ（本書） | `Ticketing::`・`Billing::` で分ける | 弱い（テストで守る。19.5） | 少ない |
| Rails Engine | コンテキストごとに `engines/billing` のような小さなRailsを作り、アプリから読み込む | 中くらい（Gemfile・依存の宣言で分かれる） | 中くらい |
| パッケージの境界を調べる gem | フォルダごとに「公開するもの」「依存してよいもの」を宣言して、違反を調べる | 中くらい | 少なめ |
| 別のアプリ（マイクロサービス） | コンテキストごとに、別のRailsアプリ・別のデータベースにする | 強い | 大きい（付録I） |

**初花**: うめチケットは、名前空間とフォルダのまま？

**マリゴールド**: 今の大きさなら十分だよ。大事なのは、どの分け方でも **コンテキストマップ（第6章）が先にある** こと。線を引く場所が決まっていれば、あとから Engine や別のアプリに分けるときも、その線に沿って切り出せる。

## 19.5　依存関係のルールをテストする

**初花**: フォルダの線を、テストで守るんだよね。どうやって？

**マリゴールド**: ソースコードの文字を調べるテストにするよ。第13章や第18章で、`grep` で確かめてきたことを、毎回流れるテストにするんだ。守るルールは3つ。

| ルール | 理由 |
|-------|------|
| ドメイン層は、Rails・Active Record・データベースのモデルを知らない | 第7章。Railsなしで動き、速くテストできるように |
| 予約のコンテキストは、決済の入口（`Billing::ChargeReservation`）だけを使う | 第18章。決済の中身が変わっても、予約に影響しないように |
| 決済と通知のコンテキストは、予約のドメインイベントだけを知っている | 第12章・第14章。予約の中身に依存しないように |

`spec/architecture/dependency_rules_spec.rb`:

```ruby
require "spec_helper"

# 層とコンテキストの依存のルール（docs/architecture.md）を、ソースコードの文字を調べて守る
RSpec.describe "依存のルール" do
  ROOT = File.expand_path("../..", __dir__)

  def files(*patterns)
    patterns.flat_map { |pattern| Dir[File.join(ROOT, pattern)] }.sort
  end

  # パターンに当てはまる行を「ファイル:行番号: 中身」の一覧にする。許すものは、行から取り除いてから調べる
  def violations(paths, pattern, allowed: [])
    paths.flat_map do |path|
      File.readlines(path).each_with_index.filter_map do |line, index|
        next if line.strip.start_with?("#")
        next unless allowed.reduce(line) { |rest, allow| rest.gsub(allow, "") }.match?(pattern)

        "#{path.delete_prefix("#{ROOT}/")}:#{index + 1}: #{line.strip}"
      end
    end
  end

  it "ドメイン層は、Rails・Active Record・データベースのモデルを知らない" do
    pattern = /\b(Rails|ActiveRecord|ActiveSupport|ApplicationRecord)\b|(^|[^:\w])(Event|Payment|TicketInventory|IdempotencyKey)\.|(^|[^\w])::Reservation\b/

    expect(violations(files("app/domain/**/*.rb"), pattern)).to eq([])
  end

  it "予約のコンテキストは、決済の入口（Billing::ChargeReservation）だけを使う" do
    ticketing = files("app/domain/ticketing/**/*.rb", "app/usecases/ticketing/**/*.rb", "app/infrastructure/ticketing/**/*.rb")

    expect(violations(ticketing, /\bBilling(::|\.)/, allowed: [ /Billing::ChargeReservation\b/ ])).to eq([])
  end

  it "決済と通知のコンテキストは、予約のドメインイベントだけを知っている" do
    others = files("app/{usecases,infrastructure,jobs}/{billing,notification}/**/*.rb", "app/infrastructure/billing.rb")
    events = /Ticketing::Reservation(Created|Confirmed|Canceled)\b/

    expect(violations(others, /\bTicketing::/, allowed: [ events ])).to eq([])
  end
end
```

## 19.6　パフォーマンスとN+1クエリ

**初花**: N+1クエリって、Railsでよく聞くやつだよね。うめチケットにもある？

**マリゴールド**: 作ってみよう。イベントの一覧に「残り◯席」を出したくなったとする。

`app/views/events/index.html.erb`（抜粋）:

```erb
      （<%= event.starts_at.strftime("%Y年%-m月%-d日 %H:%M") %>・残り <%= event.remaining_seats %>席）
```

SQLの数を数える道具を用意して、イベントが増えても一覧のSQLが増えないことをテストにします。

`spec/support/query_counter.rb`:

```ruby
# ブロックの中で流れた SQL の数を数える（トランザクションの BEGIN・COMMIT などは数えない）
def count_queries(&block)
  count = 0
  counter = lambda do |*, payload|
    count += 1 unless payload[:name].in?(%w[SCHEMA TRANSACTION]) || payload[:sql].match?(/\A\s*(BEGIN|COMMIT|ROLLBACK|SAVEPOINT|RELEASE)/)
  end
  ActiveSupport::Notifications.subscribed(counter, "sql.active_record", &block)
  count
end
```

`spec/requests/events_spec.rb`（抜粋）:

```ruby
  describe "GET /events の残りの席" do
    it "イベントごとの残りの席を表示する" do
      create(:event, title: "梅酒づくりワークショップ", capacity: 20).ticket_inventory.update!(reserved_count: 5)

      get events_path

      expect(response.body).to include("残り 15席")
    end

    it "イベントが増えても、一覧の表示で流れる SQL の数は変わらない" do
      create_list(:event, 2)
      with_two_events = count_queries { get events_path }

      create_list(:event, 3)
      with_five_events = count_queries { get events_path }

      expect(with_five_events).to eq(with_two_events)
    end
  end
```

```text
  1) イベント GET /events の残りの席 イベントが増えても、一覧の表示で流れる SQL の数は変わらない
     Failure/Error: expect(with_five_events).to eq(with_two_events)

       expected: 3
            got: 6

       (compared using ==)
```

**初花**: イベントが2件なら3本、5件なら6本。イベントが1件増えるたびに、SQLが1本増えてる。

**マリゴールド**: 開発環境のログで、イベント一覧を開いたときのSQLを見てみよう。

```text
  Event Load (2.4ms)  SELECT "events".* FROM "events" ORDER BY "events"."starts_at" ASC
  TicketInventory Load (1.4ms)  SELECT "ticket_inventories".* FROM "ticket_inventories" WHERE "ticket_inventories"."event_id" = 1 LIMIT 1
  TicketInventory Load (1.2ms)  SELECT "ticket_inventories".* FROM "ticket_inventories" WHERE "ticket_inventories"."event_id" = 2 LIMIT 1
  TicketInventory Load (0.9ms)  SELECT "ticket_inventories".* FROM "ticket_inventories" WHERE "ticket_inventories"."event_id" = 3 LIMIT 1
```

**初花**: イベントを読む1本と、イベントごとの残席を読む3本。「1 + N」本だから N+1 なんだ。

**マリゴールド**: `remaining_seats` が、イベントごとに `ticket_inventory` を読んでいるからだね。最初にまとめて読み込んでおくよう、`includes` を使おう。

`app/controllers/events_controller.rb`（抜粋）:

```ruby
  def index
    @events = Event.includes(:ticket_inventory).order(:starts_at)
  end
```

```text
  Event Load (1.4ms)  SELECT "events".* FROM "events" ORDER BY "events"."starts_at" ASC
  TicketInventory Load (1.4ms)  SELECT "ticket_inventories".* FROM "ticket_inventories" WHERE "ticket_inventories"."event_id" IN (1, 2, 3)
Completed 200 OK in 25ms (Views: 9.9ms | ActiveRecord: 12.7ms (2 queries, 0 cached) | GC: 0.0ms)
```

```text
9 examples, 0 failures
```

**初花**: 残席の読み込みが、`IN (1, 2, 3)` の1本にまとまった。

| N+1 を防ぐ方法 | 使いどころ |
|------------|---------|
| `includes`（この節） | 関連付けをまとめて読む。一番よく使う |
| 一覧の専用の読み込み（第10章の one more thing の CQRS） | 画面に合わせて、結合した形で読む |
| SQLの数のテスト（この節） | N+1 が戻ってこないように守る |
| `strict_loading` | 読み込んでいない関連付けを触ったら、エラーにする |

⚠️ 一覧の画面は、Active Record で直接読んでいます（第10章）。予約のリポジトリを通して残席を1件ずつ組み立てると、同じ N+1 が起きます。**変えるためのモデル（集約）と、読むためのモデル（画面）を分ける** と決めたのは、このためでもあります。

## 19.7　チームで設計を維持するためのルール

**初花**: これだけ決めごとが増えると、新しく入った人は大変そう。

**マリゴールド**: 決めたことは、全部ファイルに残してきたよね。どこに何があるかを並べてみよう。

| 決めたこと | ファイル | 決めた章 |
|---------|--------|-------|
| 業務の言葉 | `docs/domain/glossary.md` | 第4章 |
| 業務のルール（R-01〜R-12） | `docs/domain/rules.md` | 第4章・第10章 |
| サブドメインの分類 | `docs/domain/subdomains.md` | 第5章 |
| コンテキストのつながり | `docs/domain/context_map.md` | 第6章 |
| 層・フォルダ・やらないこと | `docs/architecture.md` | 第7章・第13章・第18章 |
| テストの方針 | `docs/testing.md` | 第17章 |
| 直してきた課題 | `docs/issues_before_ddd.md` | 第3章〜 |
| 依存のルール | `spec/architecture/dependency_rules_spec.rb` | この章 |

**初花**: 文書はあっても、プルリクエストのときに見てもらえるかな。

**マリゴールド**: プルリクエストを作るたびに、確認の項目が出るようにしておこう。GitHub は、`.github/pull_request_template.md` の中身を、プルリクエストの説明に最初から入れてくれるよ。

`.github/pull_request_template.md`:

```markdown
## 変えたこと

<!-- 何を、なぜ変えたか。業務の言葉で書く -->

## 設計の確認

- [ ] 新しく出てきた業務の言葉は、用語集（`docs/domain/glossary.md`）にある。なければ用語集も直した
- [ ] 業務のルールは、ドメイン層（`app/domain`）にある。コントローラ・ビュー・ジョブに判断を書いていない
- [ ] ルールを足した・変えたなら、`docs/domain/rules.md` と、ID を書いたテストを直した
- [ ] ほかのコンテキストのテーブルに書き込んでいない（`docs/architecture.md` の 10〜11）
- [ ] 外部サービスの呼び出しは、トランザクションの外にあり、やり直しても二重にならない
- [ ] Active Record のコールバックに、業務の判断や外への副作用を書いていない
- [ ] `bin/ci` が通る
```

| 守り方 | 守れるもの | 守れないもの |
|-------|---------|----------|
| テスト（`spec/architecture`・`bin/ci`） | 依存の向き・SQLの数 | 名前が業務の言葉かどうか |
| プルリクエストのテンプレート | 人が気づくきっかけ | 忙しいと読み飛ばされる |
| 文書（`docs/`） | なぜそう決めたか | 古くなる（コードと一緒に直す） |

**初花**: 機械で守れるものはテストで、人の判断が要るものはテンプレートで、なんだね。

## 振り返り

**初花**: Railsらしさを捨てたわけじゃなかった。コントローラ・ビュー・マイグレーション・ジョブ・`includes` は、全部Railsのまま使ってる。

**マリゴールド**: DDDの層を足したのは、ルールの置き場所のためだけ。それ以外はRailsに任せる。その線を、テストとテンプレートで守るんだ。

**初花**: ルールのテストにも抜けがあったのは、ちょっと笑っちゃった。わざと破ってみないと分からないね。

**マリゴールド**: 次の章では、完成に近づいたうめチケットを **本番で動かす** ことを考えるよ。ログ・監視・失敗したジョブの調べ方・データのずれの見つけ方。課題一覧に残っている最後の1つも、そこで片付けよう。

## 初花のメモ帳

- PORO にするのは、ルールが多く、よく変わり、速いテストで守りたい場所だけ。それ以外は Active Record のまま
- 依存のルールはテストにする。どんなテストも、わざと破って本当に気づくかを確かめる
- N+1 は `includes` で防ぎ、SQLの数のテストで戻ってこないように守る。変えるモデルと読むモデルを分ける

## マリゴールドの one more thing

**アーキテクチャの決めごとは、少ないほど守られる。**

この本では、`docs/architecture.md` に12の決めごとを書きました。決めごとが増えるほど、新しい人が覚えるのは大変になり、例外も増えていきます。決めごとを足したくなったら、まず「テストで機械的に守れるか」を考えてください。守れるならテストにして、文書からは「なぜそうしたか」だけを残します。テストにできない決めごとは、本当に必要か、ほかの決めごとと重なっていないかを見直します。半年に一度、`docs/architecture.md` を読み返して、もう守らなくてよい決めごとを消す日を作るのもおすすめです。
