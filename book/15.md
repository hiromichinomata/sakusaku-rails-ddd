# 第15章　外部サービス・バックグラウンドジョブとの連携

**初花**: 返金は決済のコンテキストに任せられたけど、支払いのほうは、まだ `PaymentsController` が `Billing::PaymentGateway.charge` を直接呼んでるよね。

**マリゴールド**: そう。それに今の `PaymentGateway` は、手元で動く偽物だけ。本番で本物の決済サービスにつなぐには、通信の失敗やタイムアウトとも付き合う必要がある。

**初花**: タイムアウトって、「お金は受け取れたのか、受け取れなかったのか分からない」ってことだよね。ちょっと怖い。

**マリゴールド**: それがこの章の一番大事なところだよ。決済サービスとのつなぎ方を **アダプター** にして、失敗したらやり直せるようにする。そして、やり直しても2回受け取らないための **冪等性** を作ろう。

---

## 15.1　外部APIをドメイン層から切り離す

**初花**: 今の作りの、何が困るの？

**マリゴールド**: 呼び出している場所と、呼び出し方を並べてみよう。

| 今の作り | 困ること |
|---------|--------|
| `Billing::PaymentGateway.charge(amount: 3000, ...)` のクラスメソッドを直接呼ぶ | 本物と偽物を差し替えられない。テストではクラスそのものをスタブにするしかない |
| 金額を整数で渡している | うめペイの「円の整数」という都合が、呼ぶ側に漏れている |
| 失敗は `CardDeclined` だけ | タイムアウトや障害を考えていない |
| 同じ支払いを2回頼んだら、2回受け取る | ボタンの連打や、通信のやり直しで二重に請求される |

**初花**: 第6章のコンテキストマップで、決済とうめペイの間に「腐敗防止層」って書いてたよね。

**マリゴールド**: そう。うめペイの言葉（`charge`・`source`・HTTPのステータス）を、決済のコンテキストの外に出さないための層だね。この章で、それを本当に作るよ。アダプターが守る約束を、先に決めておこう。

| メソッド | 受け取る | 返す | 投げる |
|---------|---------|-----|-------|
| `charge(amount:, token:, idempotency_key:)` | `Money`・カードのトークン・冪等キー | 支払いID（文字列） | `Billing::CardDeclined`・`Billing::GatewayUnavailable` |
| `refund(charge_id:, amount:, idempotency_key:)` | 支払いID・`Money`・冪等キー | 返金ID（文字列） | `Billing::GatewayUnavailable` |

```text
予約のコンテキスト                 決済のコンテキスト                         外部
───────────────                 ───────────────────                      ────
PayForReservation ── charge ──▶ Billing.gateway（アダプター）
RefundPaymentJob  ── refund ──▶   ├ FakePaymentGateway（開発・テスト）
                                  └ UmepayGateway（本番）── HTTP ──▶ うめペイの API
```

開発とテストで使う偽物です。第3章からの `PaymentGateway` を作り直して、同じ冪等キーの依頼には同じ結果を返すようにします（冪等キーは 15.5 で説明します）。

`app/infrastructure/billing/fake_payment_gateway.rb`:

```ruby
module Billing
  # 開発とテストで使う、手元で動く決済の窓口。本書用の架空の決済サービス「うめペイ」の代わり。
  # tok_visa は成功、tok_declined はカードが使えない。同じ冪等キーの依頼には、同じ結果を返す。
  class FakePaymentGateway
    @results = {}

    class << self
      attr_reader :results

      def reset!
        results.clear
      end
    end

    def charge(amount:, token:, idempotency_key:)
      remember(idempotency_key) do
        raise CardDeclined, "カードが利用できませんでした" if token == "tok_declined"

        Rails.logger.info("[PaymentGateway] charge amount=#{amount.yen}")
        "ch_#{SecureRandom.hex(8)}"
      end
    end

    def refund(charge_id:, amount:, idempotency_key:)
      remember(idempotency_key) do
        Rails.logger.info("[PaymentGateway] refund charge_id=#{charge_id} amount=#{amount.yen}")
        "re_#{SecureRandom.hex(8)}"
      end
    end

    private

    def remember(idempotency_key)
      self.class.results[idempotency_key] ||= yield
    end
  end
end
```

本番で使う、うめペイのHTTP APIのアダプターです（うめペイは本書用の架空のサービスで、`api.umepay.example` は実在しません）。

`app/infrastructure/billing/umepay_gateway.rb`:

```ruby
require "net/http"

module Billing
  # 本番で使う、うめペイの HTTP API の窓口（本書用の架空の API）。
  # うめペイの言葉（charge・source・HTTP のステータス）は、このクラスの外に出さない。
  class UmepayGateway
    BASE_URL = URI("https://api.umepay.example")

    def initialize(api_key:, open_timeout: 2, read_timeout: 5)
      @api_key = api_key
      @open_timeout = open_timeout
      @read_timeout = read_timeout
    end

    def charge(amount:, token:, idempotency_key:)
      post("/v1/charges", { amount: amount.yen, currency: "jpy", source: token }, idempotency_key).fetch("id")
    end

    def refund(charge_id:, amount:, idempotency_key:)
      post("/v1/refunds", { charge: charge_id, amount: amount.yen }, idempotency_key).fetch("id")
    end

    private

    def post(path, params, idempotency_key)
      request = Net::HTTP::Post.new(path, "Content-Type" => "application/json",
                                          "Authorization" => "Bearer #{@api_key}",
                                          "Idempotency-Key" => idempotency_key)
      request.body = params.to_json

      response = Net::HTTP.start(BASE_URL.host, BASE_URL.port, use_ssl: true,
                                 open_timeout: @open_timeout, read_timeout: @read_timeout) do |http|
        http.request(request)
      end

      case response
      when Net::HTTPSuccess then JSON.parse(response.body)
      when Net::HTTPPaymentRequired then raise CardDeclined, "カードが利用できませんでした"
      else raise GatewayUnavailable, "うめペイが #{response.code} を返しました"
      end
    rescue Net::OpenTimeout, Net::ReadTimeout, Errno::ECONNREFUSED, SocketError => e
      raise GatewayUnavailable, "うめペイにつながりませんでした（#{e.class}）"
    end
  end
end
```

**初花**: 金額は `Money` で受け取って、うめペイに送るときに `amount.yen` にしてる。HTTPの402（Payment Required）も、ここで `CardDeclined` に変えてるんだ。

**マリゴールド**: そう。うめペイの都合は、このクラスの中だけで片付ける。呼ぶ側は `Money` と `CardDeclined` だけを知っていればいい。これが腐敗防止層だよ。

`app/usecases/ticketing/pay_for_reservation.rb`:

```ruby
module Ticketing
  # 仮予約の支払い。決済サービスで支払い金額を受け取り、予約確定にする
  class PayForReservation
    # already_paid は、すでに支払いが済んでいて、今回は何もしなかったとき true
    Result = Data.define(:reservation, :already_paid)

    def initialize(reservations: ReservationRepository.new, gateway: Billing.gateway)
      @reservations = reservations
      @gateway = gateway
    end

    def call(reservation_id:, token:, now: Time.current)
      reservation = @reservations.find(reservation_id)
      # 同じ支払いが2回届いても、2回目は何もしない（ボタンの連打・通信のやり直し）
      return Result.new(reservation: reservation, already_paid: true) if reservation.status == :confirmed

      expire_if_deadline_passed(reservation, now)
      reservation.ensure_payable!(now: now)

      # 決済サービスの呼び出しは、トランザクションの外で。同じ冪等キーなら、何度頼んでも1回分
      charge_id = @gateway.charge(amount: reservation.total_price, token: token,
                                  idempotency_key: "charge-reservation-#{reservation.id}-#{token}")

      confirmed = ApplicationRecord.transaction do
        Payment.create!(reservation_id: reservation.id, amount: reservation.total_price.yen, charge_id: charge_id)
        ConfirmReservation.new(reservations: @reservations).call(reservation_id: reservation.id, now: now)
      end
      Result.new(reservation: confirmed, already_paid: false)
    end

    private

    def expire_if_deadline_passed(reservation, now)
      return unless reservation.status == :pending && now > reservation.payment_deadline

      ExpireReservation.new(reservations: @reservations).call(reservation_id: reservation.id, now: now)
      raise Reservation::PaymentDeadlinePassed
    end
  end
end
```

コントローラは、ユースケースの結果とエラーを画面のメッセージに変えるだけになります。

`app/controllers/payments_controller.rb`:

```ruby
class PaymentsController < ApplicationController
  def create
    result = Ticketing::PayForReservation.new.call(reservation_id: params[:reservation_id], token: params[:token])
    notice = result.already_paid ? "お支払いはすでに完了しています。" : "お支払いが完了し、予約が確定しました。"
    redirect_to reservation_path(params[:reservation_id]), notice: notice
  rescue Ticketing::Reservation::PaymentDeadlinePassed
    redirect_to reservation_path(params[:reservation_id]), alert: "お支払いの期限を過ぎたため、予約は取り消されました。"
  rescue Ticketing::BusinessRuleViolation
    redirect_to reservation_path(params[:reservation_id]), alert: "この予約はお支払いできません。"
  rescue Billing::CardDeclined => e
    redirect_to reservation_path(params[:reservation_id]), alert: e.message
  rescue Billing::GatewayUnavailable
    redirect_to reservation_path(params[:reservation_id]),
                alert: "決済サービスにつながりませんでした。時間をおいて、もう一度お試しください。"
  end
end
```

`app/jobs/billing/refund_payment_job.rb`:

```ruby
module Billing
  # 予約のキャンセルを受けて、決済サービスに返金を頼む。
  # 決済サービスにつながらなければ、少しずつ間をあけてやり直す。
  class RefundPaymentJob < ApplicationJob
    queue_as :default

    retry_on GatewayUnavailable, wait: :polynomially_longer, attempts: 5 do |job, _error|
      Payment.find_by!(reservation_id: job.arguments.first).update!(status: :refund_failed)
    end

    def perform(reservation_id, amount_yen)
      payment = Payment.find_by!(reservation_id: reservation_id)
      return if payment.refunded? # すでに返金済みなら、もう一度は頼まない

      # やり直しでも同じ冪等キーを使うので、決済サービスが2回返金することはない
      refund_id = Billing.gateway.refund(charge_id: payment.charge_id, amount: Money.new(amount_yen),
                                         idempotency_key: "refund-reservation-#{reservation_id}")
      payment.update!(status: :refunded, refund_id: refund_id)
    end
  end
end
```

## 15.3　メール送信をジョブに移す

**初花**: メールは、第12章でもうジョブにしたよね。

**マリゴールド**: そう。ドメインイベントの購読者は、ジョブを積むだけにした。ここでは、そのジョブが **失敗したときにどうするか** を決めよう。返金と同じく、やり直して直る失敗と、直らない失敗を分けるよ。

| 失敗 | どうする | 書き方 |
|------|--------|-------|
| メールサーバーにつながらない（タイムアウト） | やり直す | `retry_on Net::OpenTimeout, Net::ReadTimeout` |
| 予約が消えていた（送る相手がいない） | 捨てる | `discard_on ActiveRecord::RecordNotFound` |

`app/jobs/notification/send_reservation_mail_job.rb`:

```ruby
module Notification
  # 予約のメールを送るジョブ。失敗しても申込には影響せず、ジョブとしてやり直せる
  class SendReservationMailJob < ApplicationJob
    queue_as :default

    retry_on Net::OpenTimeout, Net::ReadTimeout, wait: :polynomially_longer, attempts: 3 # メールサーバーにつながらない
    discard_on ActiveRecord::RecordNotFound # 予約が消えていたら、送る相手がいない

    def perform(reservation_id, kind)
      reservation = ::Reservation.find(reservation_id)
      ReservationMailer.with(reservation: reservation).public_send(kind).deliver_now
    end
  end
end
```

`spec/jobs/notification/send_reservation_mail_job_spec.rb`:

```ruby
require "rails_helper"
```

**初花**: `deliver_later` で、Railsのメールのジョブに任せるのとは何が違うの？

**マリゴールド**: `deliver_later` のジョブは、予約のオブジェクトを渡すと、ジョブが動くときに読み直してくれる。でも、そのときに予約が消えていたらエラーになるし、やり直し方も自分では決めにくい。自分のジョブにすると、**何が起きたらどうするか** を業務に合わせて書けるんだ。

## 15.4　タイムアウトやAPI障害への対処

**初花**: `UmepayGateway` の `open_timeout: 2, read_timeout: 5` は、何の時間？

**マリゴールド**: `open_timeout` は「つながるまで待つ時間」、`read_timeout` は「つながってから返事を待つ時間」だよ。決めておかないと、うめペイが止まったときに、うめチケットのリクエストも長く待たされて、ほかの利用者まで遅くなる。

| 起きること | `UmepayGateway` が投げるもの | 支払いの画面では |
|----------|--------------------------|-------------|
| 200 番台が返った | （支払いIDを返す） | 「お支払いが完了し、予約が確定しました。」 |
| 402 が返った | `Billing::CardDeclined` | 「カードが利用できませんでした」 |
| 500 番台が返った | `Billing::GatewayUnavailable` | 「決済サービスにつながりませんでした。時間をおいて、もう一度お試しください。」 |
| つながらない・時間内に返事がない | `Billing::GatewayUnavailable` | 同上 |

本物のうめペイにはつなげないので、WebMock というテスト用のgemで、うめペイの返事を作ります。`Gemfile` の最後に、テストだけで使うグループを足します。

## 15.5　冪等性を設計する

**初花**: 「時間をおいて、もう一度お試しください」って案内したら、申込者はもう一度ボタンを押すよね。もし1回目が、うめペイの側では成功してたら？

**マリゴールド**: そこが一番の問題だね。タイムアウトは「失敗」ではなく **「結果が分からない」** なんだ。うめペイはお金を受け取ったのに、その返事がうめチケットに届かなかっただけかもしれない。

```text
うめチケット                     うめペイ
    │ charge（3,000円）           │
    │ ──────────────────────────▶ │ 支払いを受け付けた（3,000円）
    │                             │
    │   × 返事が届かない（タイムアウト）
    │                             │
    │ もう一度 charge              │
    │ ──────────────────────────▶ │ ？？ もう一度 3,000円受け取ってしまう？
```

**初花**: 2回押したら、6,000円取られちゃう……。

**マリゴールド**: それを防ぐのが **冪等性**（べきとうせい）。「同じ操作を何回やっても、1回やったのと同じ結果になる」という性質だよ。うめチケットでは、3つの段で冪等にしている。

| 段 | 仕組み | 守る場面 |
|----|-------|--------|
| ユースケース | 予約確定の予約に支払いが来たら、何もせず「済んでいる」と返す | ボタンの連打・ブラウザの戻る |
| 決済サービス | 同じ **冪等キー**（`Idempotency-Key`）の依頼には、最初の結果を返す | タイムアウトのあとのやり直し |
| データベース | `payments.reservation_id` のユニークインデックス（第3章） | それでもすり抜けたとき |

**初花**: 冪等キーは、どうやって決めるの？

**マリゴールド**: 「**同じ依頼なら、同じキー**」になるように、業務の言葉から作るんだ。うめチケットの支払いは「この予約の、このカードでの支払い」だから、予約のIDとカードのトークンからキーを作る。返金は「この予約の返金」だから、予約のIDだけで作る。

| 依頼 | 冪等キー | 同じキーになるとき |
|------|--------|---------------|
| 支払い | `charge-reservation-{予約のID}-{トークン}` | 同じ予約を同じカードで、もう一度支払ったとき |
| 返金 | `refund-reservation-{予約のID}` | 同じ予約の返金を、もう一度頼んだとき |

ユースケースの冪等性を確かめるテストです。

## 15.6　リトライによる二重実行を防ぐ

**初花**: 返金のジョブは、決済サービスにつながらないと最大5回やり直すんだよね。1回目が実はうめペイで成功してたら、5回返金されちゃう？

**マリゴールド**: やり直しのたびに **同じ冪等キー** を送っているから、うめペイは2回目以降を「さっきの返金と同じ」と分かってくれる。15.4 の「タイムアウトのあとのやり直しでも、同じ冪等キーを送る」がまさにその場面だね。ジョブの側でも確かめておこう。

`spec/jobs/billing/refund_payment_job_spec.rb`（抜粋）:

```ruby
  it "やり直しのたびに、同じ冪等キーで頼む" do
    unavailable = ->(**) { raise Billing::GatewayUnavailable }
    allow(gateway).to receive(:refund).and_invoke(unavailable, ->(**) { "re_retry" })

    perform_enqueued_jobs { described_class.perform_later(reservation.id, 3000) }

    expect(gateway).to have_received(:refund)
      .with(charge_id: "ch_test", amount: Money.new(3000), idempotency_key: "refund-reservation-#{reservation.id}").twice
  end
```

| やり直しで二重になる場面 | 防いでいるもの |
|---------------------|------------|
| 返金のジョブがやり直される | 同じ冪等キー（うめペイの側で1回分にする） |
| 返金は済んだのに、ジョブが「終わった」と記録する前に落ちた | ジョブの「返金済みなら何もしない」（第14章） |
| 支払いのボタンを2回押した | ユースケースの「予約確定なら何もしない」 |
| 支払いのタイムアウトのあと、もう一度押した | 同じ冪等キー |

**初花**: 冪等キーとジョブの確かめ、どっちか1つじゃだめ？

**マリゴールド**: 守っている場所が違うからね。ジョブの確かめは、うめチケットのデータベースを見て「もう返金したか」を判断する。冪等キーは、うめペイの側で判断する。**どちらか一方の記録だけが残る** 瞬間があるから、両方で守るんだ。

## 振り返り

**初花**: タイムアウトは「失敗」じゃなくて「分からない」。そう考えると、やり直しても大丈夫な作りにするしかないんだね。

## 初花のメモ帳

- 外部サービスとはアダプターでつなぎ、外の言葉（HTTPのステータス・金額の形）を中に持ち込まない
- 失敗は「やり直して直る」と「直らない」に分ける。タイムアウトは「結果が分からない」
- 冪等性は、ユースケース・冪等キー・データベースの制約の3段で守る。冪等キーは業務の言葉から作る

## マリゴールドの one more thing

**タイムアウトのあと「結果が分からない」支払いを、あとから確かめる仕組みもある。**

この章では、タイムアウトしたら申込者にもう一度押してもらい、冪等キーで二重の請求を防ぎました。でも、申込者がそのまま画面を閉じてしまったら、うめペイでは支払いが済んでいるのに、うめチケットでは仮予約のまま期限切れになるかもしれません。そうした食い違いを見つけるために、定期的に決済サービスの記録とうめチケットの記録を突き合わせる処理（**照合**、リコンシリエーション）を用意するのが一般的です。食い違いを見つけたら、返金するか、予約を確定にするかを決めます。第20章のデータ不整合の検知で、この考え方を残席の数え直しに応用します。
