# 第18章　よくあるアンチパターンを直す

**初花**: 第3章の課題一覧、13個のうち12個に印が付いたね。もうほとんど完成？

**マリゴールド**: 課題一覧の問題は片付いてきた。でも、DDDのパターンを入れていく途中で、**新しい種類の問題** も生まれやすいんだ。パターンを使ったつもりで、かえってコードを読みにくくしてしまう形。それを **アンチパターン** と呼ぶよ。

**初花**: うめチケットにも、そういうのがある？

**マリゴールド**: 探してみよう。この章では、よくあるアンチパターンを並べて、今のコードに残っているものを Before／After で直す。第1章で予告した「`git diff` で比べる」もやるよ。

## 18.1　名前だけのドメインサービス

**初花**: 第11章で、ドメインサービスを増やしすぎると、エンティティが「データだけの入れ物」になるって言ってたよね。

**マリゴールド**: そう。こういうクラスをよく見かけるんだ。

```ruby
module Ticketing
  # 名前だけのドメインサービス：予約が自分でできる計算を、外に出してしまっている
  class TotalPriceCalculationService
    def calculate(reservation)
      reservation.price * reservation.count.to_i
    end
  end
end
```

`bin/rails runner` で、予約のエンティティの `total_price` と比べてみます。

```text
#<Money 3,000円>
#<Money 3,000円>
```

**初花**: 結果は同じ。でも、`Ticketing::Reservation#total_price` があるのに、わざわざ別のクラスにしてるんだ。

**マリゴールド**: 支払い金額は、予約が持っている料金と人数だけで決まるよね。それを外のクラスに出すと、予約は「料金と人数を持っているだけの入れ物」になって、ルールがどこにあるか探さないといけなくなる。

| 見分け方 | 名前だけのドメインサービス | 本当に要るドメインサービス |
|---------|----------------------|----------------------|
| 使う情報 | 1つのエンティティ・値オブジェクトの中だけ | 複数の集約、またはリポジトリへの問い合わせ |
| 名前 | `◯◯CalculationService`・`◯◯Manager` | 業務の言葉（`DoubleBookingCheck`） |
| 直し方 | エンティティ・値オブジェクトのメソッドにする | そのまま |
| うめチケットでは | なし（作らなかった） | `Ticketing::DoubleBookingCheck` |

## 18.2　何でもRepository経由にする設計

**初花**: 逆に、リポジトリを作りすぎることもある？

**マリゴールド**: あるよ。イベント管理のように、Active Record をそのまま使えばいい場所に、こういうリポジトリを作ってしまう例だね。

```ruby
# 何でもリポジトリ経由：Active Record の find と save を、そのまま包んだだけ
class EventRepository
  def find(id) = Event.find(id)
  def save(event) = event.save
end
```

**初花**: `find` で返ってくるのは Active Record の `Event` そのもの。包んでるだけで、何も変換してない。

**マリゴールド**: 第10章で話したとおり、リポジトリの仕事は **ドメインのオブジェクトとテーブルの形を変換する** ことだったね。変換がないなら、間に挟む意味がない。ファイルが1つ増えて、読む人が1か所よけいに飛ぶだけなんだ。

| 何でもリポジトリ経由の困りごと | うめチケットでは |
|---------------------------|-------------|
| 変換のない、包んだだけのクラスが増える | イベント管理は `Event` をそのまま使う（第5章・第7章） |
| 一覧や検索のために、`find_by_◯◯` が増え続ける | 読むだけの画面は Active Record で読む（第10章） |
| リポジトリが Active Record を返すので、結局どこでも `save` できる | 予約のリポジトリは、ドメインのオブジェクトだけを返す |

**初花**: 予約のコンテキストのユースケースが、決済のコンテキストの `Payment` を作ってる。第6章のコンテキストマップだと、予約は決済に「頼む」だけのはずだよね。

**マリゴールド**: そう。これだと、決済の記録の仕方（列の名前、記録のタイミング）を変えるたびに、予約のユースケースを開くことになる。決済の記録は、決済のコンテキストの入口にまとめよう。

`app/usecases/billing/charge_reservation.rb`:

```ruby
module Billing
  # 予約の支払い金額を受け取り、決済の記録を残す。決済のコンテキストの入口
  class ChargeReservation
    def initialize(gateway: Billing.gateway)
      @gateway = gateway
    end

    # 支払いIDを返す。同じ予約の支払いがすでに記録されていれば、決済サービスを呼ばずにそれを返す
    def call(reservation_id:, amount:, token:)
      existing = Payment.find_by(reservation_id: reservation_id)
      return existing.charge_id if existing

      charge_id = @gateway.charge(amount: amount, token: token,
                                  idempotency_key: "charge-reservation-#{reservation_id}-#{token}")
      Payment.create!(reservation_id: reservation_id, amount: amount.yen, charge_id: charge_id)
      charge_id
    end
  end
end
```

`app/usecases/ticketing/pay_for_reservation.rb`:

```ruby
module Ticketing
  # 仮予約の支払い。決済のコンテキストに支払いを頼み、予約確定にする
  class PayForReservation
    # already_paid は、すでに支払いが済んでいて、今回は何もしなかったとき true
    Result = Data.define(:reservation, :already_paid)

    def initialize(reservations: ReservationRepository.new, billing: Billing::ChargeReservation.new)
      @reservations = reservations
      @billing = billing
    end

    def call(reservation_id:, token:, now: Time.current)
      reservation = @reservations.find(reservation_id)
      # 同じ支払いが2回届いても、2回目は何もしない（ボタンの連打・通信のやり直し）
      return Result.new(reservation: reservation, already_paid: true) if reservation.status == :confirmed

      expire_if_deadline_passed(reservation, now)
      reservation.ensure_payable!(now: now)

      # 決済のコンテキストに頼む（トランザクションの外）。やり直しても、受け取るのは1回分
      @billing.call(reservation_id: reservation.id, amount: reservation.total_price, token: token)

      confirmed = ConfirmReservation.new(reservations: @reservations).call(reservation_id: reservation.id, now: now)
      Result.new(reservation: confirmed, already_paid: false)
    end

    private

    def expire_if_deadline_passed(reservation, now)
      return unless reservation.status == :pending && now > reservation.payment_deadline

      ExpireReservation.new(reservations: @reservations).call(reservation_id: reservation.id, now: now)
      raise Reservation::PaymentDeadlinePassed
    end
  end
end
```

**初花**: 決済の記録と予約の確定が、別々のトランザクションになった。前は1つのトランザクションだったのに、大丈夫？

**マリゴールド**: 第9章で話した「1回のトランザクションでは、できるだけ1つの集約だけを変える」に近づいたんだ。その代わり、**決済の記録はできたのに、予約の確定に失敗する** 瞬間が生まれる。そのときにもう一度支払っても、二重に受け取らないことをテストで確かめよう。`Billing::ChargeReservation` は、記録済みなら決済サービスを呼ばずに同じ支払いIDを返すから、大丈夫なはずだよ。

## 18.6　一つのテーブルを全コンテキストで共有する問題

**初花**: 第6章で ⚠️ を付けた「決済が予約を知っている（`Payment belongs_to :reservation`）」も、まだ残ってるよね。

**マリゴールド**: 関連付けを、両方のモデルから探してみよう。

## マリゴールドの one more thing

**リファクタリングの順番は、課題一覧の「種類」で決めると迷わない。**

第3章の課題一覧には「種類」の列がありました（ルールの分散・状態遷移・隠れた副作用・外部サービス・並行処理）。本書では、値の表現（第8章）→ 整合性の境界（第9章）→ 保存（第10章）→ 手順（第11章）→ 副作用（第12章）→ 入口（第13章）→ 状態遷移（第14章）→ 外部（第15章）→ 並行処理（第16章）の順に進めました。小さな部品から順に固めると、後の章で使える部品が増えていくからです。自分のアプリで同じことをするときも、まず課題に種類を付けて、「ほかの直しの土台になる種類」から始めてみてください。
