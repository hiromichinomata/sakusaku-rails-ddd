# 第2章　まずは普通のRailsアプリを作る

**初花**: 土台ができたから、いよいよDDDのコードだね。エンティティから作る？

**マリゴールド**: まだ作らないよ。この章は、Railsの入門書どおりの **普通の書き方** で、イベントを登録して予約できるところまで作る。

**初花**: わざわざ普通に作るのは、あとで書き直すため？

**マリゴールド**: そう。普通の書き方がどこまで素直に通用して、どこから苦しくなるのか。それを第3章で体験するための、比べる元になるアプリだよ。

この章で作る画面とURLです。

| 画面 | URL | 使う人 |
|------|-----|--------|
| イベント一覧 | `GET /events` | 参加者 |
| イベント詳細・予約フォーム | `GET /events/:id` | 参加者 |
| 予約する | `POST /events/:event_id/reservations` | 参加者 |
| イベント登録フォーム | `GET /events/new` | 主催者 |
| イベントを登録する | `POST /events` | 主催者 |

⚠️ 本書では、ログインや権限（主催者だけがイベントを登録できる、など）は扱いません。Rails 8 には `bin/rails generate authentication` という認証の雛形があるので、必要になったら公式ガイドを参照してください。

## 2.1　イベント一覧・詳細画面を作る

**初花**: まずはイベントのテーブルからだよね。どんな項目が要る？

**マリゴールド**: 告知に必要なものと、予約に必要なものを並べてみよう。

| 項目 | カラム名 | 型 | 空を許すか |
|------|---------|----|-----------|
| タイトル | `title` | 文字列 | ❌ |
| 説明 | `description` | テキスト | ✅ |
| 会場 | `venue` | 文字列 | ✅（バリデーションで必須にする） |
| 開始日時 | `starts_at` | 日時 | ❌ |
| 定員 | `capacity` | 整数 | ❌ |
| 料金（円） | `price` | 整数 | ❌ |

モデルとマイグレーションを作ります。`--no-test-framework` は、中身が空のテストファイルを作らないための指定です。

```bash
bin/rails generate model Event title:string description:text venue:string starts_at:datetime capacity:integer price:integer --no-test-framework
```

```text
      invoke  active_record
      create    db/migrate/20261018103459_create_events.rb
      create    app/models/event.rb
```

生成されたマイグレーションに、空を許さない列の `null: false` を足します。ファイル名の先頭の数字は、作った日時なので環境ごとに変わります。

```ruby
      t.integer :price, null: false

  end
end
```

**初花**: 料金は整数なんだ。1,500.5円みたいな値段はないもんね。

**マリゴールド**: 円は小数を使わないから、整数で持つのがいちばん安全。金額の扱いは、第8章で `Money` という値オブジェクトにまとめるときに、もう一度考えるよ。

## 2.2　Active Recordによるイベントの保存

**初花**: テストでは `Event.create!` で保存してたけど、実際にどんなSQLが流れてるのか気になる。

**マリゴールド**: `bin/rails console` で一つずつ確かめてみよう。Active Record が、Rubyのオブジェクトとテーブルの行を行き来させる様子が見えるよ。

```bash
bin/rails console
```

```text
ume-tickets(dev):002> event.new_record?

ume-tickets(dev):003> event.save

  TRANSACTION (0.9ms)  COMMIT
```

（`Event.new` のあとに表示されるオブジェクトの中身と、SQLの行の末尾に付く `/*application='UmeTickets'*/` というコメントは省略しています。）

**初花**: あれ、SQLでは `'2026-11-15 01:00:00'` になってる。10時で保存したのに。

**マリゴールド**: データベースには **UTC（世界標準時）** で入るからだよ。日本時間の10時は、UTCの1時。読み出すときに `config.time_zone` の設定で日本時間に戻してくれるから、Rubyの側では10時に見えるんだ。

| 操作 | メソッド | SQL |
|------|---------|-----|
| 作る（まだ保存しない） | `Event.new(...)` | なし |
| 保存する | `event.save` | `INSERT`（トランザクションの中で） |
| IDで取り出す | `Event.find(1)` | `SELECT ... WHERE "events"."id" = 1` |
| 条件で数える | `Event.where("capacity >= ?", 10).count` | `SELECT COUNT(*) ... WHERE (capacity >= 10)` |

### 保存できないデータ

開始日時を書き忘れたイベントを保存してみます。

```text
ume-tickets(dev):007> Event.create(title: "日時を書き忘れたイベント", capacity: 10, price: 0)
(ume-tickets):7:in '<main>': PG::NotNullViolation: ERROR:  null value in column "starts_at" of relation "events" violates not-null constraint (ActiveRecord::NotNullViolation)
```

**初花**: 保存は止まったけど、すごい勢いで怒られた。画面でこれが出たら困るね。

**マリゴールド**: これはデータベースの `null: false` が止めてくれた形。最後の砦としては大事だけど、利用者に見せるメッセージにはならない。その手前で、モデルの **バリデーション** で止めて、分かりやすいエラーを返そう。

`app/models/event.rb`:

```ruby
class Event < ApplicationRecord
  validates :title, :venue, :starts_at, presence: true
  validates :capacity, numericality: { only_integer: true, greater_than: 0 }
  validates :price, numericality: { only_integer: true, greater_than_or_equal_to: 0 }
end
```

```text
ume-tickets(dev):001> event = Event.new(title: "日時を書き忘れたイベント", capacity: 0, price: -100)
ume-tickets(dev):002> event.save
=> false
ume-tickets(dev):003> event.errors.full_messages
=>
["Venue can't be blank",
 "Starts at can't be blank",
 "Capacity must be greater than 0",
 "Price must be greater than or equal to 0"]
```

`save` が例外ではなく `false` を返し、理由が `errors` に入りました。ただ、メッセージが英語です。日本語の翻訳をまとめた `rails-i18n` を入れます。

`Gemfile`（抜粋）:

```ruby

```

```bash
bundle install
```

`config/application.rb` の `config.time_zone` の下に、既定の言語を日本語にする1行を足します。

```ruby
    config.i18n.default_locale = :ja
```

項目名の日本語は自分で書きます。

`config/locales/ja.yml`:

```text
ume-tickets(dev):001> event = Event.new(title: "日時を書き忘れたイベント", capacity: 0, price: -100)
ume-tickets(dev):002> event.valid?
=> false
ume-tickets(dev):003> event.errors.full_messages
=> ["会場を入力してください", "開始日時を入力してください", "定員は0より大きい値にしてください", "料金は0以上の値にしてください"]
```

**初花**: 日本語になった。データベースの `null: false` と、モデルのバリデーション、両方書くのは二度手間じゃない？

**マリゴールド**: 役割が違うんだ。バリデーションは **利用者に理由を伝える** ため、データベースの制約は **どんな経路でも壊れたデータを入れない** ため。コンソールやスクリプトからはバリデーションを飛ばせてしまうから、両方あると安心だよ。

| | モデルのバリデーション | データベースの制約 |
|---|----------------------|------------------|
| 止めたとき | `save` が `false`、理由が `errors` に入る | 例外（`ActiveRecord::NotNullViolation` など） |
| 書ける内容 | 自由（Rubyで書ける） | NULL・一意・外部キー・CHECKなど |
| すり抜け | `save(validate: false)` や `update_column` で飛ばせる | 飛ばせない |

### イベント登録フォームを作る

主催者がイベントを登録する画面です。スペックの `describe "GET /events/:id"` の後ろに、登録のテストを足します。

`spec/requests/events_spec.rb`（抜粋）:

```ruby
  describe "POST /events" do
    let(:valid_params) do
      {
        event: {
          title: "梅林ガイドツアー",
          venue: "うめ公園",
          starts_at: "2026-12-06 13:00",
          capacity: 30,
          price: 0
        }
      }
    end

    it "イベントを登録して、詳細画面へ移動する" do
      expect { post events_path, params: valid_params }.to change(Event, :count).by(1)

      expect(response).to redirect_to(event_path(Event.last))
    end

    it "入力に誤りがあれば、登録せずにエラーを表示する" do
      invalid_params = { event: valid_params[:event].merge(title: "", capacity: 0) }

      expect { post events_path, params: invalid_params }.not_to change(Event, :count)

      expect(response).to have_http_status(:unprocessable_content)
      expect(response.body).to include("タイトルを入力してください")
      expect(response.body).to include("定員は0より大きい値にしてください")
    end
  end
```

ルーティングに `new` と `create` を足します。

```ruby
  resources :events, only: %i[index show new create]
```

`app/controllers/events_controller.rb`:

```ruby
class EventsController < ApplicationController
  def index
    @events = Event.order(:starts_at)
  end

  def show
    @event = Event.find(params[:id])
  end

  def new
    @event = Event.new
  end

  def create
    @event = Event.new(event_params)

    if @event.save
      redirect_to @event, notice: "イベントを登録しました。"
    else
      render :new, status: :unprocessable_content
    end
  end

  private

  def event_params
    params.expect(event: %i[title description venue starts_at capacity price])
  end
end
```

**初花**: `params.expect` って初めて見た。`params.require(:event).permit(...)` じゃないの？

**マリゴールド**: Rails 8 から入った書き方で、同じ意味をもっと安全に書けるんだ。`event` の形が違うパラメータが来たとき、`require.permit` だと500エラーになる場合があるけど、`expect` なら400 Bad Requestを返してくれる。

⚠️ インターネット上の記事の多くは `params.require(:event).permit(...)` で書かれています。Rails 8 でも動きますが、本書では `params.expect` を使います。

## 2.3　予約テーブルと関連付けの実装

**初花**: 次は予約だね。予約には何が要る？

**マリゴールド**: どのイベントに、誰が、何人で申し込んだか。誰かは、まずは名前とメールアドレスで表そう。

```bash
bin/rails generate model Reservation event:references name:string email:string quantity:integer --no-test-framework
```

```text
      invoke  active_record
      create    db/migrate/20261018103731_create_reservations.rb
      create    app/models/reservation.rb
```

`db/migrate/20261018103731_create_reservations.rb`:

```ruby
class CreateReservations < ActiveRecord::Migration[8.1]
  def change
    create_table :reservations do |t|
      t.references :event, null: false, foreign_key: true
      t.string :name, null: false
      t.string :email, null: false
      t.integer :quantity, null: false

      t.timestamps
    end
  end
end
```

```bash
bin/rails db:migrate
```

```text
== 20261018103731 CreateReservations: migrating ===============================
-- create_table(:reservations)
   -> 0.0110s
== 20261018103731 CreateReservations: migrated (0.0110s) ======================
```

`event:references` を指定したので、`app/models/reservation.rb` には `belongs_to :event` が最初から入っています。反対側の `Event` に `has_many` を足します。

`app/models/event.rb`:

```ruby
class Event < ApplicationRecord
  has_many :reservations, dependent: :destroy

  validates :title, :venue, :starts_at, presence: true
  validates :capacity, numericality: { only_integer: true, greater_than: 0 }
  validates :price, numericality: { only_integer: true, greater_than_or_equal_to: 0 }
end
```

| 書き方 | 意味 |
|-------|------|
| `t.references :event, foreign_key: true` | `event_id` 列と、`events` テーブルへの外部キー制約を作る |
| `belongs_to :event` | 予約は必ず1つのイベントに属する（`reservation.event`） |
| `has_many :reservations` | イベントは予約をいくつも持つ（`event.reservations`） |
| `dependent: :destroy` | イベントを消したら、その予約も消す |

コンソールで、予約を2件作ってみます。


`app/models/reservation.rb`:

```ruby
class Reservation < ApplicationRecord
  belongs_to :event

  validates :name, presence: true
  validates :email, presence: true, format: { with: URI::MailTo::EMAIL_REGEXP }
  validates :quantity, numericality: { only_integer: true, greater_than: 0 }
  validate :quantity_within_remaining_seats

  private

  def quantity_within_remaining_seats
    return if event.nil? || quantity.nil?

    remaining = event.capacity - event.reservations.where.not(id: id).sum(:quantity)
    if quantity > remaining
      errors.add(:quantity, :exceeds_remaining_seats, count: remaining)
    end
  end
end
```

```yaml
    errors:
      models:
        reservation:
          attributes:
            quantity:
              exceeds_remaining_seats: "が残りの席数（%{count}席）を超えています"
```

| コード | 意味 |
|-------|------|
| `validate :メソッド名` | 自分で書いたメソッドでチェックする |
| `where.not(id: id)` | 自分自身を除いて数える（保存済みの予約を変更するときのため） |
| `errors.add(:quantity, :exceeds_remaining_seats, count: remaining)` | `quantity` にエラーを付ける。文言は `ja.yml` から、`%{count}` に残りの席数が入る |

## 初花のメモ帳

- データベースの制約は「どんな経路でも壊れたデータを入れない」、バリデーションは「利用者に理由を伝える」
- 席を数えるときは予約の件数（`count`）ではなく人数の合計（`sum(:quantity)`）
- ルールはブラウザではなくサーバー側で確かめる。境界の値（ちょうど満席・1人超過）をスペックにする

## マリゴールドの one more thing

**`remaining_seats` は、呼ぶたびに `SUM` を数え直している。**

詳細画面を開くたび、予約するたびに、その予約の全件を合計するSQLが流れています。予約が数十件なら気になりませんが、数万件の大きなイベントや、一覧画面で全イベントの残席を出すようになると、だんだん重くなります。よくある対策は、イベントの側に「予約済みの人数」を数える列を持たせて、予約のたびに足し引きする方法です。ただし、その列と実際の予約がずれないように守る仕組みが必要になります。この「ずれないように守る」ことこそ、第9章の集約と第16章の並行処理で扱うテーマです。
