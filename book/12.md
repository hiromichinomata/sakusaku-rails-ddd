# 第12章　ドメインイベント

**初花**: ユースケースで申込の手順はまとまったけど、メールはまだ Active Record のコールバックが送ってるんだよね。

**マリゴールド**: そう。第3章で「コンソールで作っただけでもメールが積まれる」と困ったコールバックが、まだ残っている。この章では、それを外すよ。

**初花**: 外したら、メールはどこから送るの？ ユースケースに `ReservationMailer` を書く？

**マリゴールド**: それだと、予約のコンテキストが通知のことを知ってしまう。第6章のコンテキストマップでは、予約は「起きたことを知らせるだけ」、通知は「それを受け取って送る」だったよね。その「起きたこと」を表すのが **ドメインイベント** だよ。

---

## 12.1　状態変更とイベントの違い

**初花**: 状態が変わることと、イベントって、何が違うの？ 予約が作られたら、`status` が `pending` になるよね。

**マリゴールド**: 状態は「**今どうなっているか**」、イベントは「**何が起きたか**」だよ。状態は上書きされて消えていくけど、イベントは起きた事実として残る。

| | 状態 | ドメインイベント |
|---|------|--------------|
| 表すもの | 今どうなっているか | 何が起きたか |
| 例 | 予約の状態は「予約確定」 | 「予約が確定した」（11月1日10時に） |
| 名前 | 名詞・形容詞（`confirmed`） | 過去形（`ReservationConfirmed`） |
| 変わるか | 次の操作で上書きされる | 起きた事実なので変わらない |
| 知りたい人 | その集約を使う人 | ほかのコンテキスト（通知・ログ・集計） |

**初花**: 名前が過去形なのは、もう起きたことだからか。

**マリゴールド**: そう。「予約を確定せよ」は命令で、「予約が確定した」は知らせ。イベントを受け取った側は、**断ることができない**。起きたことを受け止めて、自分の仕事（メールを送る、記録する）をするだけなんだ。

| ドメインイベント | 起きたこと | 知りたいコンテキスト |
|--------------|---------|-----------------|
| `Ticketing::ReservationCreated` | 申込を受け付けて、予約が作られた | 通知（お支払いのお願い、または確定のメール） |
| `Ticketing::ReservationConfirmed` | 支払いが済んで、予約が確定した | 通知（確定のメール） |
| （第14章）予約がキャンセルされた・期限切れになった | 席が戻った | 通知、キャンセル待ち（第21章） |

## 12.2　`ReservationCreated` を定義する

**初花**: イベントは、どんな形で作るの？

**マリゴールド**: 起きた事実だから、作ったあとは変えない **値** にするよ。`Data.define` がちょうどいい。中身は、受け取った側が「何が起きたか」を知るのに要るものだけにする。

`app/domain/ticketing/reservation_created.rb`:

```ruby
module Ticketing
  # ドメインイベント「予約が作られた」。申込が受け付けられたことを、ほかのコンテキストに知らせる
  class ReservationCreated < Data.define(:reservation_id, :event_id, :status, :occurred_at)
    def self.event_name
      "ticketing.reservation_created"
    end
  end
end
```

| 属性 | 入れる理由 |
|------|----------|
| `reservation_id` | 受け取った側が、必要なら予約を読みに行ける |
| `event_id` | どのイベントの予約か（集計やキャンセル待ちで使う） |
| `status` | 仮予約で作られたのか、予約確定で作られたのか（送るメールが変わる） |
| `occurred_at` | いつ起きたか |

**初花**: 予約のオブジェクトそのものを入れないのはなんで？

**マリゴールド**: イベントは、ほかのコンテキストに渡すものだからね。予約のエンティティを丸ごと渡すと、受け取った側が予約のコンテキストの中身に依存してしまう。**IDと、起きたことの要点だけ** を渡すのが基本だよ。

## 12.3　ドメインイベントを発行する

**初花**: イベントを作ったら、どうやって知らせるの？

**マリゴールド**: 「発行する」と「購読する」の窓口を作るよ。最初は、Railsに入っている `ActiveSupport::Notifications` をそのまま使う。

`app/infrastructure/domain_events.rb`:

```ruby
# ドメインイベントを発行し、購読者に届ける
module DomainEvents
  def self.publish(event)
    ActiveSupport::Notifications.instrument(event.class.event_name, event: event)
  end

  def self.subscribe(event_class, subscriber)
    ActiveSupport::Notifications.subscribe(event_class.event_name) do |*, payload|
      subscriber.call(payload[:event])
    end
  end
end
```

**初花**: イベントを発行するのは誰？ 予約のエンティティ？

**マリゴールド**: いくつかの考え方があるんだ。

| 発行する場所 | やり方 | 本書では |
|-----------|-------|--------|
| 集約・エンティティ | 自分の中にイベントをためておき、保存したあとに誰かが取り出して発行する | 使わない（今は予約のIDが保存のあとで決まるので、手間が増える） |
| ユースケース | 手順の中で、保存が済んだあとに作って発行する | ✅ 使う |
| Active Record のコールバック | `after_create_commit` で発行する | 使わない（第3章の問題に戻る） |

**初花**: ユースケースなら、予約を保存して、IDが決まってから発行できるね。

**マリゴールド**: そう。申込のユースケースの最後に、イベントの発行を足そう。

`app/usecases/ticketing/reserve_seats.rb`（抜粋）:

```ruby
        reservation = @reservations.add(
          Reservation.apply(event_id: event_id, applicant: applicant, count: count, price: sales_info.price)
        )
        DomainEvents.publish(ReservationCreated.new(reservation_id: reservation.id, event_id: event_id,
                                                    status: reservation.status, occurred_at: now))
        reservation
      end
```

ユースケースのスペックに、イベントが届くことを確かめる例を足します。

`spec/usecases/ticketing/reserve_seats_spec.rb`（抜粋）:

```ruby
  it "予約が作られたことを、ドメインイベントで知らせる" do
    received = []
    subscription = ActiveSupport::Notifications.subscribe(Ticketing::ReservationCreated.event_name) do |*, payload|
      received << payload[:event]
    end

    reservation = reserve(count: 2)

    expect(received.map(&:reservation_id)).to eq([ reservation.id ])
    expect(received.first.status).to eq(:pending)
  ensure
    ActiveSupport::Notifications.unsubscribe(subscription)
  end
```

## 12.4　イベントからメール通知を起動する

**初花**: 次は、イベントを受け取ってメールを送る側だね。

**マリゴールド**: 通知のコンテキストに、**購読者** を作るよ。購読者は、イベントの種類と中身を見て、どのメールを送るかを決める。支払いが済んだときのイベントも、ここで作っておこう。

`app/domain/ticketing/reservation_confirmed.rb`:

```ruby
module Ticketing
  # ドメインイベント「予約が確定した」。支払いが済んだことを、ほかのコンテキストに知らせる
  class ReservationConfirmed < Data.define(:reservation_id, :event_id, :occurred_at)
    def self.event_name
      "ticketing.reservation_confirmed"
    end
  end
end
```

`app/infrastructure/notification/reservation_mail_subscriber.rb`:

```ruby
module Notification
  # 予約のドメインイベントを受け取って、申込者に送るメールのジョブを積む
  class ReservationMailSubscriber
    def call(event)
      kind =
        case event
        when Ticketing::ReservationCreated then event.status == :pending ? "payment_request" : "confirmed"
        when Ticketing::ReservationConfirmed then "confirmed"
        end

      SendReservationMailJob.perform_later(event.reservation_id, kind)
    end
  end
end
```

購読者は、メールを送るジョブを積むだけです。なぜ購読者の中で直接メールを組み立てないのかは、12.6 で確かめます。

`app/jobs/notification/send_reservation_mail_job.rb`:

```ruby
module Notification
  # 予約のメールを送るジョブ。失敗しても申込には影響せず、ジョブとしてやり直せる
  class SendReservationMailJob < ApplicationJob
    queue_as :default

    def perform(reservation_id, kind)
      reservation = ::Reservation.find(reservation_id)
      ReservationMailer.with(reservation: reservation).public_send(kind).deliver_now
    end
  end
end
```

購読者を、イベントに登録します。

`config/initializers/domain_events.rb`:

```ruby
# ドメインイベントの購読者を登録する。
# 開発中にコードを読み込み直すたびに呼ばれるので、先に同じイベントの購読を外してから登録し直す。
Rails.application.config.to_prepare do
  events = [ Ticketing::ReservationCreated, Ticketing::ReservationConfirmed ]
  events.each { |event_class| ActiveSupport::Notifications.unsubscribe(event_class.event_name) }

  mail = Notification::ReservationMailSubscriber.new
  events.each { |event_class| DomainEvents.subscribe(event_class, mail) }
end
```

支払いが済んだときも、確定のイベントを発行します。支払いの処理は、第15章でユースケースに移すまで、今のコントローラのまま直します。

`app/controllers/payments_controller.rb`（抜粋）:

```ruby
    Reservation.transaction do
      @reservation.create_payment!(amount: amount.yen, charge_id: charge_id)
      @reservation.update!(status: :confirmed)
      DomainEvents.publish(Ticketing::ReservationConfirmed.new(reservation_id: @reservation.id,
                                                               event_id: @reservation.event_id,
                                                               occurred_at: Time.current))
    end
```

これで、メールのコールバックを Active Record から外せます。

`app/models/reservation.rb`:

```ruby
class Reservation < ApplicationRecord
  belongs_to :event
  has_one :payment, dependent: :destroy

  enum :status, {
    pending: "pending",
    confirmed: "confirmed",
    canceled: "canceled",
    expired: "expired"
  }, default: :pending

  scope :active, -> { where(status: %w[pending confirmed]) }

  validates :name, presence: true
  validates :email, presence: true, format: { with: URI::MailTo::EMAIL_REGEXP }
  validates :quantity, numericality: { only_integer: true, greater_than: 0, less_than_or_equal_to: Ticketing::ReservationCount::MAX }

  before_create :copy_price_from_event

  def total_price
    Money.new(price) * quantity
  end

  private

  def copy_price_from_event
    self.price ||= event&.price
  end
end
```

**初花**: コールバックが `copy_price_from_event` だけになった。コンソールで予約を作っても、もうメールは飛ばないんだね。

**マリゴールド**: そう。メールが送られるのは、**申込や支払いのユースケースが「起きた」と知らせたときだけ** になった。取り込みのスクリプトで予約を作っても、テストの準備で作っても、メールは積まれないよ。

## 12.5　ドメインイベントとActive Support Notifications

**初花**: `ActiveSupport::Notifications` って、もともとは何に使うものなの？

**マリゴールド**: Rails自身が、「SQLを実行した」「テンプレートを描いた」といった出来事を知らせるための仕組みだよ。ログに出ている `Reservation Create (2.9ms)` のような行も、この仕組みで作られている。名前の付いた出来事を発行して、その名前を購読した人に届ける、という形がドメインイベントにぴったりなんだ。

| | 発行 | 購読 |
|---|-----|-----|
| Rails の出来事 | `sql.active_record`・`render_template.action_view` | ログ・計測のツール |
| うめチケットのドメインイベント | `ticketing.reservation_created`・`ticketing.reservation_confirmed` | 通知の購読者（第20章ではログも） |

**初花**: `config/initializers/domain_events.rb` の `to_prepare` と、最初に購読を外してるのは何のため？

**マリゴールド**: 開発中は、コードを変えるとRailsが読み込み直すよね。そのたびに購読を登録すると、同じ購読者が2つ、3つと増えて、メールが何通も送られてしまう。読み込み直すたびに外してから登録し直せば、いつも1つで済む。確かめてみよう。

```bash
bin/rails runner 'name = Ticketing::ReservationCreated.event_name; count = -> { ActiveSupport::Notifications.notifier.listeners_for(name).size }; puts "起動直後: #{count.call}"; 2.times { Rails.application.reloader.reload! }; puts "2回読み込み直したあと: #{count.call}"'
```

```text
起動直後: 1
2回読み込み直したあと: 1
```

ドメインイベントの仕組みには、ほかの選択肢もあります。

| 仕組み | 特徴 | 向いている場面 |
|-------|------|------------|
| `ActiveSupport::Notifications`（本書） | Railsに入っている。同じプロセスの中で、同期的に届ける | 1つのRailsアプリの中で、まず始めるとき |
| 自分で書いた小さなイベントバス | 購読者の一覧を自分で持つ | 細かい制御（順番・失敗の扱い）が必要なとき |
| イベントを保存するgem（Rails Event Store など） | イベントをデータベースに保存して、あとから読み直せる | イベントの履歴そのものが業務で必要なとき |
| メッセージキュー（Kafka・SQS など） | 別のサービスに届ける | アプリを分けたとき（付録I） |

## 12.6　非同期ジョブとの接続

**初花**: 購読者がジョブを積むだけ、っていうのは、なんで？ 購読者の中で予約を読んで、`deliver_later` すればよくない？

**マリゴールド**: 購読者が失敗したときに何が起きるか、試してみよう。購読者が例外を出すように差し替えて、申込のユースケースを呼んでみるよ（確かめるための一時的なスペックです）。

```ruby
    event = create(:event)
    allow_any_instance_of(Notification::ReservationMailSubscriber).to receive(:call).and_raise("メールの準備に失敗")

    begin
      Ticketing::ReserveSeats.new.call(event_id: event.id, name: "初花", email: "hatsuka@example.com", count: 1)
    rescue => e
      puts "呼び出し元が受け取ったエラー: #{e.class}: #{e.message}"
    end
    puts "保存された予約: #{Reservation.count}件 / 押さえた席: #{event.ticket_inventory.reload.reserved_count}席"
```

```text
呼び出し元が受け取ったエラー: RuntimeError: メールの準備に失敗
保存された予約: 1件 / 押さえた席: 1席
```

**初花**: 予約も席も保存されてるのに、呼び出し元はエラーを受け取ってる！ 画面だと、予約できてるのにエラー画面が出るってこと？

**マリゴールド**: そう。`ActiveSupport::Notifications` は、購読者を **同じ処理の中で順番に呼ぶ** から、購読者の失敗が発行した側まで伝わってしまうんだ。だから購読者は、失敗しにくい「ジョブを積む」だけにする。予約の読み込みやメールの組み立てのように失敗しうる仕事は、ジョブの中で行って、失敗したらジョブとしてやり直せばいい。

画面から申し込んだときのログで、流れを確かめます。

```text
  TRANSACTION (8.1ms)  BEGIN
  TRANSACTION (2.0ms)  COMMIT
[ActiveJob] Enqueued Notification::SendReservationMailJob (Job ID: …) to Async(default) with arguments: 1, "payment_request"
Redirected to http://localhost:3000/reservations/1
[ActiveJob] [Notification::SendReservationMailJob] [f06008bd-b33e-45a6-976a-199fc1319f86] Performing Notification::SendReservationMailJob (Job ID: …) from Async(default) enqueued at 2026-10-18T11:38:54.218297000Z with arguments: 1, "payment_request"
[ActiveJob] [Notification::SendReservationMailJob] [f06008bd-b33e-45a6-976a-199fc1319f86] ReservationMailer#payment_request: processed outbound mail in 10.0ms
```

（`BEGIN` と `COMMIT` の間のSQL、ジョブIDなどは省略しています。）

**初花**: `COMMIT` のあとにジョブが積まれて、画面はすぐリダイレクトしてる。メールはそのあと、別の流れで組み立てられてるんだ。

| 仕事 | どこで | 失敗したら |
|------|-------|----------|
| 申込（席・予約の保存） | ユースケース（リクエストの中） | 申込のエラーとして画面に出す |
| ドメインイベントを受け取る | 購読者（リクエストの中） | 申込の呼び出し元に伝わる。だから軽くする |
| 予約を読み、メールを組み立てて送る | ジョブ（リクエストの外） | ジョブのやり直しに任せる。申込には影響しない |

### テストの確かめ方を変える

メールの送り方が変わったので、テストを流すと2件落ちます。

```text
  1) 予約 POST /events/:event_id/reservations 仮予約を作成して、お支払いのお願いをメールで送る
     Failure/Error:
       expect { reserve(quantity: 2) }.to change(Reservation, :count).by(1)
         .and have_enqueued_mail(ReservationMailer, :payment_request)

       expected to enqueue ReservationMailer.payment_request exactly 1 time but enqueued 0
```

**初花**: メールは送られてるのに、テストは落ちた。`have_enqueued_mail` は「メールの送信ジョブが積まれたか」を見てたからだ。今は、先に `SendReservationMailJob` が積まれる。

**マリゴールド**: そう。テストが **仕組み** を確かめていたから、仕組みを変えたら落ちたんだ。もっと気をつけたいのは、無料のイベントのテストのほう。「お支払いのお願いのメールが積まれない」を確かめていたから、今の仕組みでも **何も確かめずに通っている**。

**初花**: 否定の確かめ方だと、仕組みが変わっても気づけないんだ……。

**マリゴールド**: 確かめたいのは「申込者にどのメールが届いたか」だよね。ジョブを実際に動かして、届いたメールの件名で確かめよう。

```ruby
# 届いたメールの件名の一覧
def delivered_subjects
  ActionMailer::Base.deliveries.map(&:subject)
end
```

## 12.7　トランザクションとイベント発行の整合性

**初花**: 12.3 の `DomainEvents.publish` は、呼ばれたらすぐに購読者に届けてるよね。申込のユースケースでは、トランザクションの中で呼んでる。

**マリゴールド**: そこが問題になるんだ。トランザクションが最後に取り消されたら、イベントはどうなると思う？ `DomainEvents` のスペックを書いて確かめよう。本物の購読者にイベントが届かないように、テスト専用のイベントを使うよ。

**初花**: 取り消されたのに、イベントは届いてる。予約は保存されていないのに「予約が作られた」メールが飛ぶってことか。

**マリゴールド**: そう。たとえば、主催者の申込をまとめて取り込むスクリプトが1つのトランザクションの中で3件目に失敗すると、全部が取り消されるのに、1件目と2件目のメールは送られてしまう。**イベントは、コミットが確定してから届ける** ようにしよう。Rails 7.2 からある `ActiveRecord.after_all_transactions_commit` を使うよ。

`app/infrastructure/domain_events.rb`:

```ruby
# ドメインイベントを発行し、購読者に届ける。
# トランザクションの中で発行されたイベントは、コミットのあとで届ける（取り消されたら届けない）。
module DomainEvents
  def self.publish(event)
    ActiveRecord.after_all_transactions_commit do
      ActiveSupport::Notifications.instrument(event.class.event_name, event: event)
    end
  end

  def self.subscribe(event_class, subscriber)
    ActiveSupport::Notifications.subscribe(event_class.event_name) do |*, payload|
      subscriber.call(payload[:event])
    end
  end
end
```

## 12.8　Outboxパターンが必要になる場面

**初花**: コミットのあとで届けるなら、もう完璧だよね？

**マリゴールド**: ほぼね。でも、**コミットしてから、ジョブを積むまでの間** にサーバーが落ちたらどうなるかな。

```text
 ① 予約をコミットする            ✅ データベースに残る
 ② イベントを購読者に届ける
 ③ 購読者がジョブを積む          ← ここでサーバーが落ちたら？
 ④ ジョブがメールを送る
```

**初花**: 予約はあるのに、メールのジョブはどこにもない。メールが送られないまま、誰も気づかない。

**マリゴールド**: そう。①と③が別々の場所に書かれているから、片方だけが成功しうる。それを防ぐのが **Outbox パターン** で、イベントを、予約と **同じトランザクションで、同じデータベースの「送信箱」テーブルに書いておく**。別の係が送信箱を見て、まだ送っていないイベントを届ける。

```text
 1つのトランザクション
 ┌───────────────────────────────────────┐
 │ reservations に予約を書く               │
 │ outbox に「予約が作られた」を書く        │
 └───────────────────────────────────────┘
          │ コミット（両方そろって残る）
          ▼
 送信の係（ジョブ）が outbox を読み、購読者に届けて「送信済み」にする
```

| | コミットのあとで届ける（本書） | Outbox |
|---|------------------------|-------|
| 取り消されたイベント | 届かない | 届かない |
| コミットのあとに落ちたとき | イベントが失われる | 送信箱に残るので、あとで届く |
| 仕組み | `after_all_transactions_commit` だけ | 送信箱のテーブル・送信の係・送信済みの管理 |
| 同じイベントが2回届くことがある | ほぼない | ある（送ったあと「送信済み」にする前に落ちたら）。受け取る側で冪等にする |

**初花**: どういうときに、Outbox が必要になるの？

**マリゴールド**: **イベントが失われると、業務として困るとき** だね。

| 場面 | 失われたら | Outbox |
|------|----------|-------|
| お支払いのお願いのメール | 申込者が困るが、予約の画面からも支払える | なくてもよい（本書） |
| 決済サービスへの返金の依頼（第14章） | お金が返らない | 検討する |
| 別のサービスへの連携（会計システムなど） | 帳簿がずれる | 必要 |

⚠️ 本番では、ジョブの置き場所（Solid Queue）を、アプリとは別のデータベース（`queue`）にする設定になっています（`config/environments/production.rb` の `config.solid_queue.connects_to`）。そのため、ジョブを積むことを予約の保存と同じトランザクションに入れることはできません。同じトランザクションで確実に残したいものは、Outbox のように、予約と同じデータベースに書く必要があります。

## マリゴールドの one more thing

**ドメインイベントは、ログや監視にもそのまま使える。**

この章では、ドメインイベントの購読者として通知だけを登録しました。同じイベントに、もう一つ「記録する」購読者を足すと、予約がいつ作られ、いつ確定したかを、業務の言葉でログに残せます。Rails 8.1 には、構造化されたイベントを記録する `Rails.event` という仕組みも入りました。SQLのログからは「どの行が更新されたか」しか分かりませんが、ドメインイベントのログからは「申込者が予約を確定した」と読めます。第20章で、予約IDや決済IDを使ってログをたどる方法を扱うときに、この購読者を足します。
