# 第7章　RailsでDDDを実践するための設計方針

**初花**: コンテキストも決まったし、いよいよ `Ticketing` のクラスを書ける！

**マリゴールド**: あと一歩だよ。書き始める前に、「どのフォルダに、どんな種類のクラスを置くか」を決めておこう。決めずに書き始めると、第3章の `app/services` のように、何でも入る場所ができてしまう。

**初花**: Railsって、フォルダがもう決まってるよね。`models`、`controllers`、`views`。そこに入れればいいんじゃない？

**マリゴールド**: Railsのフォルダは、MVCという分け方に合わせてあるんだ。DDDの分け方とは少し違う。この章では、2つの分け方をどう重ねるかを決めて、最後に実際にフォルダを作るよ。

---

## 7.1　DDDとMVCは競合するのか

**初花**: DDDを使うなら、MVCは捨てるの？

**マリゴールド**: 捨てないよ。MVCは **画面とリクエストの扱い方** の分け方で、DDDは **業務のルールの置き方** の考え方なんだ。見ている場所が違うから、重ねて使える。

| | MVC（Rails） | DDD |
|---|------------|-----|
| 関心 | リクエストを受けて、データを読み書きし、画面を返す | 業務の知識を、正確にコードに写す |
| 分け方 | モデル・ビュー・コントローラ | 層（プレゼンテーション・アプリケーション・ドメイン・インフラ）とコンテキスト |
| 「モデル」の意味 | データベースのテーブルと対応する Active Record | 業務の概念とルール（テーブルとは限らない） |

**初花**: 「モデル」の意味が違うんだ。それで混乱するのか。

**マリゴールド**: そう。Railsの `app/models` は「データベースの行を表すクラス」が入る場所で、DDDのドメインモデルは「業務のルールを持つクラス」。第3章の `Reservation` は、その両方を一人でやっていたから太ったんだ。

---

## 7.2　ドメイン層・アプリケーション層・インフラ層

**初花**: じゃあ、DDDの分け方ってどうなってるの？

**マリゴールド**: DDDでは、コードを **層** に分けることが多いよ。上の層は下の層を使ってよいけど、下の層は上の層を知らない、という決まりにする。

```text
┌──────────────────────────────────────────────────────────┐
│ プレゼンテーション層   コントローラ・ビュー・メール          │  HTTPのことを知っている
├──────────────────────────────────────────────────────────┤
│ アプリケーション層     ユースケース（申し込む・キャンセルする）│  手順を並べる。ルールは持たない
├──────────────────────────────────────────────────────────┤
│ ドメイン層            エンティティ・値・集約・ドメインサービス │  業務のルール。RailsもHTTPも知らない
├──────────────────────────────────────────────────────────┤
│ インフラ層            Active Record・リポジトリ・決済アダプター│  データベースや外部サービスとつなぐ
└──────────────────────────────────────────────────────────┘
         ↑ インフラ層はドメイン層の型を使って実装する（依存はドメイン層に向かう）
```

| 層 | 仕事 | 例 | 知らないこと |
|----|------|----|------------|
| プレゼンテーション | リクエストを受け取り、結果を画面やJSONにする | `ReservationsController` | 返金のルール |
| アプリケーション | 一つの用事（ユースケース）の手順を並べる。トランザクションを決める | 「予約をキャンセルする」 | HTTP、画面 |
| ドメイン | 業務のルールを判断する | 「72時間前なら返金する」 | データベース、Rails |
| インフラ | 保存・読み込み、外部サービスとのやり取り | リポジトリ、`Billing::PaymentGateway` | 業務のルールの中身 |

**初花**: ドメイン層が、Railsも知らないってところが気になる。Railsのアプリなのに？

**マリゴールド**: ドメイン層は、業務のルールだけを持つ場所だからね。Railsのバージョンを上げても、データベースを変えても、返金のルールは変わらないでしょう。変わらないものを、変わるものから切り離しておくんだ。それに、Railsを読み込まないテストはとても速いよ。

---

## 7.3　Active Recordをドメインモデルとして使う方法

**初花**: でも、Active Record にルールを書くのも、そんなに悪くなかった気がする。`Reservation#total_price` とか。

**マリゴールド**: 悪くないよ。Active Record のモデルに業務のルールを書くのは、Railsでいちばん普通のやり方だし、多くのアプリはそれで十分なんだ。返金のルールを、Active Record に書くとこうなる。

```ruby
class Reservation < ApplicationRecord
  def refundable_at?(time)
    confirmed? && time <= event.starts_at - 72.hours
  end
end
```

このメソッドを `bin/rails runner` で試すと、ちょうど72時間前（11月12日10時）は `true`、その1分後は `false` になります。

| 良いところ | 困るところ |
|----------|----------|
| ファイルが増えない。Railsの書き方のまま | テストに、データベースと `Event` の準備が要る |
| `confirmed?` や `event` をそのまま使える | ルールとテーブルの形が結びつく（`starts_at` の列がないと書けない） |
| チームの誰でも読める | コールバックやバリデーションと同じクラスに並び、太りやすい |

## 7.4　Plain Old Ruby Object（PORO）を使う方法

**初花**: ほかのやり方もあるの？

**マリゴールド**: もう一つの方法が、**PORO**（Plain Old Ruby Object）。Active Record を継承しない、普通の Ruby のクラスでルールを書くんだ。

```ruby
module Ticketing
  class RefundPolicy
    HOURS_BEFORE_START = 72

    def initialize(starts_at:)
      @starts_at = starts_at
    end

    def refundable_at?(time)
      time <= @starts_at - (HOURS_BEFORE_START * 60 * 60)
    end
  end
end

policy = Ticketing::RefundPolicy.new(starts_at: Time.new(2026, 11, 15, 10, 0, 0, "+09:00"))
p policy.refundable_at?(Time.new(2026, 11, 12, 10, 0, 0, "+09:00"))
p policy.refundable_at?(Time.new(2026, 11, 12, 10, 1, 0, "+09:00"))
```

```bash
ruby refund_policy_demo.rb
```

```text
true
false
```

**初花**: `ruby` コマンドだけで動いた。Railsもデータベースもなしで。

**マリゴールド**: そこがPOROの強みだよ。`72.hours` はRailsの書き方だから使えないけど、そのぶん、このクラスは **どこにも依存していない**。テストも一瞬で終わる。

| | Active Record に書く | PORO に書く |
|---|-------------------|-----------|
| テストに要るもの | データベース・Rails・関連するレコード | Ruby だけ |
| ルールの置き場所 | テーブルと同じクラス | ルールの名前のクラス（`RefundPolicy`） |
| 保存 | `save` でそのまま | 別の仕組み（リポジトリ）が要る |
| 書く量 | 少ない | 多い（保存の変換も書く） |
| 向いている場所 | ルールが少ない・単純なところ | ルールが多く、よく変わるところ |

**初花**: どっちも一長一短なんだね。本書はどっちにするの？

**マリゴールド**: **コアドメインだけPOROにする**。第5章で決めた「力を注ぐ場所」に、手間のかかるほうの道具を使うんだ。イベント管理は、Active Record のままにするよ。

---

## 7.5　Railsの慣習を活かす部分、分離する部分

**初花**: POROにするなら、Railsの便利な機能は全部使えなくなるの？

**マリゴールド**: 使える場所では、どんどん使うよ。分けるのは「業務のルール」だけ。入口と出口は、Railsの得意分野だからね。

| Railsの機能 | 本書での使い方 |
|------------|-------------|
| ルーティング・コントローラ・ビュー | そのまま使う。コントローラは薄くする（第13章） |
| マイグレーション・Active Record | そのまま使う。コアドメインでは「保存のための入れ物」にする |
| バリデーション | 入力の形のチェック（空・形式）に使う。業務のルールはドメイン層へ（第13章） |
| コールバック | 保存の都合（正規化など）だけに使う。メールや決済は呼ばない（第12章） |
| Action Mailer・Active Job | そのまま使う。ドメインイベントから呼ぶ（第12章） |
| `rails-i18n`・`travel_to` などのテストの道具 | そのまま使う |

| ドメイン層に移すもの | 理由 |
|------------------|------|
| 定員・期限・返金・状態の変わり方のルール | 第3章で散らばったもの。一か所にまとめる |
| 金額・人数・メールアドレスのような値の決まり | 値オブジェクトにする（第8章） |
| 予約の状態の変わり方 | 自由に書き換えられないようにする（第14章） |

## 7.6　Repositoryを導入する判断基準

**初花**: POROにすると、保存はどうするの？ `save` がないんだよね。

**マリゴールド**: **リポジトリ** という、保存と読み込みを担当するクラスを作るよ。ドメインのオブジェクトを渡すと保存してくれて、IDを渡すと組み立てて返してくれる。中では Active Record を使うんだ。

```text
ユースケース ──「予約を保存して」──▶ リポジトリ ──▶ Active Record ──▶ データベース
              ◀──「予約（PORO）」──              ◀──  行       ◀──
```

**初花**: 便利そう。全部のモデルに作る？

**マリゴールド**: 作らないよ。リポジトリは、ドメインのオブジェクトと Active Record の間で **変換を書く手間** がかかるからね。判断の基準を決めておこう。

| リポジトリを作る | 作らない |
|---------------|--------|
| コアドメインの集約（第9章） | 支援サブドメインのモデル（`Event` の登録） |
| ドメインのオブジェクトがPOROで、保存の形と違う | Active Record のモデルを、そのままドメインモデルとして使っている |
| 「どう保存するか」をテストで差し替えたい | 一覧や検索の画面のための読み込み（第10章で詳しく） |

詳しい作り方は第10章で扱います。

## 7.7　ディレクトリ構成を決める

**初花**: いよいよフォルダだね。

**マリゴールド**: 層ごとにフォルダを作って、その中をコンテキストで分けるよ。Railsは `app/` の下のフォルダを、名前空間の根っこ（ルート）として自動で読み込むから、`app/domain/ticketing/reservation.rb` に書いたクラスは `Ticketing::Reservation` になる。

| フォルダ | 層 | 定数の例 |
|---------|----|---------|
| `app/domain/` | ドメイン（コンテキストをまたいで使う値） | `Money` |
| `app/domain/ticketing/` | ドメイン（予約） | `Ticketing::Reservation` |
| `app/usecases/ticketing/` | アプリケーション | `Ticketing::ReserveSeats` |
| `app/infrastructure/ticketing/` | インフラ（リポジトリ） | `Ticketing::ReservationRepository` |
| `app/infrastructure/billing/` | インフラ（決済のアダプター） | `Billing::PaymentGateway` |
| `app/models/` | インフラ（Active Record）・イベント管理 | `Event`・`Reservation` |
| `app/controllers/`・`app/views/`・`app/mailers/` | プレゼンテーション | `ReservationsController` |

**初花**: `Ticketing::` のクラスが、`domain` と `usecases` と `infrastructure` の3つのフォルダに分かれるんだ。

**マリゴールド**: 名前空間はコンテキストで、フォルダは層。Railsの自動読み込みは、同じ名前空間が複数のフォルダにまたがっても扱えるよ。フォルダを作って試そう。

`app/services/` は「何でも入る場所」になりやすいので、使うのをやめます。第6章で置いた決済の窓口は、インフラ層に移します。

```bash
mkdir -p app/domain/ticketing app/usecases/ticketing app/infrastructure/ticketing app/infrastructure/billing
git mv app/services/billing/payment_gateway.rb app/infrastructure/billing/payment_gateway.rb
rmdir app/services/billing app/services
```

空のフォルダは Git に記録されないので、`.keep` という空のファイルを置いておきます。

```bash
touch app/domain/ticketing/.keep app/usecases/ticketing/.keep app/infrastructure/ticketing/.keep
```

新しいフォルダが自動読み込みの対象になったかを確かめます。

```bash
bin/rails runner 'puts Rails.autoloaders.main.dirs.map { |d| d.sub(Rails.root.to_s + "/", "") }.sort'
```

出力（アプリのフォルダの部分の抜粋）:

**初花**: `app/domain` も `app/usecases` も、何も設定しないで読み込まれた。`Billing::PaymentGateway` を `infrastructure` に移しても、呼び出す側を直さなくていいんだね。

**マリゴールド**: 名前空間は `Billing` のままで、フォルダだけが変わったからね。`app/services/billing/` でも `app/infrastructure/billing/` でも、定数は同じ `Billing::PaymentGateway`。この性質のおかげで、**層を変えても呼び出し側は変わらない** んだ。

### ドメイン層のテストは Rails を読み込まない

第1章で、Railsに頼らないクラスは `spec_helper` だけで速くテストできると話しました。ドメイン層のスペックでは、Rails の代わりに `app/domain` のファイルだけを読み込む `spec/domain_helper.rb` を使うことにします。作るのは、最初のドメインのクラスを書く第8章です。

| スペック | 読み込むもの | 置き場所 |
|---------|-----------|---------|
| ドメイン層 | `spec/domain_helper.rb`（Rails なし） | `spec/domain/` |
| ユースケース・リポジトリ | `rails_helper`（Rails・データベースあり） | `spec/usecases/`・`spec/infrastructure/` |
| リクエスト | `rails_helper` | `spec/requests/` |

## 7.8　過剰な抽象化を避ける

**初花**: 層が4つもあると、何でも層を通さなきゃいけない気がしてくる。

**マリゴールド**: そこが一番の落とし穴なんだ。DDDのパターンを覚えたばかりのころは、全部に当てはめたくなる。本書で **やらない** ことも決めておこう。

| やらないこと | 理由 |
|------------|------|
| 実装が1つしかないのに、インターフェース用の抽象クラスを作る | Rubyはダックタイピングなので、同じメソッドを持っていれば差し替えられる |
| イベント管理のCRUDに、ユースケースやリポジトリを挟む | 入力して保存するだけの処理に、ルールの置き場所は要らない |
| すべてのクラスをPOROにする | Active Record で十分な場所は、Active Record のままでよい |
| 「◯◯Service」という名前のクラスを作る | 何をするクラスか分からない名前になる。ユースケースは動詞（`CancelReservation`）で名付ける |
| ドメイン層に Rails の機能を少しだけ持ち込む | 「少しだけ」が積み重なると、ドメイン層だけでテストできなくなる |

**初花**: ドメイン層の「今」を引数でもらう、っていうのも決めたほうがいい？ 第3章で、`Time.current` がいろんなところにあって、テストで `travel_to` が大変だった。

**マリゴールド**: いいね、それも決めよう。ドメイン層は「今」を自分で取りに行かず、`refundable_at?(time)` のように **外から受け取る**。今を決めるのはユースケースの仕事にする。こうすると、ドメイン層のテストでは `travel_to` が要らなくなるよ。

## 決めたこと

1. コアドメイン（予約・`Ticketing`）だけ、ドメインモデルを普通の Ruby のクラス（PORO）で書く
2. 支援サブドメイン（イベント管理）は、Active Record のモデルとコントローラだけで作る
3. `app/domain` のコードは Rails を読み込まずに動く。テストは `spec_helper` だけで実行する
4. ドメイン層は「今」を自分で取りに行かず、引数で受け取る（`now:`）
5. リポジトリは、コアドメインの集約にだけ作る

- イベント管理のような CRUD に、ユースケースやリポジトリを挟む

## 振り返り

**初花**: フォルダを作っただけなのに、どこに何を書くかが見えてきた。返金のルールなら `app/domain/ticketing`、キャンセルの手順なら `app/usecases/ticketing`。

**マリゴールド**: 置き場所が決まると、「このクラスは何の仕事をするのか」を名前を付ける前に考えるようになるよ。それが層を分ける一番の効果なんだ。

**初花**: 第II部はコードがあまり出てこなかったけど、第3章の課題一覧の、どこをどう直すかの道筋はできた気がする。

**マリゴールド**: 次はいよいよ第III部。最初は一番小さな部品、値オブジェクトから作ろう。`Money` と `ReservationCount` で、第3章の「整数 × 整数」の課題を消すよ。

## 初花のメモ帳

- MVCは画面とリクエストの分け方、DDDは業務のルールの置き方。重ねて使える
- コアドメインだけPOROにして、リポジトリで保存する。支援サブドメインはActive Recordのまま
- フォルダは層、名前空間はコンテキスト。ドメイン層は Rails を知らず、「今」も引数でもらう

## マリゴールドの one more thing

**このアーキテクチャの文書は、決めた理由まで書いておこう。**

`docs/architecture.md` には「何を決めたか」を書きました。半年後に新しいメンバーが「なぜイベント管理にはリポジトリがないの？」と聞いてきたとき、答えになるのは「何を」ではなく「なぜ」です。決めた理由・ほかに考えた案・その案を選ばなかった理由を、1つの決定につき1つのファイルに残す方法を **ADR**（Architecture Decision Record）と呼びます。第21章で新しい要件を入れるとき、ADRの書き方を練習します。今は、`architecture.md` の「決めたこと」の各行に、第5章と第7章の議論を思い出せるだけの一言を足しておくとよいでしょう。
