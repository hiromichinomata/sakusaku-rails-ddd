# 付録A　DDDの重要用語集

**初花**: 本編で出てきたDDDの言葉を、まとめて見返したい。

**マリゴールド**: 付録Aは **DDDの用語** の一覧だよ。うめチケットの業務の言葉（申込・仮予約・残席など）は、アプリの `docs/domain/glossary.md` にあるから、ここでは設計の言葉だけを並べるね。

---

## A.1　戦略的設計の用語

業務をどう分けるか、チームでどう話すかを決めるための言葉です。

| 用語 | 意味 | うめチケットでは | 章 |
|------|------|--------------|----|
| ドメイン | ソフトウェアで解きたい業務の領域 | イベントの告知・予約・決済・通知 | 4 |
| ユビキタス言語 | 業務の人と開発者が、会話でもコードでも同じ意味で使う言葉 | 申込・仮予約・予約確定・残席。`docs/domain/glossary.md` | 4 |
| 業務ルール | 業務が守る決まりごと。文章にして ID を振る | R-01〜R-14（`docs/domain/rules.md`） | 4 |
| サブドメイン | ドメインを、業務の関心ごとに分けたもの | イベント管理・予約・決済・通知 | 5 |
| コアドメイン | 事業の強みになり、いちばん力を注ぐサブドメイン | 予約（`Ticketing`） | 5 |
| 支援サブドメイン | 業務に必要だが、強みにはならないサブドメイン。素直な作りでよい | イベント管理（普通の Rails） | 5 |
| 汎用サブドメイン | どの会社にもあり、外部のサービスで済ませやすいサブドメイン | 決済（うめペイ）・通知（メール） | 5 |
| 境界づけられたコンテキスト | 1つのモデルと言葉が、同じ意味で通じる範囲 | `Ticketing`・`Billing`・`Notification`・`Audit` | 6 |
| コンテキストマップ | コンテキストどうしの関係（上流・下流と、つなぎ方）の図 | `docs/domain/context_map.md` | 6 |
| 上流・下流 | 相手の変更の影響を受ける側が下流 | イベント管理が上流、予約が下流 | 6 |
| 顧客／供給者 | 下流の要望を、上流が聞いて応える関係 | イベント管理 → 予約、決済 → 予約 | 6 |
| 公開された言語 | コンテキストの間でやり取りするための、決まった形 | ドメインイベント（`ReservationCanceled` など） | 6・12 |
| 腐敗防止層 | 外のモデルの言葉が、自分のモデルに入り込まないようにする変換の層 | `Billing::UmepayGateway`・`Ticketing::SalesInfoReader` | 6・15 |

## A.2　戦術的設計の用語

ドメインモデルをコードにするための部品の名前です。

| 用語 | 意味 | うめチケットでは | 章 |
|------|------|--------------|----|
| エンティティ | ID で見分けるもの。中身が変わっても同じもの | `Ticketing::Reservation` | 8 |
| 値オブジェクト | 中身で見分ける、変わらない値。作るときに正しさを確かめる | `Money`・`EmailAddress`・`ReservationCount`・`CancellationDeadline`・`ReservationPolicy` | 8 |
| 同一性・等価性 | エンティティは ID が同じなら同じ（同一性）、値オブジェクトは中身が同じなら同じ（等価性） | `Reservation#==` は ID で比べる | 8 |
| 不変条件 | いつでも成り立っていなければならない条件 | 予約済みの人数は定員を超えない | 8・9 |
| 集約 | 不変条件を一緒に守る、オブジェクトのまとまり。1回のトランザクションで1つだけ変える | `Ticketing::Inventory`（残席） | 9 |
| 集約ルート | 集約の入口。外からは、集約ルートのメソッドを通してだけ変える | `Inventory#reserve`・`#release` | 9 |
| リポジトリ | 集約を保存し、読み込む窓口。データベースの事情を隠す | `Ticketing::ReservationRepository`・`InventoryRepository` | 10 |
| ドメインサービス | どのエンティティにも自然に置けない、業務の判断 | `Ticketing::DoubleBookingCheck` | 11 |
| アプリケーションサービス（ユースケース） | 1つの操作の手順を組み立てる。トランザクションの範囲を決める | `Ticketing::ReserveSeats`・`CancelReservation` | 11 |
| ドメインイベント | 業務の上で起きたこと。過去形で名前を付ける | `ReservationCreated`・`ReservationCanceled`・`ReservationExpired` | 12 |
| 状態遷移 | エンティティの状態が、決まった操作でだけ変わること | 仮予約 → 予約確定 → キャンセル（`confirm`・`cancel`・`expire`） | 14 |
| ファクトリ | 正しい状態のオブジェクトを作る手順をまとめたもの | `Reservation.apply`（有料なら仮予約、無料なら予約確定） | 11・14 |

## A.3　Rails と組み合わせるときの用語

DDDの本ではあまり出てこないものの、Railsで実践するときに本書で使った言葉です。

| 用語 | 意味 | うめチケットでは | 章 |
|------|------|--------------|----|
| PORO | Rails のクラスを継承しない、普通の Ruby のオブジェクト | `app/domain` のクラスすべて | 7 |
| 層 | 役割ごとのまとまり。依存してよい向きを決める | プレゼンテーション・アプリケーション・ドメイン・インフラ（`docs/architecture.md`） | 7・19 |
| フォームオブジェクト | 画面や API の入力の形を確かめ、ユースケースに渡す値にする | `ReservationForm` | 13 |
| アダプター | 外部サービスの API を、自分の言葉の窓口に包んだもの | `Billing::UmepayGateway`・`FakePaymentGateway` | 15 |
| 冪等 | 同じ操作を何度行っても、結果が1回分と同じになること | 冪等キー（`Idempotency-Key`）・返金のジョブ | 15・16 |
| 悲観ロック | 読むときに行をロックして、ほかのトランザクションを待たせる | `InventoryRepository#find(lock: true)`（`FOR UPDATE`） | 16 |
| 楽観ロック | 書くときに、読んだあとで変わっていないかを確かめる | `lock_version`（本書では比べただけで採用せず） | 16 |
| Outbox パターン | 送るイベントを同じトランザクションでテーブルに書き、あとで確実に送る | 必要になる場面だけを説明（本書では採用せず） | 12 |
| 契約テスト | 偽物と本物の窓口に同じテストを流し、同じ約束を守らせる | `spec/support/shared_examples/payment_gateway_contract.rb` | 17 |
| ADR | 設計の判断を、理由・ほかの案・割り切りとともに1件1ファイルで残す記録 | `docs/adr/0001`〜`0003` | 7・21 |

## A.4　似ている言葉の使い分け

| 似ている言葉 | 違い |
|------------|------|
| エンティティ と Active Record のモデル | エンティティは業務の判断を持つ PORO。Active Record のモデルは、コアドメインでは保存の入れ物（`docs/architecture.md` の決めたこと7） |
| ドメインサービス と アプリケーションサービス | ドメインサービスは業務の判断をする。アプリケーションサービスは手順を組み立てるだけで、判断はしない（第11章） |
| 集約 と トランザクション | 1回のトランザクションで変える集約は、原則1つ。複数を一緒に変えるときは、理由を書いて例外にする（第9章・第16章） |
| ドメインイベント と Rails のコールバック | イベントは業務で起きたことを、聞く側を知らずに知らせる。コールバックは保存のたびに動き、副作用が隠れやすい（第12章・第18章） |
| サブドメイン と コンテキスト | サブドメインは業務の分け方（問題の側）。コンテキストはモデルの境界（解き方の側）。うめチケットでは、ほぼ1対1にした（第6章） |
| 入力の形の誤り と 業務の誤り | 入力の形の誤り（空・形式・範囲）は、入力を直せば通る（422）。業務の誤りは、今の状態とぶつかった誤り（409）（第13章・第21章） |
